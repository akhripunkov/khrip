# Дизайн Khrip

Khrip — компилируемый язык для HTTP API под Linux x86-64. Каждое решение в языке
проверяется по целям ниже, и у каждой цели есть замер. Сравниваем с Go и C#, на
задачах бэкенда — и с Python; Java и Node войдут в итоговый замер v0.13.

Цель 1 — главная. Модель не видела Khrip в обучении, поэтому описание языка
занимает место в промпте. Значит, язык должен экономить на коде больше, чем стоит
его описание, — это ограничивает размер описания и диктует синтаксис: всё, что можно
вывести, выводит компилятор, а не пишет модель. С v0.13 модель учится по скиллу
([skill/khrip/](../skill/khrip/SKILL.md)): ядро загружается всегда и кэшируется,
главы (PostgreSQL, MongoDB, ClickHouse, продакшен) модель читает сама, когда они
нужны задаче. Полный справочник — [KHRIP.md](KHRIP.md).

Подробнее о замерах — в разделе «Как проверяем» ниже и в `bench/`.

## Как выглядит API на Khrip

Компилируется и работает с v0.4; почему синтаксис такой — в [CRITERIA.md](CRITERIA.md).
Полное описание языка — [KHRIP.md](KHRIP.md).

```khrip
type NewUser {
    name: str
    email: str
}

type User {
    id: int
    ...NewUser
}

store users: map[int, User]          // долгоживущие данные объявляются явно
store last_id: int

route GET "/users/{id}" (id: int) -> User | 404 {
    return users[id] ?? 404
}

route POST "/users" (body: NewUser) -> 201 User | 400 str {
    if body.name == "" {
        return 400 "name is required"
    }
    last_id += 1
    let user = User { id: last_id, ...body }
    users[user.id] = user
    return 201 user
}

test "unknown user returns 404" {
    let res = call GET "/users/42"
    expect res.status == 404
}
```

Из одних только объявлений `route` компилятор знает всё о контракте API и сам генерирует:

- маршрутизатор и разбор параметров пути, строки запроса и тела — исходным текстом
  на Khrip, который компилируется вместе с программой (неверный ввод → `400`
  с понятным текстом, путь без такого метода → `405`);
- описания типов в данных программы, по которым работают JSON в обе стороны
  и копирование значений в постоянную память `store` — без рефлексии;
- описание OpenAPI — без аннотаций и отдельных файлов (ещё не сделано).

**Анонимные структуры** (этап токенов, часть 1). Тип `{ поле: T, ... }` пишется
везде, где пишется тип, а литерал `{ поле: значение }` — без имени типа: тип
берётся из того, куда значение идёт (`let`/`var` с типом, присваивание,
параметр, `return`, элемент списка, поле), иначе это анонимный тип его полей.
Анонимные типы структурные: те же поля (имя, тип и значение по умолчанию) в
том же порядке — один тип. Порядок — часть типа, потому что в нём поля уходят
в JSON и BSON: сортировка MongoDB `{ score: -1, name: 1 }` — не то же, что
`{ name: 1, score: -1 }`, и тип параметра одной функции не должен менять
порядок ответа другой. Литерал с ожидаемым типом берёт его порядок (как
`T { ... }`), литерал без него — свой; типы, которые отличаются только
порядком или значением по умолчанию, не смешиваются, и ошибка говорит, чем они
отличаются. Компилятор держит анонимный тип одной записью в таблице структур,
как именованный, поэтому у него одно описание типа — JSON в обе стороны,
копирование в store, маска ссылок для кучи и сборщика, проверка графа, снимок
KHRIP_DATA — и всё это тот же код, что у именованных. Именованные типы
остаются номинальными: значение анонимного типа становится именованным только
явно (`User { ...x }`), поэтому литерал, у которого есть ожидаемый тип,
проверяется полностью (лишние и недостающие поля, типы); тело `call` с путём-
литералом получает тип тела маршрута. Молча другой тип получает только литерал
без ожидаемого типа — как словарь. Тот же текст `{k: v}` раньше был словарём с
ключом — значением `k`; чтобы смысл не менялся молча, голое имя ключом словаря
— ошибка (`{"k": v}` или `{(k): v}`), а литерал, который был бы таким словарём
(имена полей — переменные int или str, значения их не упоминают), — ошибка с
той же подсказкой. В сгенерированном коде (маршрутизатор, снимок store)
анонимный тип называется `__anon<номер>`, в сообщениях — записью типа.

## Удобство для нейросетей и экономия токенов

Критерии, по которым устроен язык, чтобы модель писала на нём быстрее и дешевле, —
с замерами и обоснованием — в [CRITERIA.md](CRITERIA.md). Коротко:

1. Строгая статическая типизация: тип каждого значения известен однозначно; типы
   обязательны на границах, внутри функций выводятся; нет неявных преобразований и `null`.
2. Знакомый синтаксис — выжимка из Go, Rust, TypeScript, Python, Swift и C#. Где языки
   согласны — делаем так же; где расходятся — выбираем одно и подсказываем при ошибке.
3. Не писать то, что выводит компилятор: маршрутизация, проверка входа, JSON, коды
   ответов, OpenAPI — из `route` и типов; нет импортов стандартной библиотеки.
4. Ошибки громкие: фигурные скобки, проверки границ и переполнения, исчерпывающий `match` (с v0.7).
5. Все ошибки компиляции сразу, с местом, ожидаемым и найденным типом и готовым
   исправлением; JSON для агентов. Привычки других языков (`x in xs`, `.get(k, 0)`,
   `{x:.2f}`, `sum(xs)`, `return 400, "msg"`) — ошибки с подсказкой, как написать
   на Khrip.
6. Код понятен локально: нет исключений, наследования, перегрузки, макросов, `async`.
7. Встроенные тесты.
8. Описание языка окупает себя: ядро скилла — не больше 3000 токенов, глава — не
   больше 900 (это проверяет набор тестов, как и то, что примеры скилла
   компилируются, а его правила сходятся с компилятором).

## Скорость, память, запуск и размер

1. **Нативный код без посредников.** Компилятор сам генерирует машинный код x86-64
   и собирает статический ELF без libc. Маленький бинарник, старт за миллисекунды.
2. **Каждому ядру свой рабочий поток, без общего состояния.** У потока свой `epoll`
   (позже `io_uring`) и свой сокет с `SO_REUSEPORT`, поэтому потокам не нужно
   синхронизироваться на каждом запросе. Синхронизация есть только у `store`: первое
   обращение запроса к нему берёт блокировку до конца запроса — разделяемую, если
   компилятор доказал, что маршрут только читает, иначе исключительную.

   Доказательство «только читает» консервативно: ложное «чтение» — это гонка
   данных. Маршрут читающий, если ни одно его выражение не пишет в значение,
   которое может быть из `store`: свежие значения (литерал, `copy()`, `split`,
   локальный словарь `{}`, куда кладут только свежее) менять можно, псевдонимы
   `store` — нет. Конец выражения и цель присваивания анализ находит по грамматике
   парсера, а не по строкам текста; набор держит генератор маршрутов с
   псевдонимами (`tests/rw_gen.py`: ни одного ложного read) и мутации
   компилятора. `khc check --locks` показывает решение для каждого маршрута.
3. **Запрос — сопрограмма, ожидание — обычный вызов.** Как горутины в Go, без
   `async`/`await`: `fetch` и `sleep` останавливают только свою сопрограмму, поток
   выполняет другие запросы. Стек запросов у потока один; кадры ждущей сопрограммы
   копируются в кучу, только когда стек нужен другой, поэтому ждущий запрос стоит
   несколько КБ, а запрос, который не ждёт, не стоит ничего. На время ожидания
   блокировка `store` отпускается, а запрос публикует свои ссылки на `store` (запись
   контекста, ниже), поэтому то, что он держит, сборщик не освободит. Сопрограммы не
   вытесняются: долгое вычисление держит свой поток.
4. **Арена на запрос, сборка мусора только для `store`.** Выделение памяти внутри
   обработчика — сдвиг указателя; освобождение всей памяти запроса — сброс указателя
   после ответа. Объект вне арены (данные `store`) не может ссылаться на арену: запись
   значения внутрь такого объекта копирует значение в постоянную память — проверка
   по адресу, без пометок в типах; общие ссылки и циклы внутри значения сохраняются.
   Заменённые и удалённые значения `store` освобождает сборщик: объекты не
   перемещаются (псевдонимы, изменения на месте и адреса вариантов не меняются);
   разметка идёт в отдельном потоке кусками до 200 мкс, которые задерживают только
   пишущие запросы, читающие идут параллельно. Запрос, который ждёт (`fetch`, `sql`,
   `sleep`, хеш пароля), при отпускании блокировки публикует свои ссылки на `store`,
   поэтому то, что он держит, не освобождается. Свободные страницы возвращаются
   системе. Устройство — в разделе «Сборщик `store`» ниже.

   Отсюда правило для библиотеки: её функции не пишут в поля объектов, до которых
   может дотянуться код программы (такой объект может лежать в `store`), — барьер
   компилятор вставляет только в код программы. Запись библиотеки в такой объект
   допустима, только если компилятор сам вставит для неё барьер; контейнеры она
   меняет только функциями ядра, у которых барьеры свои (`push`, запись в map).
   Типы, которые библиотека меняет на месте (`MongoCursor`, `BsonBuilder`, `Buf`),
   положить в `store` нельзя — это ошибка компиляции. На этом же правиле держатся
   барьеры SATB сборщика мусора `store`: отдельной таблицы барьеров для функций
   библиотеки не нужно.

   **Память вне `store`** (этап памяти). Арена после запроса не отдаётся вся:
   две последние свободные сопрограммы потока держат тёплые арены до 8 МБ,
   остальные остывают до 32 КБ, а буферы ответа — до 4 КБ, — так запросы по
   1–4 МБ не платят отказами страниц, а простаивающие сопрограммы не держат память
   самого большого своего запроса. Буферы соединения берутся из запаса потока,
   только пока у соединения есть работа: молчащее соединение стоит 0,2 КБ, а не
   8 КБ (Go — 22), это нужно потокам v0.14. Словарь растёт по частям: вставка
   нового ключа готовит до 32 КБ новой памяти или переносит 64 записи, поэтому
   рост словаря на миллионы ключей не останавливает `store` на секунды.
5. **Разбор без копирования.** `str` — это указатель и длина внутри буфера чтения.
   Заголовки, путь и поля JSON не копируются, пока их не нужно сохранить.
   Скопированная строка короче 64 КБ (в `store`, склейка) — один объект: длина и
   адрес байтов — в одном слове заголовка, байты сразу за ним; оба вида строки
   читаются одними и теми же тремя командами, без ветвления.

   **Компактные данные `store`** (этап памяти, часть 3): массивы словаря — прямо в
   заголовке, признак «жива» и значения `bool` — байтами, таблица — u32 на слот;
   заголовок списка — 16 байт, копия получает ёмкость своего слота; ключ словаря,
   равный полю значения, не копируется второй раз; большой массив растёт на месте
   в запасе чистых страниц. Живые данные на запись — 0,76–1,26 от Go (было
   1,16–1,90).
6. **Всё, что известно при компиляции, делается при компиляции.** Маршрутизация —
   сгенерированный код под конкретные маршруты. JSON пока работает по описаниям типов
   одним общим кодом; специализированный код под каждый тип — следующий шаг.

   **Цепочки методов** (этап скорости). `m.values()` и цепочки списка от двух
   звеньев с `filter`, `map`, `any`, `all`, `count`, `find`, `sort_by` компилятор
   сливает в один проход по массивам без промежуточных списков. Поэтому семантика
   цепочек — поэлементная, как у LINQ, итераторов Rust и Java Streams: элемент
   проходит все лямбды до следующего, `any`, `all`, `find` останавливаются на
   решающем, а паника — от первого по порядку элемента. Сливаются только лямбды
   без побочных действий (записи, вывода, вызовов пишущих функций), остальные
   цепочки идут метод за методом. Неизменные подвыражения лямбд (`q.lower()` от
   параметра или `let`) вычисляются один раз до цикла, а `x.lower().contains(y)`
   у ASCII-строки ищет без её копии.
7. **SIMD там, где API тратит время.** Поиск `\r\n` в заголовках, проверка и
   экранирование строк JSON, проверка UTF-8, перевод регистра — через SSE2 и AVX2 с
   проверкой возможностей процессора и запасным путём.
8. **Свой TLS и криптография в машинном коде.** Клиент TLS 1.3, сертификаты и
   криптография — в библиотеке, без OpenSSL: бинарник самодостаточен. Горячие
   места (AES-NI, PCLMULQDQ, ChaCha20, SHA-256/512, умножение Монтгомери) —
   машинный код, который пишет компилятор, как и SIMD.
9. **Оптимизации генератора кода.** Уже есть: локальные переменные в регистрах rbx,
   r12–r15 с выбором по весу использования в циклах (значения живут в регистрах между
   итерациями), встраивание маленьких функций, слияние сравнения с переходом,
   непосредственные операнды, компактный пролог, операнды без стека, свёртка
   констант, пересылка записи в чтение. Дальше — кэш вершины стека вычислений в
   R8–R11 и дешёвый вызов функций. Контракт со сборщиком `store`: значение, живое
   через вызов, лежит в rbx, rbp, r12–r15 или в памяти (стек, арена); будущий кэш
   вершины стека в R8–R11 сбрасывается в память перед вызовом.
10. **Ничего лишнего в бинарнике.** Нет libc; сборщик мусора попадает только в
   программы со `store`, проверки и журнал сборщика — только в программы, собранные
   с `KHRIP_GC_VERIFY` и `KHRIP_GC_LOG`; в программу попадают только вызванные
   функции библиотеки. Библиотеки драйверов MongoDB и ClickHouse
   подключаются, только если программа пользуется их именами (точное имя, которое
   программа не объявляет сама; функция — только вызовом), а их тексты компилятор
   читает, только если в программе есть похожее имя, поэтому программа без них не
   платит ни размером, ни временем компиляции. Отсюда размер в десятки килобайт, старт без
   прогрева и расход памяти, близкий к объёму реальных данных.

## Сборщик `store`

Проект и замеры каждого шага — [v0.13-store-gc.md](design/v0.13-store-gc.md).

**Куча.** Данные `store` лежат в своей области: классы размеров от 16 Б до 32 КБ
в спанах по страницам 8 КБ (как у Go), большие объекты — в своих спанах, повторно
занимаются сначала самые низкие адреса. Заголовков у объектов нет: начало объекта,
пометка и «в этом слове может быть ссылка» — битовые карты по постоянным адресам
(2–4 % живого). Ссылки точные: биты ставит выделение по типу значения, поэтому
разметке не нужно описание типа; слова ожидающих запросов (ниже) — единственное
место, где ссылка угадывается по значению. Объекты не перемещаются.

**Сборка.** Цель — помеченное × (1 + `KHRIP_GC`/100), `KHRIP_GC` = 50, не меньше
`KHRIP_GC_MIN_MB` (4 МБ); сборка начинается на 70 % пути к цели. Множитель запаса
всегда 1: адаптивный (до 8 при высоком выживании) этап памяти убрал — при смене
фазы (рост, затем замены) он давал пик 2 × Go. Начало — под
исключительной блокировкой (корни и записи, единицы мкс); разметка, её конец и
уборка — кусками до `KHRIP_GC_SLICE_US` (200 мкс) под мьютексом писателей:
читающие запросы идут, пишущие — между кусками. Доля разметки растёт с кучей: ниже
цели — четверть времени, выше — половина, выше 1,25 цели — всё; выше цели
писатели помогают разметке сами при последнем отпускании (по выделенному, выше
1,5 цели — куском). Барьер SATB серит
старое значение каждой записи указателя в `store` во время разметки (компилятор —
в коде программы, библиотека — в функциях контейнеров: рост, `pop`, `truncate`,
`clear`, `remove_at`, `reverse`, `sort`, `sort_by`, сжатие словаря), новые объекты
чёрные.
Массивы больше 2 КБ размечаются кадрами по 256 слов. Возврат памяти: свободные
страницы сверх 1,1 цели уходят системе (`MADV_DONTNEED`, вне блокировки), после
10 с без выделений — все. У жёсткого предела (max(2 цели, цель + 64 МБ)) запрос,
который держит `store` исключительно, собирает сам, опубликовав себя.
`KHRIP_GC_LIMIT_MB` — мягкий предел цели.

**Записи и окна.** Запрос, задача и тест, которые взяли `store` и отпускают его
посреди работы (окно: `fetch`, `sleep`, хеш пароля, драйверы), сначала публикуют
запись контекста — слова регистров, стека, контекста и буферов со значением в
`store`, а арену — границами; сборщик просматривает арену лениво, а если контекст
продолжит раньше, тот передаёт её сам. Окно подчиняется правилам:
- **W1** — код окна не пишет в арену ниже опубликованной границы (с проверками —
  хеш при отзыве записи);
- **W2** — не читает изменяемых объектов `store`;
- **W3** — каждая паника в окне доходит до `__store_release_final`, которое берёт
  блокировку снова, чтобы отозвать запись.

Места окон перечислены в `tests/store_windows.sh` (`__store_release_keep` в
`__co_wait`, `__fetch`, `__pbkdf2_unlocked`, `mongo_command`, `__ch_run`):
новое место не пройдёт набор тестов, пока его не проверят по W1–W3.

**Проверка при ревью** кода рантайма и библиотеки:
- никаких ссылок в `store` из структур кучи библиотеки (запасы соединений, кэши):
  сборщик их не видит;
- отпускать блокировку посреди работы — только через `__store_release_keep` в
  проверенных местах; разблокировка без записи — только внутри API блокировки;
- запись библиотеки в объект, который может быть в `store`, — только через функции
  с барьером;
- типы, которые библиотека меняет на месте, — ошибка компиляции в `store`.

**Настройки разработчика** (пользовательские — в README): `KHRIP_GC_VERIFY=1` —
полные проверки (граф `store` от корней, куча, записи в начале каждой сборки,
независимая разметка до уборки, яд 0xDE в освобождённом), `=fast` — те же
проверки, но с быстрым путём выделения; `KHRIP_GC_STRESS=1` — сборка каждые 64 КБ
выделений (у большой кучи — каждую четверть помеченного), куски по 5 мкс, в тестах
— и в окнах, с проверками; `KHRIP_GC_SLICE_US` — длина куска. Проверки и
`KHRIP_GC_LOG` попадают в программу, только если её собирают с этими
переменными (и в `khc test`). Только для тестов сборщика: `KHRIP_GC_FAULT=hbuf`
и `hbuf2` (отказ памяти на передачу арены) и `KHRIP_GC_WINDOW_CYCLE=1` (каждое
окно сервера начинает сборку — так `tests/gc.sh` проверяет каждый вид окна
посреди разметки без расчёта на время). Строки: `KHRIP_SIMD=0|1|2` понижает
уровень SIMD, `KHRIP_STRCACHE=off|stress` — кэш строк, `KHRIP_STR_COMPACT=0` —
прежний вид копий строк.

## Как проверяем

**Веб-серверы** — `bench/run.sh`. Одни и те же сценарии на Khrip, Go (`net/http`) и C#
(ASP.NET Core Minimal API, JIT и Native AOT), идиоматичный код без экзотических настроек.
Сервер и нагрузочный клиент `wrk` работают на разных ядрах.

| Сценарий | Что проверяет | С какого шага |
|---|---|---|
| `GET /plaintext` | накладные расходы HTTP-стека | v0.2 |
| `GET /json` | сериализация JSON на каждый запрос | v0.2 (вручную), v0.4 (из типов) |
| CRUD в памяти | параметры пути, разбор и проверка тела, хранилище | v0.4 |
| шлюз к медленному сервису | запросы, которые ждут, не держат поток | v0.10 |
| CRUD с PostgreSQL | драйвер БД, пул, транзакции | v0.12 |

Метрики: запросы в секунду, задержка p50 и p99, пиковая память, размер артефакта,
время старта.

**Задачи бэкенда** — `eval/perf.sh`: решения задач eval на Khrip, Go, C# и Python под
реалистичными смесями запросов. С v0.13 память и задержки меряются методом v2: одна и
та же постоянная частота для всех языков (`wrk2 -R`, `RATE_MODE=1`), прогрев 60 с,
замер 60 с, RSS каждые 100 мс; иначе быстрый сервер за то же время создаёт больше
данных и хранит больше. `bench/tools/quiet.sh` убирает контейнеры баз с ядер сервера.

**Вычисления** — `bench/compute/run.sh`: одинаковые задачи на одном ядре (рекурсия,
цикл с памятью; набор будет расти: сортировка, хеширование, разбор JSON), время от
запуска до выхода, проверка одинакового ответа.

**Токены** — `bench/tokens/count.mjs` считает размер одинаковых программ несколькими
токенизаторами: OpenAI o200k и cl100k и публичным токенизатором Anthropic;
`bench/tokens/skill.mjs` — стоимость задачи для агента со скиллом.

**ИИ пишет код** — набор задач «напиши такой API» с готовыми тестами
([eval/](../eval/README.md)). Модель получает скилл Khrip (ядро — в system prompt,
главы читает сама) и текст задачи; те же задачи решаются на Go, C# и Python. Слепая
проверка (`eval/blind.py`) — на моделях нескольких поставщиков, которые не
участвовали в разработке; считаем:

- долю задач, решённых с первой попытки и не больше чем за пять (вывод
  компилятора или проверки уходит модели следующим сообщением);
- **стоимость решённой задачи**: счёт поставщика за каждый вызов (входные токены,
  включая скилл, кэш и выходные) по всем итерациям. Это главная метрика цели 1.

Выигрыш объявляем только после замеров. Самокомпиляция и прохождение тестов доказывают,
что компилятор работает; скорость доказывают отдельные измерения.

## Открытые вопросы

- `store` сейчас — общее хранилище под одной блокировкой на запрос. Если она станет
  узким местом — блокировки по отдельным `store` или шардирование по ключу.
- Снимок KHRIP_DATA без исключительной блокировки — для больших `store`: сейчас
  сохранение — JSON всего `store` под блокировкой раз в секунду после изменений.
- Вытеснение сопрограмм: долгий обработчик, занятый процессором (большой JSON),
  держит остальные соединения своего потока.
- В маршруте без базы нельзя отличить поле, присланное как `null`, от не
  присланного (это умеет только `SET {patch}` в `sql`), поэтому JSON Merge Patch со
  стиранием через `null` в памяти не написать.
- Синтаксис обработки ошибок вне маршрутов (`?` как в Rust или явный `else`).
- Формат модулей и пакетов.
