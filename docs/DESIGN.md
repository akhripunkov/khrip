# Дизайн Khrip

Khrip — компилируемый язык для HTTP API под Linux x86-64. Каждое решение в языке
проверяется по целям ниже, и у каждой цели есть замер. Сравниваем с Go и C#.

| # | Цель | Как меряем | v0.7 сейчас |
|---|---|---|---|
| 1 | **ИИ пишет код на Khrip быстрее и дешевле.** При сравнимом результате на основных задачах — меньше токенов, на любой доступной модели | токены на решение задачи: код + спецификация в промпте + итерации исправления ошибок (v1.0); размер кода в токенах нескольких токенизаторов (`bench/tokens`) | hello — 46 токенов против 133 у C# и 191 у Go; CRUD — 252 против 283 у C#, 289 у Python и 716 у Go; TODO API — 349 против 410, 412 и 974 (o200k); код компилируется и проходит те же сценарии; спецификация [KHRIP.md](KHRIP.md) — ~2400 токенов; все ошибки сразу, с подсказками |
| 2 | **Многопоточность и веб-серверы** лучше, чем у Go и C# | запросы в секунду и p99 на всех ядрах (`bench/run.sh`) | на 2 ядрах в 2,1 раза больше запросов, чем у C#, и в 3,2 раза больше, чем у Go; p99 на json лучше, на plaintext шумит |
| 3 | **Скорость вычислений** выше | задачи на одном ядре (`bench/compute`) | решето — на уровне Go и C# AOT; рекурсия — в 1,4 раза медленнее (стоимость вызова) |
| 4 | **Память** — лучшая или близкая к лучшей | пиковый RSS сервера под нагрузкой | 2,1 МБ против 14,8 у Go и 41–95 у C# |
| 5 | **Быстрый запуск** | от запуска процесса до первого ответа | 14 мс против 31 у Go и 40–549 у C# |
| 6 | **Небольшой размер приложения** | размер того, что кладётся на сервер | 57 КБ (hello), ~100 КБ (CRUD), 150 КБ (погодный бэкенд) против 8 МБ у Go и 9 МБ у C# AOT |

Цель 1 — главная. Модель не видела Khrip в обучении, поэтому спецификация языка
занимает место в промпте каждого запроса. Значит, язык должен экономить на коде больше,
чем стоит его описание, — это ограничивает размер спецификации и диктует синтаксис:
всё, что можно вывести, выводит компилятор, а не пишет модель.

Подробнее о замерах — в разделе «Как проверяем» ниже и в `bench/`.

## Как выглядит API на Khrip

Компилируется и работает с v0.4; почему синтаксис такой — в [CRITERIA.md](CRITERIA.md).
Полное описание языка — [KHRIP.md](KHRIP.md).

```khrip
type NewUser {
    name: str
    email: str
}

type User {
    id: int
    ...NewUser
}

store users: map[int, User]          // долгоживущие данные объявляются явно
store last_id: int

route GET "/users/{id}" (id: int) -> User | 404 {
    return users[id] ?? 404
}

route POST "/users" (body: NewUser) -> 201 User | 400 str {
    if body.name == "" {
        return 400 "name is required"
    }
    last_id += 1
    let user = User { id: last_id, ...body }
    users[user.id] = user
    return 201 user
}

test "unknown user returns 404" {
    let res = call GET "/users/42"
    expect res.status == 404
}
```

Из одних только объявлений `route` компилятор знает всё о контракте API и сам генерирует:

- маршрутизатор и разбор параметров пути, строки запроса и тела — исходным текстом
  на Khrip, который компилируется вместе с программой (неверный ввод → `400`
  с понятным текстом, путь без такого метода → `405`);
- описания типов в данных программы, по которым работают JSON в обе стороны
  и копирование значений в постоянную память `store` — без рефлексии;
- описание OpenAPI — без аннотаций и отдельных файлов (ещё не сделано).

## Удобство для нейросетей и экономия токенов

Критерии, по которым устроен язык, чтобы модель писала на нём быстрее и дешевле, —
с замерами и обоснованием — в [CRITERIA.md](CRITERIA.md). Коротко:

1. Строгая статическая типизация: тип каждого значения известен однозначно; типы
   обязательны на границах, внутри функций выводятся; нет неявных преобразований и `null`.
2. Знакомый синтаксис — выжимка из Go, Rust, TypeScript, Python, Swift и C#. Где языки
   согласны — делаем так же; где расходятся — выбираем одно и подсказываем при ошибке.
3. Не писать то, что выводит компилятор: маршрутизация, проверка входа, JSON, коды
   ответов, OpenAPI — из `route` и типов; нет импортов стандартной библиотеки.
4. Ошибки громкие: фигурные скобки, проверки границ и переполнения, исчерпывающий `match` (с v0.7).
5. Все ошибки компиляции сразу, с местом, ожидаемым и найденным типом и готовым
   исправлением; JSON для агентов.
6. Код понятен локально: нет исключений, наследования, перегрузки, макросов, `async`.
7. Встроенные тесты.
8. Спецификация — не больше ~3000 токенов и окупает себя.

## Скорость, память, запуск и размер

1. **Нативный код без посредников.** Компилятор сам генерирует машинный код x86-64
   и собирает статический ELF без libc. Маленький бинарник, старт за миллисекунды.
2. **Каждому ядру свой рабочий поток, без общего состояния.** У потока свой `epoll`
   (позже `io_uring`) и свой сокет с `SO_REUSEPORT`, поэтому потокам не нужно
   синхронизироваться на каждом запросе. Синхронизация есть только у `store`: первое
   обращение запроса к нему берёт блокировку (мьютекс на futex) до конца запроса.
3. **Арена на запрос.** Выделение памяти внутри обработчика — сдвиг указателя;
   освобождение всей памяти запроса — сброс указателя после ответа. Сборщика мусора нет,
   поэтому нет и пауз, которые портят p99. Объект вне арены (данные `store`) не может
   ссылаться на арену: запись значения внутрь такого объекта копирует значение
   в постоянную память — проверка по адресу, без пометок в типах. Удалённые из `store`
   данные пока не освобождаются.
4. **Разбор без копирования.** `str` — это указатель и длина внутри буфера чтения.
   Заголовки, путь и поля JSON не копируются, пока их не нужно сохранить.
5. **Всё, что известно при компиляции, делается при компиляции.** Маршрутизация —
   сгенерированный код под конкретные маршруты. JSON пока работает по описаниям типов
   одним общим кодом; специализированный код под каждый тип — следующий шаг.
6. **SIMD там, где API тратит время.** Поиск `\r\n` в заголовках, проверка и
   экранирование строк JSON — через SSE2 и AVX2 с проверкой возможностей процессора
   и запасным путём.
7. **Оптимизации генератора кода.** Уже есть: локальные переменные в регистрах rbx,
   r12–r15 с выбором по весу использования в циклах (значения живут в регистрах между
   итерациями), встраивание маленьких функций, слияние сравнения с переходом,
   непосредственные операнды, компактный пролог. Дальше — кэш вершины стека
   вычислений в R8–R11 и дешёвый вызов функций.
8. **Ничего лишнего в бинарнике.** Нет сборщика мусора и libc; в программу попадают
   только вызванные функции библиотеки. Отсюда размер в десятки килобайт, старт без
   прогрева и расход памяти, близкий к объёму реальных данных.

## Как проверяем

**Веб-серверы** — `bench/run.sh`. Одни и те же сценарии на Khrip, Go (`net/http`) и C#
(ASP.NET Core Minimal API, JIT и Native AOT), идиоматичный код без экзотических настроек.
Сервер и нагрузочный клиент `wrk` работают на разных ядрах.

| Сценарий | Что проверяет | С какого шага |
|---|---|---|
| `GET /plaintext` | накладные расходы HTTP-стека | v0.2 |
| `GET /json` | сериализация JSON на каждый запрос | v0.2 (вручную), v0.4 (из типов) |
| CRUD в памяти | параметры пути, разбор и проверка тела, хранилище | v0.4 |
| CRUD с PostgreSQL | асинхронный ввод-вывод, драйвер БД | после v1.0 |

Метрики: запросы в секунду, задержка p50 и p99, пиковая память, размер артефакта,
время старта.

**Вычисления** — `bench/compute/run.sh`: одинаковые задачи на одном ядре (рекурсия,
цикл с памятью; набор будет расти: сортировка, хеширование, разбор JSON), время от
запуска до выхода, проверка одинакового ответа.

**Токены** — `bench/tokens/count.mjs` считает размер одинаковых программ несколькими
токенизаторами: OpenAI o200k и cl100k и публичным токенизатором Anthropic.

**ИИ пишет код** — набор задач «напиши такой API» с готовыми тестами (шаг v1.0).
Модель получает `KHRIP.md` и текст задачи; те же задачи решаются на Go и C#. Прогоняем
на нескольких моделях разных поставщиков и считаем:

- долю задач, которые проходят тесты с первой попытки и за три итерации с ошибками
  компилятора;
- **токены на решённую задачу**: входные (включая спецификацию языка) и выходные,
  по всем итерациям. Это главная метрика цели 1.

Выигрыш объявляем только после замеров. Самокомпиляция и прохождение тестов доказывают,
что компилятор работает; скорость доказывают отдельные измерения.

## Открытые вопросы

- `store` сейчас — общее хранилище под одной блокировкой на запрос. Если она станет
  узким местом — блокировки по отдельным `store` или шардирование по ключу.
- Освобождение памяти `store` при перезаписи и удалении.
- Синтаксис обработки ошибок вне маршрутов (`?` как в Rust или явный `else`).
- Формат модулей и пакетов.
