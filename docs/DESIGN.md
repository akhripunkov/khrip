# Дизайн Khrip

Khrip — компилируемый язык для HTTP API под Linux x86-64. Каждое решение в языке
проверяется по целям ниже, и у каждой цели есть замер. Сравниваем с Go и C#.

| # | Цель | Как меряем | v0.2 сейчас |
|---|---|---|---|
| 1 | **ИИ пишет код на Khrip быстрее и дешевле.** При сравнимом результате на основных задачах — меньше токенов, на любой доступной модели | токены на решение задачи: код + спецификация в промпте + итерации исправления ошибок (v0.7); размер кода в токенах нескольких токенизаторов (`bench/tokens`) | код сервера: 169 токенов против 191 у Go и 133 у C# — проигрываем C# |
| 2 | **Многопоточность и веб-серверы** лучше, чем у Go и C# | запросы в секунду и p99 на всех ядрах (`bench/run.sh`) | 1 поток Khrip ≈ C# на 2 ядрах, в 1,5 раза быстрее Go; p99 хуже, чем у C# |
| 3 | **Скорость вычислений** выше | задачи на одном ядре (`bench/compute`) | в 1,65–1,7 раза медленнее Go: генератор кода пока самый простой |
| 4 | **Память** — лучшая или близкая к лучшей | пиковый RSS сервера под нагрузкой | 1,1 МБ против 14,7 у Go и 43–96 у C# |
| 5 | **Быстрый запуск** | от запуска процесса до первого ответа | 10 мс против 16 у Go и 38–418 у C# |
| 6 | **Небольшой размер приложения** | размер того, что кладётся на сервер | 25 КБ против 8 МБ у Go и 9 МБ у C# AOT |

Цель 1 — главная. Модель не видела Khrip в обучении, поэтому спецификация языка
занимает место в промпте каждого запроса. Значит, язык должен экономить на коде больше,
чем стоит его описание, — это ограничивает размер спецификации и диктует синтаксис:
всё, что можно вывести, выводит компилятор, а не пишет модель.

Подробнее о замерах — в разделе «Как проверяем» ниже и в `bench/`.

## Как выглядит API на Khrip

Набросок синтаксиса. Он будет уточняться по шагам дорожной карты, но направление такое:

```khrip
// users.kh — небольшой CRUD API

type User {
    id: i64
    name: str
    email: str
}

type NewUser {
    name: str
    email: str
}

store users: Map<i64, User>          // долгоживущие данные объявляются явно

route GET "/users/{id}" (id: i64) -> 200 User | 404 {
    let user = users.get(id) else {
        return 404
    }
    return 200 user
}

route POST "/users" (body: NewUser) -> 201 User | 400 str {
    if body.name == "" {
        return 400 "name is required"
    }
    let user = User { id: users.next_id(), name: body.name, email: body.email }
    users.put(user.id, user)
    return 201 user
}

test "unknown user returns 404" {
    let res = call GET "/users/42"
    expect res.status == 404
}
```

Из одних только объявлений `route` компилятор знает всё о контракте API и сам генерирует:

- разбор и проверку параметров пути и тела запроса (неверный ввод → автоматический `400`);
- сериализацию и разбор JSON для каждого типа — во время компиляции, без рефлексии;
- таблицу маршрутов — как дерево сравнений по байтам пути, без поиска по словарю;
- описание OpenAPI — без аннотаций и отдельных файлов.

## Удобство для нейросетей и экономия токенов

Новый язык не встречался модели в обучении. Поэтому всё, что модель должна знать, должно
помещаться в промпт, а всё, что она может перепутать, должно ловить компилятор. Каждый
лишний токен в коде модель пишет и читает при каждой правке, а каждая итерация
«ошибка → исправление» стоит целого запроса — поэтому экономим и на коде, и на итерациях.

1. **Знакомый синтаксис.** Берём то, что модели уже хорошо знают из Go, Rust и TypeScript:
   `fn`, `let`, `if`, `for`, фигурные скобки, типы после имени. Ничего экзотического.
2. **Спецификация помещается в промпт.** Файл `KHRIP.md` на английском (с ним модели
   работают лучше всего) содержит всю грамматику и стандартную библиотеку для HTTP
   и укладывается примерно в 4000 токенов. Это жёсткое ограничение на размер языка.
3. **Один способ сделать одно дело.** Нет синонимов, перегрузки операторов, макросов,
   наследования, неявных преобразований типов, `null` и исключений. Ошибка — это значение
   в типе результата (`-> 200 User | 404`).
4. **Всё видно локально.** Сигнатуры функций и маршрутов всегда полностью типизированы.
   Чтобы понять обработчик, не нужно читать остальной проект.
5. **Нет async/await.** Обработчик пишется как обычный последовательный код. Ожидание
   сети и базы данных берёт на себя рантайм (лёгкие корутины поверх event loop),
   а не программист. Модели часто ошибаются именно в асинхронном коде.
6. **Нет ручного управления памятью и нет сборщика мусора.** Память запроса живёт до
   отправки ответа (см. «Арена на запрос»). Ошибиться с освобождением негде; попытку
   сохранить данные запроса в долгоживущее хранилище без копирования ловит компилятор.
7. **Компилятор как наставник.** `khc check --json` выдаёт ошибки в машинном формате:
   код ошибки, точное место и готовое исправление. Цикл «написал → скомпилировал →
   исправил» должен сходиться за одну-две итерации.
8. **Встроенные тесты API.** Блоки `test` и команда `khc test` позволяют модели самой
   проверить, что API делает то, что просили.
9. **Один стиль.** `khc fmt` форматирует код единственным способом.
10. **Не писать то, что выводит компилятор.** Маршрутизация, разбор и проверка входа,
    JSON, коды ответов и OpenAPI получаются из объявления `route` и типов. Модель пишет
    только логику обработчика.
11. **Короткие, но обычные слова.** Ключевые слова и имена стандартной библиотеки
    выбираются так, чтобы токенизаторы разных моделей резали их на один-два токена
    (`fn`, `let`, `str`, `route`), без сокращений, которые модель не угадает.

## Скорость, память, запуск и размер

1. **Нативный код без посредников.** Компилятор сам генерирует машинный код x86-64
   и собирает статический ELF без libc. Маленький бинарник, старт за миллисекунды.
2. **Каждому ядру свой рабочий поток, без общего состояния.** У потока свой `epoll`
   (позже `io_uring`) и свой сокет с `SO_REUSEPORT`, поэтому потокам не нужно
   синхронизироваться на каждом запросе.
3. **Арена на запрос.** Выделение памяти внутри обработчика — сдвиг указателя;
   освобождение всей памяти запроса — сброс указателя после ответа. Сборщика мусора нет,
   поэтому нет и пауз, которые портят p99.
4. **Разбор без копирования.** `str` — это указатель и длина внутри буфера чтения.
   Заголовки, путь и поля JSON не копируются, пока их не нужно сохранить.
5. **Всё, что известно при компиляции, делается при компиляции.** Маршрутизация и JSON —
   сгенерированный код под конкретные типы, а не универсальные механизмы во время работы.
6. **SIMD там, где API тратит время.** Поиск `\r\n` в заголовках, проверка и
   экранирование строк JSON — через SSE2 и AVX2 с проверкой возможностей процессора
   и запасным путём.
7. **Оптимизации генератора кода.** Слияние соседних операций, локальные переменные
   в регистрах, кэш вершины стека вычислений в регистрах R8–R11. Это главный рычаг
   скорости вычислений: сейчас каждое промежуточное значение проходит через стек.
8. **Ничего лишнего в бинарнике.** Нет рантайма, сборщика мусора и libc. Отсюда размер
   в десятки килобайт, старт без прогрева и расход памяти, близкий к объёму реальных
   данных. Следующий шаг — выбрасывать неиспользуемые функции библиотек.

## Как проверяем

**Веб-серверы** — `bench/run.sh`. Одни и те же сценарии на Khrip, Go (`net/http`) и C#
(ASP.NET Core Minimal API, JIT и Native AOT), идиоматичный код без экзотических настроек.
Сервер и нагрузочный клиент `wrk` работают на разных ядрах.

| Сценарий | Что проверяет | С какого шага |
|---|---|---|
| `GET /plaintext` | накладные расходы HTTP-стека | v0.2 |
| `GET /json` | сериализация JSON на каждый запрос | v0.2 (вручную), v0.4 (из типов) |
| CRUD в памяти | параметры пути, разбор и проверка тела, хранилище | v0.4 |
| CRUD с PostgreSQL | асинхронный ввод-вывод, драйвер БД | после v0.7 |

Метрики: запросы в секунду, задержка p50 и p99, пиковая память, размер артефакта,
время старта.

**Вычисления** — `bench/compute/run.sh`: одинаковые задачи на одном ядре (рекурсия,
цикл с памятью; набор будет расти: сортировка, хеширование, разбор JSON), время от
запуска до выхода, проверка одинакового ответа.

**Токены** — `bench/tokens/count.mjs` считает размер одинаковых программ несколькими
токенизаторами: OpenAI o200k и cl100k и публичным токенизатором Anthropic.

**ИИ пишет код** — набор задач «напиши такой API» с готовыми тестами (шаг v0.7).
Модель получает `KHRIP.md` и текст задачи; те же задачи решаются на Go и C#. Прогоняем
на нескольких моделях разных поставщиков и считаем:

- долю задач, которые проходят тесты с первой попытки и за три итерации с ошибками
  компилятора;
- **токены на решённую задачу**: входные (включая спецификацию языка) и выходные,
  по всем итерациям. Это главная метрика цели 1.

Выигрыш объявляем только после замеров. Самокомпиляция и прохождение тестов доказывают,
что компилятор работает; скорость доказывают отдельные измерения.

## Открытые вопросы

- Семантика `store` при нескольких рабочих потоках: шардирование по ключу или общее
  хранилище с блокировками. Решаем на шаге v0.4.
- Синтаксис обработки ошибок вне маршрутов (`?` как в Rust или явный `else`).
- Формат модулей и пакетов.
