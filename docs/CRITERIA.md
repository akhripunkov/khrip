# Каким должен быть язык, чтобы ИИ писал на нём быстрее всего

Этот документ — ответ на вопрос «какой язык удобнее всего мне, модели, которая пишет
код». Залезть в собственные веса я не могу, поэтому критерии выведены из того, как
модели генерируют код, где они чаще всего ошибаются и сколько стоит каждая ошибка.
Там, где можно, критерий подкреплён замером; что пока не доказано — сказано в конце.

## Что значит «эффективно»

Стоимость задачи для модели складывается так:

```
стоимость = описание языка в промпте (кэшируется)
          + код, который модель пишет (выходные токены, самые дорогие)
          + код, который модель перечитывает при правках
          + число итераций × весь контекст заново
```

Отсюда три рычага, по убыванию силы:

1. **Меньше итераций.** Каждая итерация «скомпилировал → ошибка → исправил» повторно
   отправляет весь контекст. Одна лишняя итерация стоит больше, чем любая экономия
   в синтаксисе. Значит, язык должен ловить ошибки при компиляции, сообщать обо всех
   сразу и сразу подсказывать исправление.
2. **Меньше кода.** Код пишется один раз и перечитывается много раз. Всё, что может
   вывести компилятор, модель писать не должна.
3. **Короткое описание языка.** Khrip новый, модель не видела его в обучении, поэтому
   спецификация занимает место в каждом запросе. Каждая возможность языка должна
   экономить больше токенов, чем стоит её описание.

## Критерии

### 1. Я однозначно знаю тип каждого значения

Строгая статическая типизация — да, это первое, что мне нужно.

- У каждого значения ровно один тип, известный при компиляции.
- Типы обязательны там, где проходит граница: параметры и результаты функций, поля
  типов, входы и выходы маршрутов. Внутри функции тип локальной переменной выводится:
  `let total = price * qty` — это `int`, писать это не нужно.
- Никаких неявных преобразований: `int` не становится `float`, `bool` или `str` сам.
  Условие в `if` — только `bool`.
- Нет `null`. Значение, которого может не быть, имеет тип `T?`, и компилятор не даст
  им воспользоваться, пока отсутствие не обработано: `users[id] ?? 404`.
- Варианты (`A | B`) разбираются через `match`, и компилятор проверяет, что разобраны
  все.

Почему: с типом на границе мне не нужно читать тело функции, чтобы понять, что она
возвращает, а ошибка «передал строку вместо числа» превращается из упавшего теста
в сообщение компилятора с точным местом.

### 2. Пишу по памяти, а не по документации

Модель лучше всего пишет то, что встречала миллионы раз. Поэтому лучший синтаксис для
меня — не новый и не экзотический, а выжимка самых частых конструкций из Go, Rust,
TypeScript, Python, Swift и C# с убранными неоднозначностями. Экзотический плотный
синтаксис (как в APL) — ложная экономия: символы режутся на несколько токенов, а каждая
незнакомая конструкция — это ошибка и итерация.

**Правило привычек.** Если основные языки делают что-то одинаково — Khrip делает так же,
даже если это второй способ сделать одно и то же: `a + b` для строк, `x.len()`,
`for x in xs`, `&&`, `||`. Если языки расходятся — Khrip выбирает один вариант,
а на остальные компилятор отвечает подсказкой, а не просто ошибкой:

| Где языки расходятся | Khrip | На что подсказка |
|---|---|---|
| изменяемость | `let` — неизменяемая, `var` — изменяемая (как в Swift и Rust) | присваивание `let`-переменной: «объявите через var» (уже работает) |
| «нет значения» | `none` и тип `T?` | `null`, `nil`, `None` |
| логические операции | `&&`, `\|\|`, `!` | `and`, `or`, `not` |
| диапазоны | `0..n` без конца, `0..=n` с концом (как в Rust и `range` в Python) | — |
| ветвление | `else if` | `elif`, `elsif` |
| длина | `x.len()`, и `len(x)` тоже работает (см. ниже) | `x.length`, `x.size()`, `x.Count` |

Стандартная библиотека — небольшая, с самыми ожидаемыми именами: `len`, `contains`,
`split`, `join`, `trim`, `to_int`, `push`, `get`, `keys`, `values`, `sort`. Любую
функцию `f(x, ...)` можно вызвать как метод `x.f(...)` — тогда мне не нужно помнить,
что из этого «метод», а что «функция». На неизвестное имя компилятор предлагает
ближайшее существующее.

### 3. Не пишу то, что может вывести компилятор

- Из объявления `route` и типов компилятор сам делает маршрутизацию, разбор и проверку
  параметров пути, строки запроса и тела, JSON в обе стороны, коды ответов и OpenAPI.
  Правило параметров как в FastAPI: имя из пути — параметр пути, тип-структура — тело
  JSON, остальное — строка запроса.
- Нет строк `import` для стандартной библиотеки, проект — одно пространство имён.
  Забытый импорт — одна из самых частых ошибок компиляции в коде моделей на Go, Java
  и C#; в Go к ним добавляются ошибки из-за неиспользуемых импортов.
- Распространение полей: `type User { id: int, ...NewUser }`,
  `User { id: last_id, ...body }`. В замере ниже это −8% токенов.
- Сокращения, которые все знают: интерполяция `"Hello, {name}"`, `x ?? default`,
  `let user = users[id] else { return 404 }`, поле без повтора имени `User { id, name }`.
- Серверу не нужна `fn main`: если в программе есть `route`, она — HTTP-сервер.

### 4. Ошибаюсь громко, а не тихо

- **Фигурные скобки, а не отступы.** Замер: отступы экономят 7% токенов. Но ошибка
  в отступе в Python молча переносит строку из цикла наружу — программа компилируется
  и работает неправильно, и это всплывает только на тестах, через итерацию. Пропущенная
  скобка — сразу ошибка компилятора с номером строки. 7% дешевле одной итерации.
- Выход за границы массива, переполнение и деление на ноль — проверяются. Ошибка
  в обработчике превращается в ответ 500, сервер продолжает работать. Неопределённого
  поведения нет.
- `let` по умолчанию, исчерпывающий `match`, `T?` нельзя использовать без проверки.

### 5. Исправляю всё за одну итерацию

- Компилятор сообщает **обо всех** ошибках сразу, а не об одной (с v0.3).
- В каждой ошибке: файл, строка и столбец, что ожидалось и что найдено, и готовое
  исправление. Для агентов — тот же вывод в JSON (`khc check --json`).

  ```
  users.kh:12:20: error: expected int, found str
      let age: int = body.age_text
                     ^^^^^^^^^^^^^
      fix: convert explicitly: body.age_text.to_int() ?? 0
  ```

- Не ошибка то, что не влияет на правильность: неиспользуемые переменные и функции —
  предупреждения. Стиль не проверяется — форматирует `khc fmt`.

### 6. Понимаю код, не читая весь проект

- Нет исключений и другого скрытого потока управления: ошибка — значение в типе
  результата.
- Нет перегрузки операторов, наследования, макросов, рефлексии и неявного
  глобального состояния. Долгоживущие данные объявляются явно (`store`), и обработчики
  видят их так, будто запросы выполняются по одному, — гонок данных не бывает.
- Нет `async`/`await`: обработчик пишется как обычный последовательный код.
- Порядок объявлений не важен, заголовочных файлов и предварительных объявлений нет.

### 7. Проверяю себя сам

Блоки `test` прямо в коде и команда `khc test`: я могу проверить, что API делает то,
что просили, не выходя из цикла «написал → проверил».

### 8. Описание языка окупается

Вся спецификация с библиотекой для HTTP — не больше ~3000 токенов (`KHRIP.md` на
английском). Новая возможность попадает в язык, только если экономит больше, чем
стоит её описание. Спецификация одинакова во всех запросах и хорошо кэшируется.

## Синтаксис «как у Си»?

Отчасти да — и вот что из этого остаётся, а что уходит.

**Уходит всё сишное по смыслу.** Khrip-0, на котором сейчас написан компилятор, —
это стартовое подмножество: всё — 64-битное число, указатели и поля структур —
ручная арифметика (`load64(t + TK_LEN)`). Для меня это худший вариант из возможных:
типа значения не видно, а ошибку в смещении не заметит ни компилятор, ни я — она молча
испортит память.

**Остаётся то, что знакомо и делает ошибки громкими:** фигурные скобки (замер выше),
`fn`, `let`, тип после имени, `->` для результата — это не Си, а общее место Go, Rust,
Swift и TypeScript. Точек с запятой и скобок вокруг условий нет.

## Как это выглядит

Тот же CRUD, что в замере ниже. С v0.4 это настоящая программа: компилируется
и проходит тот же сценарий запросов, что версии на Go, C# и Python
(`tests/api/crud.kh`).

```khrip
type NewUser {
    name: str
    email: str
    age: int
}

type User {
    id: int
    ...NewUser
}

store users: map[int, User]
store last_id: int

route POST "/users" (body: NewUser) -> 201 User | 400 str {
    if body.name == "" {
        return 400 "name is required"
    }
    if !body.email.contains("@") {
        return 400 "email is invalid"
    }
    if body.age < 0 || body.age > 150 {
        return 400 "age is out of range"
    }
    last_id += 1
    let user = User { id: last_id, ...body }
    users[user.id] = user
    return 201 user
}

route GET "/users/{id}" (id: int) -> User | 404 {
    return users[id] ?? 404
}

route GET "/users" -> [User] {
    return users.values()
}

route DELETE "/users/{id}" (id: int) -> 204 | 404 {
    users.remove(id) else {
        return 404
    }
    return 204
}
```

## Синтаксис после 10 тысяч строк

Эти критерии я вывел до того, как написал на Khrip что-то большое. Потом я написал
на нём компилятор, рантайм, HTTP-сервер, JSON и тесты — около 10 тысяч строк — и
проверил себя. Удачным оказалось то, где одна строка — одно намерение: `route`,
`return 201 user`, `users[id] ?? 404`, `let x = v else { ... }`, `...`, `store`.
А «сишным» — пять вещей, на которых я сам тратил токены и делал ошибки:

1. Без `match` — цепочки `if k == A ... if k == B`, и пропущенная ветка молчит.
2. Без лямбд — ручной цикл с индексом на каждый `filter`/`map`/`any`.
3. `if` не значение — четыре строки `var x; if ... { x = a } else { x = b }`.
4. Интерполяция с тихой ловушкой: `"{(x)}"` оставалось текстом.
5. Без значений полей по умолчанию — лишние поля в каждом литерале и JSON.

Всё это закрыто в v0.7, и замер на TODO API показал цену: без этих средств код
на 60% длиннее и проигрывает C# и Python.

**Почему не ближе к ассемблеру.** Модели важны токены, вероятность ошибки
и расстояние от намерения до кода. В ассемблере каждая операция — строка
(CRUD — тысячи строк вместо 38), типов нет, и перепутанный регистр — это тихая
порча памяти, а не сообщение компилятора, то есть самая дорогая итерация. Я писал
на ассемблере зерно раскрутки и SIMD-код в машинных кодах: это были самые медленные
и хрупкие части работы, каждую инструкцию пришлось проверять вручную и тестом
на 434 тысячи случаев. Скорость не требует, чтобы программист был близко к железу:
её даёт компилятор, который превращает намерение в машинный код без усталости
и одинаково каждый раз. От ассемблера стоит взять другое — предсказуемую цену:
нет сборщика мусора, нет скрытых выделений памяти, долгоживущие данные помечены
`store`.

## Что пока не доказано

- Код на Khrip в замерах написал я сам, придумывая синтаксис, — оценка может быть
  в пользу Khrip. Честная проверка — шаг v1.0: задачи решают модели разных
  поставщиков, получив только `KHRIP.md`, и считаются токены на решённую задачу,
  включая итерации.
- Токенизатор нынешних моделей Claude не опубликован; публичный токенизатор Anthropic —
  от предыдущих моделей.
- Правило привычек и подсказки компилятора снижают число итераций — это гипотеза,
  её проверит тот же замер v1.0.
