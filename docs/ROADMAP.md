и собирает сам себя. Каждый шаг заканчивается тестами и замером в `bench/` против Go

## v0.1. Самокомпилирующийся компилятор ✅

Компилятор `khc` сразу написан на Khrip (`src/khc.kh`, подмножество
[Khrip-0](KHRIP0.md)). Первый раз его собирает зерно `bootstrap/khc0.asm` на
ассемблере x86-64; ни Go, ни C, ни других компиляторов в цепочке нет. Компилятор сам
генерирует машинный код и записывает статический ELF без libc.

Проверка (`build.sh`): зерно собирает `khc1`, тот собирает себя (`khc2`), тот снова
себя (`khc3`); `khc2` и `khc3` совпадают побайтно. Тесты: `tests/run.sh`.

## v0.2. Первый HTTP-сервер на Khrip ✅

Однопоточный сервер на `epoll` (`lib/http.kh`): неблокирующие сокеты, keep-alive,
конвейерные запросы, тело по `Content-Length`, заголовок `Date`, ошибки протокола
(400, 413, 431, 501). Библиотеки `lib/net.kh` и `lib/json.kh`. Приложение пока
определяет `fn handle(req)` — временный интерфейс до объявлений `route`.

Результат ([отчёт](../bench/results/2026-10-19-v0.2.md)): один поток Khrip —
~114–118 тыс. запросов в секунду, как C# на двух ядрах и в 1,5 раза больше Go;
1,1 МБ памяти, 25 КБ бинарник, старт 10 мс. Проигрываем по p99 (C# лучше) и по
вычислениям (в 1,65–1,7 раза медленнее Go). Добавлены замеры вычислений
(`bench/compute`) и токенов (`bench/tokens`).

## v0.3. Строгие типы: Khrip-1 ✅

Компилятор переписан на Khrip-1 (`src/*.kh`, ~6 тыс. строк) и собирает сам себя.
Цепочка раскрутки: зерно `bootstrap/khc0.asm` → `bootstrap/boot.kh` (на Khrip-0,
понимает подмножество Khrip-1) → `khc1` → `khc2` → `khc3`; `khc2` и `khc3` совпадают.

- Типы `int`, `bool`, `str`, `[T]`, `map[K, V]`, `T?`, структуры `type` с `...`;
  `??`, `let x = v else { ... }`, `if let`, интерполяция `"{x}"`, `for x in xs`,
  `for i, x in xs`, `for i in a..b`, вызов функции как метода. Условие — только
  `bool`, неявно только `T` → `T?`.
- Все ошибки сразу: файл:строка:столбец, строка исходника с указателем, подсказка
  («может быть, вы имели в виду», `null`, `elif`, `String`, `++` ...); `--json`.
- Проверки границ, переполнения и деления на ноль — паника с местом и кодом 101.
- Генератор кода: однопроходный, с распределением регистров по весу циклов
  (значения живут в rbx, r12–r15 между итерациями), встраиванием маленьких функций,
  слиянием сравнения с переходом, непосредственными операндами, компактным прологом.

Вычисления (`bench/compute`): sieve — на уровне Go и C# AOT; fib — в 1,4 раза
медленнее Go (стоимость вызова).

## v0.4. API-слой языка ✅

- `route МЕТОД "путь" (параметры) -> варианты { ... }`: параметр из пути —
  `{id}`, структура/список — тело JSON, остальное — строка запроса (`T?` — не
  обязателен). Ответ — `return 201 user`, `return 404`, `return users[id] ?? 404`;
  `str` уходит текстом, остальное — JSON. Неверные параметры и тело — 400
  с понятным текстом; путь есть, метода нет — 405.
- Маршрутизатор и разбор параметров компилятор генерирует исходным текстом на
  Khrip; JSON в обе стороны работает по описаниям типов, которые компилятор кладёт
  в данные программы.
- `store` — данные, переживающие запрос. Каждый запрос выполняется в своей арене,
  которая обнуляется после ответа; запись внутрь объектов store копирует значение
  в постоянную память (барьер записи по адресу), рост списков и словарей store идёт
  там же. Обращения к store одного запроса — под одной блокировкой.
- Паника в обработчике — ответ 500, сервер работает дальше.
- `test "имя" { ... }`, `call POST "/users" body`, `expect a == b` (при провале —
  обе стороны); `khc test`, `khc run` — сборка в память и запуск без файлов.
- Неиспользуемые функции библиотеки не попадают в программу: hello — 5,8 КБ,
  HTTP-сервер — 44 КБ.

Один поток: plaintext 126 тыс. запросов/с, json 116 тыс., p99 2,3–3,1 мс — лучше v0.2.

## v0.5. Многоядерность и арены ✅

Рабочий поток на каждое доступное ядро (`THREADS` меняет число): у каждого свой
`epoll`, свой слушающий сокет `SO_REUSEPORT`, свои соединения, своя арена запроса;
поток привязан к своему ядру. Потоки создаёт встроенная `__spawn` (clone без libc),
блокировка store — мьютекс на futex. Арена запроса — с v0.4.

## v0.6. SIMD ✅

Три примитива рантайма — поиск байта, поиск конца заголовков `\r\n\r\n` и поиск
символов, которые экранирует JSON, — встроенные функции компилятора: он сам пишет их
машинный код в трёх вариантах (AVX2 по 32 байта, SSE2 по 16, побайтно). Вариант
выбирается при старте по `cpuid` и `xgetbv` (AVX2 нужен и процессору, и ОС);
`KHRIP_SIMD=0|1` понижает уровень. На них построены разбор запроса в `lib/http.kh`
и запись и чтение строк JSON в `lib/api.kh`. Корректность: тест `tests/run/simd.kh`
сверяет все три пути с простым циклом на 434 тыс. случаев.

Замер ([отчёт](../bench/results/2026-10-19-v0.6-simd.md)), одно ядро:

| | Заголовки браузера (700 Б) | Запись JSON (3,6 КБ) | Чтение JSON |
|---|---:|---:|---:|
| побайтно | 816 нс | 2754 нс | 3391 нс |
| SSE2 | 179 нс | 550 нс | 1065 нс |
| AVX2 | **134 нс** (×6,1) | **465 нс** (×5,9) | **973 нс** (×3,5) |

На всём сервере с такими заголовками выигрыш меньше — +2% plaintext, +11% json:
основное время запроса уходит на системные вызовы.

## v0.7. Язык по опыту ✅

Написав на Khrip 10 тысяч строк (компилятор, рантайм, HTTP, JSON, тесты), я
выписал, где язык заставлял писать «как на Си» и где я ошибался, и закрыл это:

- **Варианты и исчерпывающий `match`.** `type Role = Admin | Member`,
  `type Shape = Circle { r: int } | Rect { w: int, h: int } | Empty`; `match` по
  вариантам, int, str и bool, несколько образцов через `|`, `_`. Пропущенный
  вариант — ошибка с перечнем недостающих. Перечисления в JSON — строки, остальные
  варианты — объекты с полем `"type"`; перечисления работают и в параметрах маршрутов.
  Метка варианта лежит перед полями структуры, поэтому вариант — тот же указатель,
  без упаковки.
- **Лямбды в методах списков:** `map filter find any all count sort_by`.
  Цикл и тело лямбды компилируются на месте вызова: лямбда видит локальные
  переменные, ничего не выделяет и ничего не стоит.
- **`if` и `match` — значения**, блок со значением в последней строке.
- **Значения полей по умолчанию** — и в литералах, и при разборе JSON.
- **Громкая интерполяция:** каждая `{` в строке — подстановка любого выражения,
  буквальная скобка — `\{`; пустая и незакрытая `{` — ошибка с исправлением.
  Раньше `"{(x)}"` молча оставалось текстом.
- `x == value` для `x: T?`, подсказки на `switch`, `enum`, `?:`, `and`/`or`.

Замер на новой задаче — TODO API с перечислением статусов, фильтрами, сортировкой
и статистикой; все четыре версии проходят один сценарий из 15 проверок
(`bench/tokens/samples/todo/check.sh`):

| | Khrip v0.7 | Khrip v0.6 | C# | Python FastAPI | Go |
|---|---:|---:|---:|---:|---:|
| o200k | **349** | 563 | 410 | 412 | 974 |
| Claude (публичный) | **367** | 575 | 501 | 459 | 1272 |

Честный вывод: на этой задаче Khrip v0.6 проиграл бы C# и Python. Выигрыш
на CRUD объяснялся тем, что задача хорошо ложилась на `route` и `store`; как только
появляются фильтры и перечисления, без лямбд и вариантов код растёт на 60%.

## v0.8. Связь с внешним миром ✅

Вопрос «можно ли уже написать бэкенд, который уведомляет о погоде» показал три
пробела: не было дробных чисел, исходящих запросов и фоновых задач. Закрыты так,
чтобы каждое решение окупалось по соотношению пользы и затрат:

- **`float`** — 64-битные числа, арифметика — скалярный SSE2. Целый *литерал*
  рядом с float сам становится float (`t * 2`, `t < 0`), как в Go; целую
  переменную нужно перевести явно — типы остаются строгими. Перевод десятичной
  записи в двоичную и обратно — точный, на длинных целых; печать — самая короткая
  обратимая запись, как в JavaScript (`0.1 + 0.2` → `0.30000000000000004`).
- **`fetch МЕТОД url [тело] [headers карта]`** → `Response`; если сервис не
  ответил — `status 0` и причина в `body`, поэтому одна проверка статуса закрывает
  оба случая. http — свой клиент (DNS, `/etc/hosts`, `HTTP_PROXY`, chunked);
  https — пока через `curl`: свой TLS — это тысячи строк криптографии, где ошибка
  означает уязвимость, поэтому он вынесен в отдельный шаг. Пока `fetch` ждёт сеть,
  блокировка `store` отпущена: медленный внешний сервис не останавливает остальные
  запросы.
- **`every 10 min { ... }`** — объявление, как `route`; задачи идут в отдельном
  потоке со своей ареной и не тормозят HTTP. Паника в задаче пишется в лог.
- **`KHRIP_DATA=файл`** — `store` загружается при старте и сохраняется раз в
  секунду после изменений и при SIGTERM/SIGINT (снимок через временный файл).
- `now()`, `now_ms()`, `url_encode`, `s.to_float()`.

Проверка — [examples/weather/weather.kh](../examples/weather/weather.kh): погода
по городу (Open-Meteo, без ключа), подписки с порогами, проверка каждые 10 минут,
уведомление на вебхук (подходит и Telegram). Сквозной тест `tests/weather.sh`
поднимает поддельный Open-Meteo и приёмник вебхуков — оба тоже на Khrip — и
проверяет погоду, уведомление при похолодании, отсутствие повторов, повтор после
возврата к норме и сохранение подписок через перезапуск по SIGTERM.

## v0.9. Проверка на типичных задачах ✅

Вопрос «почему ты решил, что этот подход лучше Go и C#» требовал не довода, а
замера. Сделан набор [eval/](../eval/README.md): восемь задач бэкенда с условием
без упоминания языка и общими проверками через `curl` (коды, тела, заголовки,
одновременные запросы); каждая решена на Khrip, Python FastAPI, C# и Go.

Пять задач — настроечные: на них искали, чего не хватает. Пробелы и решения:

- заголовки: `header(name)`, `set_header(name, value)`, `headers` у `call`, ответ
  `fetch` с заголовками;
- `fail(status[, message])` — прервать запрос из любой функции (как
  `HTTPException` в FastAPI): проверка ключа или токена — одна функция, а не
  по три строки в каждом маршруте;
- `random_str(n)`, `time_iso(t)`, `sha256`, `hash_password`/`check_password`
  (PBKDF2-SHA256 с солью, сверено с `hashlib`);
- сужение `T?` после проверки на `none` (как в Kotlin и TypeScript) — вместо
  `(min ?? 0)` пишется просто `min`;
- значения параметров по умолчанию — в функциях и в строке запроса
  (`page: int = 1`);
- `Product { ...old, ...patch }`: необязательные поля `patch` заменяют поле, только
  если пришли, — PATCH в одну строку; необязательные поля по умолчанию `none`;
- `s.matches(regex)` — автомат Томпсона: время линейно, шаблон не может «подвесить»
  сервер; сырые строки в обратных кавычках и `{3,32}` в строке — текст;
- срезы прижимаются к границам, `sort` и `reverse` возвращают список;
- сервер закрывает соединение после ошибки мягко (ответ не теряется из-за RST).

Затем язык заморозили и написали три отложенные задачи. Результат — в
[eval/README.md](../eval/README.md): там, где язык «не видел» задачу, он был
вровень с C# и хуже Python (не было разбора дат: 1046 токенов против 711). После
`parse_time`/`parse_date` — лучше всех, но это снова доработка под увиденное.
Все решения написал тот же ИИ, что и язык; независимая проверка — v1.0.

Затем — нагрузочный замер тех же решений ([eval/perf.sh](../eval/perf.sh)):
реалистичные смеси запросов, сервер на 2 ядрах, `wrk` на двух других; скорость,
p50/p99, процессор на запрос, память в покое, с данными и после нагрузки, запуск,
размер, время сборки, инварианты под нагрузкой. Найдено и исправлено:

- вход с паролем: блокировка `store` держалась во время PBKDF2 — все входы шли по
  одному (5 в секунду, все по тайм-ауту). Теперь хеш считается без блокировки, как
  `fetch` ждёт сеть;
- SHA-256 на инструкциях SHA-NI (машинный код, как SIMD в v0.6), PBKDF2 без
  выделений памяти в цикле: 100 тыс. итераций — 16 мс против 26 мс у OpenSSL;
- печать дробных чисел: быстрый путь для обычных дробей, 15 мкс → 0,25 мкс,
  сверено с Python на 200 тыс. случайных чисел;
- `lower`, `upper`, поиск подстроки и сравнение строк — по 8 байт за шаг;
- разделяемая блокировка `store`: компилятор консервативно находит маршруты,
  которые только читают (`khc check --locks`), такие запросы идут параллельно;
  блокировка «много читателей или один писатель» на futex, с приоритетом писателя.

Итог по 10 сценариям — среднее геометрическое: Khrip 35 тыс. запросов в секунду,
C# 23 тыс., Go 18 тыс., Python 2 тыс.; p99 9 мс против 21–23 мс; 48 мкс процессора на
запрос против 77–98. C# быстрее на поиске по каталогу (в 2,3 раза) и расписании
переговорных (в 1,3 раза) — это качество генератора кода (v0.11). Главная
найденная проблема не исправлена: старые значения в `store` не освобождаются,
при постоянных обновлениях память растёт на ~96 байт на обновление (v0.10).

## v0.10. Сопрограммы ✅

До v0.10 запрос, который ждал внешний сервис, держал свой поток: на одном потоке
шлюз к сервису с задержкой 100 мс делал 10 запросов в секунду, а запрос сервера
к самому себе ждал бы себя вечно. Теперь каждый запрос выполняется в сопрограмме,
как горутина в Go: `fetch`, `sleep` и хеширование пароля остаются обычными
вызовами, без `async`/`await` и «окрашенных» функций, а поток, пока запрос ждёт,
выполняет другие. Синтаксис языка не изменился, кроме новой функции `sleep(ms)`.

Устройство (`lib/rt.kh`, `lib/http.kh`):

- **Один стек запросов на поток.** Сопрограммы выполняются на нём по очереди; кадры
  остановленной копируются в кучу, только когда на стеке нужно выполнить другую, и
  возвращаются на те же адреса перед продолжением (как greenlet в Python), поэтому
  указатели внутрь стека остаются верными. Ждущий запрос занимает столько памяти,
  какова глубина его стека (обычно 2–4 КБ), каждому запросу доступны все 8 МБ
  стека, а запросы, которые не ждут, ничего не копируют.
- **Переключение** — `__setjmp`/`__longjmp` и часть контекста потока: выделитель
  памяти, арена, блокировка `store`, состояние запроса — своя у каждой сопрограммы.
  Новая встроенная `__co_call` переводит выполнение на стек запросов.
- **Арена у каждой сопрограммы** (1 ГБ адресов, страницы — по мере касания), пул
  сопрограмм на поток; лишние свободные отдают память системе.
- **Ожидание** — `epoll` с `EPOLLONESHOT` и двоичная куча сроков; блокировка
  `store` на время ожидания отпускается. Вне сервера (тесты, `every`) ожидание —
  обычный `poll` своего потока.
- **Соединение, чей запрос ждёт,** не читается и не сдвигается (строки запроса
  указывают в его буфер); ответы конвейера уходят по порядку; клиент, ушедший во
  время ожидания, закрывается, когда запрос закончится. Больше `KHRIP_COROUTINES`
  (4096) ждущих запросов на поток — остальные ждут в очереди.
- **`fetch` неблокирующий** целиком: connect, запись, чтение, DNS по UDP, `curl`
  для https (каналы и конец процесса через `pidfd`); общий срок — 30 с. PBKDF2
  каждые 1024 итерации уступает поток другим запросам.
- **Соединения `fetch` переиспользуются** (keep-alive): у потока запас свободных
  соединений по адресам; конец ответа определяется по `Content-Length` или по
  частям, не по закрытию. Соединение из запаса перед отправкой проверяется
  (`MSG_PEEK`); если сервис его всё же закрыл, запрос без побочных эффектов (GET,
  PUT, DELETE) повторяется по новому, как в Go.

Найдено по дороге:

- буферы ответа потока росли через постоянную память `store` под блокировкой — у
  читающих маршрутов с разделяемой блокировкой это была гонка (и утечка). Теперь
  они растут через `mmap`, а запись в `store` под разделяемой блокировкой — паника
  вместо тихой порчи данных;
- на процессоре без SHA-NI (Xeon до Ice Lake) SHA-256 шёл через обычный код
  Khrip: `hash_password` — 560 мс, вход с паролем упирался в тайм-ауты. Теперь и
  этот путь — машинный код компилятора (32-битные регистры, раунды по 8 со
  сдвигом ролей регистров): 81 мс против 70 мс у Go и 114 мс у OpenSSL на той же
  машине.

Замер — шлюз на одном потоке, 200 одновременных клиентов, сервис отвечает через
100 мс: было 9,7 запроса в секунду (p50 834 мс), стало 1 870 (p50 105 мс; предел —
2 000). 1000 одновременных `sleep(100)` на одном потоке — 9 433 запроса в секунду,
память всего процесса — 17 МБ.

## v0.11. Свой TLS 1.3 ✅

`fetch` по https раньше запускал `curl` на каждый запрос: 106 запросов в секунду
на шлюзе, процесс на запрос, зависимость от программы в системе. Теперь клиент
TLS 1.3 — в библиотеке Khrip, без OpenSSL и сторонних библиотек
([отчёт](../bench/results/2026-10-21-v0.11-tls.md)):

- **Протокол** (`lib/tls.kh`, RFC 8446): обмен ключами X25519, а если сервер
  попросит (HelloRetryRequest) — P-256; шифры AES-128-GCM, AES-256-GCM,
  ChaCha20-Poly1305 (с AES-NI предпочитается AES); подписи сервера ECDSA
  P-256/P-384 и RSA-PSS; KeyUpdate, билеты сессий пропускаются, режим
  совместимости с промежуточными устройствами. Состояние соединения — в блоке
  `mmap`, а не в арене: соединение возвращается в запас keep-alive вместе с
  ключами, запас различает серверы по имени.
- **Сертификаты** (`lib/x509.kh`): разбор DER, корни системы (Debian, Alpine,
  RHEL, SUSE) или `SSL_CERT_FILE`, читаются один раз на процесс; цепочка — от
  сертификата сервера к корню, на каждом шаге сначала корень (так переживаются
  перекрёстные подписи); сроки, basicConstraints, keyUsage, extKeyUsage,
  nameConstraints, неизвестные критические расширения; имя — только из
  subjectAltName, шаблоны «*.» на одну метку, адреса IP. Проверенные цепочки
  помнятся у потока до часа: повторное рукопожатие с тем же сервером проверяет
  только подпись CertificateVerify.
- **Криптография** (`lib/crypto.kh`, `lib/cipher.kh`, `lib/pk.kh`): SHA-384/512,
  HMAC, HKDF; AES-GCM на AES-NI и PCLMULQDQ, ChaCha20 на SSE2, Poly1305;
  RSA PKCS#1 v1.5 и PSS; ECDSA и ECDH на P-256/P-384; X25519. Длинная арифметика
  — части по 64 бита, умножение Монтгомери, сложение и вычитание по модулю —
  машинный код компилятора без ветвлений; блоки SHA-256 и SHA-512 без SHA-NI —
  тоже машинный код.
- **Прокси**: https через `HTTPS_PROXY` — туннелем CONNECT (с логином из адреса
  прокси), `NO_PROXY` соблюдается.

Проверка: 300 случайных наборов против Python `cryptography` (AEAD, RSA, ECDSA,
ECDH, X25519) на каждом прогоне тестов, фиксированные значения от Python в
`tests/run/crypto.kh`, 13 случаев проверки цепочек (шаблоны, IP, просроченный,
сертификат для клиентов, nameConstraints, чужой корень с тем же именем),
рукопожатия с OpenSSL по всем трём шифрам, с ключом RSA, с HelloRetryRequest,
отказы, KeyUpdate от сервера, keep-alive, ответ 2 МБ и тело 300 КБ; вручную —
настоящие сайты через прокси песочницы.

Что нашлось по дороге: первая версия проверяла подпись ECDSA P-384 за 7,6 мс —
время уходило на обвязку вокруг каждой операции поля и на временные числа в
арене. После переноса сложения и вычитания по модулю в машинный код, окон по 4
бита и постоянных временных — 1,2 мс; P-256 — 0,48 мс вместо 1,65.

Чего нет: TLS 1.2, сертификата клиента, возобновления сессий, ключей P-521 и
Ed25519 в сертификатах, проверки отзыва; TLS на стороне сервера — за обратным
прокси. Программа с `fetch` весит около 300 КБ (TLS внутри; у Go — 8 МБ).

## v0.12. PostgreSQL ✅

Свой клиент PostgreSQL в библиотеке Khrip и запросы как часть языка: SQL
пишется как есть, значения — `{x}`, тип результата берётся из ожидаемого типа,
а ошибки ловит компилятор, а не первый запрос в продакшене
([отчёт](../bench/results/2026-10-22-v0.12-postgres.md)):

- **Протокол** (`lib/pg.kh`, без libpq): SCRAM-SHA-256, MD5 и открытый пароль
  (открытый — только по TLS или на 127.x); TLS — свой TLS 1.3 с режимами
  `sslmode` как у libpq (`prefer` откатывается на открытое соединение,
  `verify-full`, `sslrootcert=system`); расширенный протокол: Parse/Bind/Execute
  одним пакетом, подготовленный оператор на каждое место `sql` в соединении,
  BEGIN — тем же пакетом, что первый запрос. Строки читаются без копирования.
  Пул на процесс (`DATABASE_POOL`, по умолчанию 4 на поток, не больше 32),
  ожидание соединения — в сопрограмме, очередь по порядку. Тайм-аут запроса
  (`DATABASE_TIMEOUT`) — с CancelRequest; keepalive и TCP_USER_TIMEOUT; простоявшее
  5 минут соединение закрывается.
- **Язык**: `sql "..."` и `` sql `...` ``; `{expr}` уходит параметром, пути от
  строки времени выполнения к тексту SQL нет. `T` — одна строка (нет — 404, и
  маршрут обязан перечислить 404), `T?` — одна или ни одной, `[T]` — все, без
  типа — число изменённых строк. Переписывания: `{x} IS NULL`, `IN ({list})`,
  `INSERT INTO t {v}` и `{[v]}` (поля → столбцы, `none` → DEFAULT, список —
  через `unnest`), `SET {patch}` (только присланные поля), `'%{q}%'` с
  экранированием LIKE, `ORDER BY {o}` из строковых литералов (по оператору на
  вариант).
- **Проверки при компиляции**: привычки других драйверов и диалектов (`$1`, `?`,
  `:name`, `BEGIN`, `= NULL`, `LIMIT a, b`...), DDL вне миграций, UPDATE/DELETE
  без WHERE, LIMIT без ORDER BY, сравнение необязательного значения без
  `IS NULL`, запись после чтения вне `tx` (гонка «проверил — записал»), 404,
  которого нет в маршруте; анализатор миграций знает таблицы, столбцы, типы и
  NULL (с внешними соединениями) и проверяет каждый запрос без базы. При запуске
  сервер готовит каждый запрос на настоящей базе, сверяет типы столбцов и
  параметров с типами Khrip и NOT NULL — и не запускается, если что-то не
  сходится.
- **Транзакции**: `tx { }` — SERIALIZABLE с повтором при конфликте; внутри
  компилятор запрещает то, что нельзя повторить (`fetch`, `sleep`, `call`,
  изменения `store` и внешних переменных, в том числе через вызванные функции и
  методы). Статус от 400, `fail` и паника откатывают. `let t = tx { ...; v }`.
  Потеря связи во время COMMIT — 500 «outcome unknown», а не тихий повтор.
- **Миграции**: `migration N` в коде, по номерам, под advisory-блокировкой (две
  копии сервера не применят дважды), контрольные суммы (изменённую — не
  запустит), `lock_timeout` с повторами, `CREATE INDEX CONCURRENTLY` вне
  транзакции; `DATABASE_MIGRATE=check` и `./app migrate` — для выкладки отдельным
  шагом.
- **Ошибки базы → HTTP**: дубликат и CHECK — 409, нет ссылки — 404, на строку
  ещё ссылаются — 409, NOT NULL и плохое значение — 400, база недоступна,
  перегружена или тайм-аут — 503 с `Retry-After`; тексты ответов без значений из
  базы, 500 пишет в журнал запрос.
- **Тесты**: `khc test` работает во временной схеме и удаляет её
  (`KHRIP_TEST_DATABASE_URL`); `tests/pg.sh` поднимает свой PostgreSQL с SCRAM,
  MD5, паролем и TLS.

Три новые задачи eval на базе — ledger (переводы с ключом идемпотентности),
shop (заказы со складом), tracker (нумерация задач без пропусков) — решены на
четырёх языках и проходят проверки с двумя копиями сервера на одной базе и
перезапуском.

Под нагрузкой ([eval/results/perf_db.md](../eval/results/perf_db.md), медиана трёх
прогонов; сервер на 2 ядрах, PostgreSQL на той же машине):

| | Khrip | Go | C# | Python |
|---|---:|---:|---:|---:|
| ledger: запросов в секунду | **3 767** | 2 762 | 2 055 | 1 202 |
| shop | **3 107** | 2 474 | 2 117 | 1 199 |
| tracker | **4 519** | 3 537 | 2 856 | 1 437 |
| мкс процессора сервера на запрос | **140** | 289 | 467 | 769 |
| мкс процессора PostgreSQL на запрос | 612 | **528** | 890 | 698 |
| p99, мс | 46,9 | **40,6** | 139 | 100 |
| память с данными, МБ | **0,8** | 14 | 95 | 48 |
| токены трёх решений, o200k | **4 295** | 9 922 | 7 428 | 5 819 |

База тратит на запрос Khrip больше, чем на запрос Go: SERIALIZABLE вместо
`FOR UPDATE` даёт около 15% повторов в ledger, а в сводках Khrip за то же время
успевает создать больше данных. p99 в shop и tracker хуже, чем у Go (60 мс
против 47, 36 против 30). Справочник языка вырос с 3 025 до 3 945 токенов.

Что нашлось по дороге:

- На маленькой таблице планировщик выбирает последовательный просмотр даже для
  `WHERE id = $1`, а в SERIALIZABLE он ставит предикатную блокировку на всю
  таблицу: ledger то держал 4 тыс. запросов в секунду, то падал до 1,1 тыс. с
  цепочками по сотне повторов. Блоки `tx` выключают последовательный просмотр
  (`set_config` тем же пакетом, что BEGIN).
- Очередь повторов сначала была одна на блок `tx`: под нагрузкой она выстраивала
  в ряд все переводы, даже между разными счетами. Теперь компилятор выписывает
  для каждого запроса «таблица.столбец» из `WHERE col = {x}`, и повтор ждёт
  только на строках своей попытки; первая попытка, которая касается строки в
  очереди, встаёт за ней, а не идёт на верный конфликт.
- Независимая проверка очереди нашла: транзакция больше набора ключей (тогда
  11) могла уступать без конца; выключенный последовательный просмотр включал
  JIT; план места `sql`, построенный вне `tx`, доставался транзакции. Исправлено,
  а проверки привычек других диалектов перестали путать столбцы `money`, `top`
  или `unsigned` с типами.
- Огромный результат (3 млн строк) переполнял арену и ронял сервер: теперь у
  арены есть резерв, такой запрос получает 500, сервер работает дальше.
- `NaN == NaN` было истиной: сравнение дробных чисел исправлено по IEEE 754.

Чего нет: `LISTEN/NOTIFY`, `COPY`, курсоров для потоковой выдачи больших
результатов, реплик для чтения, сертификата клиента в TLS; `schema.sql` с текущей
схемой не пишется — схема видна только из миграций.

## v0.13. Память и строки

Сборка мусора в `store`: значения `store` живут в постоянной области, и сейчас она
только растёт — заменённая структура, строка или список остаются навсегда (в
замере v0.9 — 168 МБ за 13 с обновлений). План — уплотняющая сборка: под
исключительной блокировкой, когда ни один запрос не держит ссылок на `store`, живые
значения копируются от корней по описаниям типов (они уже есть для JSON) в новую
область, общие ссылки сохраняются через таблицу переадресации, старая область
возвращается системе.

Строки UTF-8: `len`, срезы, `lower`/`upper` и поиск на кириллице и других
алфавитах дают правильный результат; JSON проверяет кодировку.

## v0.15. Оптимизации генератора кода

По очереди, с замером после каждой:

1. Слияние соседних операций: например, загрузка переменной и арифметика с константой.
2. Локальные переменные в регистрах с сохранением при рекурсии и вложенных вызовах.
3. Верхние значения стека вычислений в регистрах R8–R11; при нехватке регистров старое
   значение уходит в память, на границах ветвлений и вызовов кэш выгружается в стек.

## v0.16. Слепая проверка и заморозка языка

`KHRIP.md` — спецификация для промпта ~3000 токенов. `khc check --json` — есть с
v0.3. Набор задач с проверками и протокол — есть с v0.9
([eval/](../eval/README.md)). Осталось главное: задачи решают модели разных
поставщиков, не участвовавшие в разработке, на Khrip, Go, C# и Python. Метрика —
доля решённых задач и токены на решённую задачу, включая спецификацию и попытки
исправления ([CRITERIA.md](CRITERIA.md)). Если Khrip не выигрывает, язык меняется

## v1.0. Обещание совместимости

Программа, написанная на 1.0, собирается и работает на всех 1.x. Перед этим —
период без ломающих изменений, фаззинг разборщиков HTTP, JSON и регулярных
выражений, сутки под нагрузкой без роста памяти и дескрипторов.
