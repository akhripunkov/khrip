# Дорожная карта Khrip

Сначала рабочий минимум, затем скорость. Компилятор с самого начала написан на Khrip
и собирает сам себя. Каждый шаг заканчивается тестами и замером в `bench/` против Go
и C#. Выигрыш объявляем только по результатам замеров.

| **v0.1** ✅ | Самокомпилирующийся компилятор: зерно на ассемблере + `khc` на Khrip | `khc` собирает сам себя, поколения побайтно совпадают; 21 тест |

## v0.1. Самокомпилирующийся компилятор ✅

Компилятор `khc` сразу написан на Khrip (`src/khc.kh`, подмножество
[Khrip-0](KHRIP0.md)). Первый раз его собирает зерно `bootstrap/khc0.asm` на
ассемблере x86-64; ни Go, ни C, ни других компиляторов в цепочке нет. Компилятор сам
генерирует машинный код и записывает статический ELF без libc.

Проверка (`build.sh`): зерно собирает `khc1`, тот собирает себя (`khc2`), тот снова
себя (`khc3`); `khc2` и `khc3` совпадают побайтно. Тесты: `tests/run.sh`.

## v0.2. Первый HTTP-сервер на Khrip ✅

Однопоточный сервер на `epoll` (`lib/http.kh`): неблокирующие сокеты, keep-alive,
конвейерные запросы, тело по `Content-Length`, заголовок `Date`, ошибки протокола
(400, 413, 431, 501). Библиотеки `lib/net.kh` и `lib/json.kh`. Приложение пока
определяет `fn handle(req)` — временный интерфейс до объявлений `route`.

Результат ([отчёт](../bench/results/2026-10-19-v0.2.md)): один поток Khrip —
~114–118 тыс. запросов в секунду, как C# на двух ядрах и в 1,5 раза больше Go;
1,1 МБ памяти, 25 КБ бинарник, старт 10 мс. Проигрываем по p99 (C# лучше) и по
вычислениям (в 1,65–1,7 раза медленнее Go). Добавлены замеры вычислений
(`bench/compute`) и токенов (`bench/tokens`).

## v0.3. Строгие типы: Khrip-1 ✅

Компилятор переписан на Khrip-1 (`src/*.kh`, ~6 тыс. строк) и собирает сам себя.
Цепочка раскрутки: зерно `bootstrap/khc0.asm` → `bootstrap/boot.kh` (на Khrip-0,
понимает подмножество Khrip-1) → `khc1` → `khc2` → `khc3`; `khc2` и `khc3` совпадают.

- Типы `int`, `bool`, `str`, `[T]`, `map[K, V]`, `T?`, структуры `type` с `...`;
  `??`, `let x = v else { ... }`, `if let`, интерполяция `"{x}"`, `for x in xs`,
  `for i, x in xs`, `for i in a..b`, вызов функции как метода. Условие — только
  `bool`, неявно только `T` → `T?`.
- Все ошибки сразу: файл:строка:столбец, строка исходника с указателем, подсказка
  («может быть, вы имели в виду», `null`, `elif`, `String`, `++` ...); `--json`.
- Проверки границ, переполнения и деления на ноль — паника с местом и кодом 101.
- Генератор кода: однопроходный, с распределением регистров по весу циклов
  (значения живут в rbx, r12–r15 между итерациями), встраиванием маленьких функций,
  слиянием сравнения с переходом, непосредственными операндами, компактным прологом.

Вычисления (`bench/compute`): sieve — на уровне Go и C# AOT; fib — в 1,4 раза
медленнее Go (стоимость вызова).

## v0.4. API-слой языка ✅

- `route МЕТОД "путь" (параметры) -> варианты { ... }`: параметр из пути —
  `{id}`, структура/список — тело JSON, остальное — строка запроса (`T?` — не
  обязателен). Ответ — `return 201 user`, `return 404`, `return users[id] ?? 404`;
  `str` уходит текстом, остальное — JSON. Неверные параметры и тело — 400
  с понятным текстом; путь есть, метода нет — 405.
- Маршрутизатор и разбор параметров компилятор генерирует исходным текстом на
  Khrip; JSON в обе стороны работает по описаниям типов, которые компилятор кладёт
  в данные программы.
- `store` — данные, переживающие запрос. Каждый запрос выполняется в своей арене,
  которая обнуляется после ответа; запись внутрь объектов store копирует значение
  в постоянную память (барьер записи по адресу), рост списков и словарей store идёт
  там же. Обращения к store одного запроса — под одной блокировкой.
- Паника в обработчике — ответ 500, сервер работает дальше.
- `test "имя" { ... }`, `call POST "/users" body`, `expect a == b` (при провале —
  обе стороны); `khc test`, `khc run` — сборка в память и запуск без файлов.
- Неиспользуемые функции библиотеки не попадают в программу: hello — 5,8 КБ,
  HTTP-сервер — 44 КБ.

Один поток: plaintext 126 тыс. запросов/с, json 116 тыс., p99 2,3–3,1 мс — лучше v0.2.

## v0.5. Многоядерность и арены ✅

Рабочий поток на каждое доступное ядро (`THREADS` меняет число): у каждого свой
`epoll`, свой слушающий сокет `SO_REUSEPORT`, свои соединения, своя арена запроса;
поток привязан к своему ядру. Потоки создаёт встроенная `__spawn` (clone без libc),
блокировка store — мьютекс на futex. Арена запроса — с v0.4.

Замер ([отчёт](../bench/results/2026-10-19-v0.5.md)), сервер на 2 ядрах:

|---|---:|---:|---:|---:|---:|---:|---:|
| Khrip v0.5 | **250 502** | 8,55* | **245 216** | **3,70** | **2,1** | **0,05** | **14** |
| Go 1.24 | 77 798 | 6,39 | 69 881 | 13,81 | 14,8 | 8,08 | 31 |

## v0.6. SIMD ✅

Три примитива рантайма — поиск байта, поиск конца заголовков `\r\n\r\n` и поиск
символов, которые экранирует JSON, — встроенные функции компилятора: он сам пишет их
машинный код в трёх вариантах (AVX2 по 32 байта, SSE2 по 16, побайтно). Вариант
выбирается при старте по `cpuid` и `xgetbv` (AVX2 нужен и процессору, и ОС);
`KHRIP_SIMD=0|1` понижает уровень. На них построены разбор запроса в `lib/http.kh`
и запись и чтение строк JSON в `lib/api.kh`. Корректность: тест `tests/run/simd.kh`
сверяет все три пути с простым циклом на 434 тыс. случаев.

Замер ([отчёт](../bench/results/2026-10-19-v0.6-simd.md)), одно ядро:

| | Заголовки браузера (700 Б) | Запись JSON (3,6 КБ) | Чтение JSON |
|---|---:|---:|---:|
| побайтно | 816 нс | 2754 нс | 3391 нс |
| SSE2 | 179 нс | 550 нс | 1065 нс |
| AVX2 | **134 нс** (×6,1) | **465 нс** (×5,9) | **973 нс** (×3,5) |

На всём сервере с такими заголовками выигрыш меньше — +2% plaintext, +11% json:
основное время запроса уходит на системные вызовы.

## v0.7. Язык по опыту ✅

Написав на Khrip 10 тысяч строк (компилятор, рантайм, HTTP, JSON, тесты), я
выписал, где язык заставлял писать «как на Си» и где я ошибался, и закрыл это:

- **Варианты и исчерпывающий `match`.** `type Role = Admin | Member`,
  `type Shape = Circle { r: int } | Rect { w: int, h: int } | Empty`; `match` по
  вариантам, int, str и bool, несколько образцов через `|`, `_`. Пропущенный
  вариант — ошибка с перечнем недостающих. Перечисления в JSON — строки, остальные
  варианты — объекты с полем `"type"`; перечисления работают и в параметрах маршрутов.
  Метка варианта лежит перед полями структуры, поэтому вариант — тот же указатель,
  без упаковки.
- **Лямбды в методах списков:** `map filter find any all count sort_by`.
  Цикл и тело лямбды компилируются на месте вызова: лямбда видит локальные
  переменные, ничего не выделяет и ничего не стоит.
- **`if` и `match` — значения**, блок со значением в последней строке.
- **Значения полей по умолчанию** — и в литералах, и при разборе JSON.
- **Громкая интерполяция:** каждая `{` в строке — подстановка любого выражения,
  буквальная скобка — `\{`; пустая и незакрытая `{` — ошибка с исправлением.
  Раньше `"{(x)}"` молча оставалось текстом.
- `x == value` для `x: T?`, подсказки на `switch`, `enum`, `?:`, `and`/`or`.

Замер на новой задаче — TODO API с перечислением статусов, фильтрами, сортировкой
и статистикой; все четыре версии проходят один сценарий из 15 проверок
(`bench/tokens/samples/todo/check.sh`):

| | Khrip v0.7 | Khrip v0.6 | C# | Python FastAPI | Go |
|---|---:|---:|---:|---:|---:|
| o200k | **349** | 563 | 410 | 412 | 974 |
| Claude (публичный) | **367** | 575 | 501 | 459 | 1272 |

Честный вывод: на этой задаче Khrip v0.6 проиграл бы C# и Python. Выигрыш
на CRUD объяснялся тем, что задача хорошо ложилась на `route` и `store`; как только
появляются фильтры и перечисления, без лямбд и вариантов код растёт на 60%.

## v0.8. Связь с внешним миром ✅

Вопрос «можно ли уже написать бэкенд, который уведомляет о погоде» показал три
пробела: не было дробных чисел, исходящих запросов и фоновых задач. Закрыты так,
чтобы каждое решение окупалось по соотношению пользы и затрат:

- **`float`** — 64-битные числа, арифметика — скалярный SSE2. Целый *литерал*
  рядом с float сам становится float (`t * 2`, `t < 0`), как в Go; целую
  переменную нужно перевести явно — типы остаются строгими. Перевод десятичной
  записи в двоичную и обратно — точный, на длинных целых; печать — самая короткая
  обратимая запись, как в JavaScript (`0.1 + 0.2` → `0.30000000000000004`).
- **`fetch МЕТОД url [тело] [headers карта]`** → `Response`; если сервис не
  ответил — `status 0` и причина в `body`, поэтому одна проверка статуса закрывает
  оба случая. http — свой клиент (DNS, `/etc/hosts`, `HTTP_PROXY`, chunked);
  https — пока через `curl`: свой TLS — это тысячи строк криптографии, где ошибка
  означает уязвимость, поэтому он вынесен в отдельный шаг. Пока `fetch` ждёт сеть,
  блокировка `store` отпущена: медленный внешний сервис не останавливает остальные
  запросы.
- **`every 10 min { ... }`** — объявление, как `route`; задачи идут в отдельном
  потоке со своей ареной и не тормозят HTTP. Паника в задаче пишется в лог.
- **`KHRIP_DATA=файл`** — `store` загружается при старте и сохраняется раз в
  секунду после изменений и при SIGTERM/SIGINT (снимок через временный файл).
- `now()`, `now_ms()`, `url_encode`, `s.to_float()`.

Проверка — [examples/weather/weather.kh](../examples/weather/weather.kh): погода
по городу (Open-Meteo, без ключа), подписки с порогами, проверка каждые 10 минут,
уведомление на вебхук (подходит и Telegram). Сквозной тест `tests/weather.sh`
поднимает поддельный Open-Meteo и приёмник вебхуков — оба тоже на Khrip — и
проверяет погоду, уведомление при похолодании, отсутствие повторов, повтор после
возврата к норме и сохранение подписок через перезапуск по SIGTERM.

## v0.9. Проверка на типичных задачах ✅

Вопрос «почему ты решил, что этот подход лучше Go и C#» требовал не довода, а
замера. Сделан набор [eval/](../eval/README.md): восемь задач бэкенда с условием
без упоминания языка и общими проверками через `curl` (коды, тела, заголовки,
одновременные запросы); каждая решена на Khrip, Python FastAPI, C# и Go.

Пять задач — настроечные: на них искали, чего не хватает. Пробелы и решения:

- заголовки: `header(name)`, `set_header(name, value)`, `headers` у `call`, ответ
  `fetch` с заголовками;
- `fail(status[, message])` — прервать запрос из любой функции (как
  `HTTPException` в FastAPI): проверка ключа или токена — одна функция, а не
  по три строки в каждом маршруте;
- `random_str(n)`, `time_iso(t)`, `sha256`, `hash_password`/`check_password`
  (PBKDF2-SHA256 с солью, сверено с `hashlib`);
- сужение `T?` после проверки на `none` (как в Kotlin и TypeScript) — вместо
  `(min ?? 0)` пишется просто `min`;
- значения параметров по умолчанию — в функциях и в строке запроса
  (`page: int = 1`);
- `Product { ...old, ...patch }`: необязательные поля `patch` заменяют поле, только
  если пришли, — PATCH в одну строку; необязательные поля по умолчанию `none`;
- `s.matches(regex)` — автомат Томпсона: время линейно, шаблон не может «подвесить»
  сервер; сырые строки в обратных кавычках и `{3,32}` в строке — текст;
- срезы прижимаются к границам, `sort` и `reverse` возвращают список;
- сервер закрывает соединение после ошибки мягко (ответ не теряется из-за RST).

Затем язык заморозили и написали три отложенные задачи. Результат — в
[eval/README.md](../eval/README.md): там, где язык «не видел» задачу, он был
вровень с C# и хуже Python (не было разбора дат: 1046 токенов против 711). После
`parse_time`/`parse_date` — лучше всех, но это снова доработка под увиденное.
Все решения написал тот же ИИ, что и язык; независимая проверка — v1.0.

Затем — нагрузочный замер тех же решений ([eval/perf.sh](../eval/perf.sh)):
реалистичные смеси запросов, сервер на 2 ядрах, `wrk` на двух других; скорость,
p50/p99, процессор на запрос, память в покое, с данными и после нагрузки, запуск,
размер, время сборки, инварианты под нагрузкой. Найдено и исправлено:

- вход с паролем: блокировка `store` держалась во время PBKDF2 — все входы шли по
  одному (5 в секунду, все по тайм-ауту). Теперь хеш считается без блокировки, как
  `fetch` ждёт сеть;
- SHA-256 на инструкциях SHA-NI (машинный код, как SIMD в v0.6), PBKDF2 без
  выделений памяти в цикле: 100 тыс. итераций — 16 мс против 26 мс у OpenSSL;
- печать дробных чисел: быстрый путь для обычных дробей, 15 мкс → 0,25 мкс,
  сверено с Python на 200 тыс. случайных чисел;
- `lower`, `upper`, поиск подстроки и сравнение строк — по 8 байт за шаг;
- разделяемая блокировка `store`: компилятор консервативно находит маршруты,
  которые только читают (`khc check --locks`), такие запросы идут параллельно;
  блокировка «много читателей или один писатель» на futex, с приоритетом писателя.

Итог по 10 сценариям — среднее геометрическое: Khrip 35 тыс. запросов в секунду,
C# 23 тыс., Go 18 тыс., Python 2 тыс.; p99 9 мс против 21–23 мс; 48 мкс процессора на
запрос против 77–98. C# быстрее на поиске по каталогу (в 2,3 раза) и расписании
переговорных (в 1,3 раза) — это качество генератора кода (v0.11). Главная
найденная проблема не исправлена: старые значения в `store` не освобождаются,
при постоянных обновлениях память растёт на ~96 байт на обновление (v0.10).

## v0.10. Сборка мусора в store

Значения `store` живут в постоянной области, и сейчас она только растёт: заменённая
структура, строка или список остаются в памяти навсегда. План — уплотняющая
сборка: под исключительной блокировкой `store`, когда ни один запрос не ждёт
`fetch` с отпущенной блокировкой, живые значения копируются от корней (`store`)
по описаниям типов (они уже есть для JSON) в новую область, общие ссылки
сохраняются через таблицу переадресации, старая область возвращается системе.
Запуск — когда область выросла вдвое с прошлой сборки.

## v0.11. Оптимизации генератора кода

По очереди, с замером после каждой:

1. Слияние соседних операций: например, загрузка переменной и арифметика с константой.
2. Локальные переменные в регистрах с сохранением при рекурсии и вложенных вызовах.
3. Верхние значения стека вычислений в регистрах R8–R11; при нехватке регистров старое
   значение уходит в память, на границах ветвлений и вызовов кэш выгружается в стек.

## v0.12. Свой TLS 1.3

Клиент TLS 1.3 без сторонних библиотек: X25519, ChaCha20-Poly1305 и AES-GCM,
SHA-256/384, проверка цепочки сертификатов (RSA, ECDSA P-256/P-384) по системному
хранилищу корневых сертификатов. После этого `fetch` по https не нужен `curl`,
а бинарник остаётся самодостаточным.

## v1.0. Инструменты для нейросетей

`KHRIP.md` — спецификация для промпта до ~3000 токенов (есть: ~2900). `khc check
--json` — есть с v0.3. Набор задач с проверками и протокол — есть с v0.9
([eval/](../eval/README.md)). Осталось главное: задачи решают модели разных
поставщиков, не участвовавшие в разработке, на Khrip, Go, C# и Python. Метрика —
доля решённых задач и токены на решённую задачу, включая спецификацию и попытки
исправления ([CRITERIA.md](CRITERIA.md)). `khc fmt`.
