# Khrip v0.14: design for protocols — production server, streams and SSE, WebSocket and topics, TLS server and HTTP/2, gRPC

This design covers the five protocol stages the owner approved, in the approved order:

1. **v0.14 production server**: streaming responses and Server-Sent Events, chunked and large request bodies, limits and timeouts, graceful shutdown, request logs, metrics and trace ids, deadlines for `fetch`.
2. **WebSocket** with typed messages, and **topics**: broadcast across connections and worker threads, with bounded queues for slow clients.
3. **Server-side TLS** (certificates, constant-time ECDSA P-256 and RSA-PSS signing, ALPN, optional mTLS) and **HTTP/2** server and client (HPACK, flow control, h2c prior knowledge behind proxies, ALPN h2, multiplexed `fetch`).
4. **gRPC** on HTTP/2: services declared from Khrip types, protobuf derived from types with stable field numbers, unary and streaming RPCs, deadlines, status codes, `.proto` written by khc and imported into Khrip types, plus Connect and gRPC-Web for browsers.
5. **HTTP/3** left to the edge, with the reasons and the triggers that would change the decision.

Every decision is checked against the owner's two rules:
- **Rule 1 (efficiency):** a Khrip program must beat the same program in Go, C#/.NET, Java, Node and Python on throughput, latency, memory, CPU and startup; Rust is reported where relevant.
- **Rule 2 (tokens):** an AI writes the same backend in fewer tokens than in any other language, with fewer places to make silent mistakes.

**What was checked, not only argued:**
- **Four evidence programs** were written in this design's syntax, and the same programs in Go, C# and Python (§14). Every competitor program compiles: Go 1.24 with gorilla/websocket, grpc-go and pgx (P4's grpc-gateway v2.26 needs Go 1.26, which `go` fetched); C# on .NET 10 with Grpc.AspNetCore, Npgsql and JSON transcoding. ## 0. Decisions

Each decision lists the rule it serves: **R1** is efficiency, **R2** is tokens and silent mistakes.

### Production server (stage 1)

1. **One server core for every protocol.**
   - Connection state machines (HTTP/1.1, WebSocket, HTTP/2, TLS) run in each worker thread's event loop.
   - Handlers run in coroutines, as today.
   - Per-thread buffer pools replace the per-connection 64 KB input and 128 KB output mmaps.

   *R1:* an idle keep-alive connection drops from 9.7 KB to ≤ 1 KB, and one code path serves every protocol. *R2:* no surface.
2. **Bodies up to `KHRIP_MAX_BODY` (4 MiB)** are read by the request's own coroutine into its arena.
   - Chunked bodies are accepted.
   - Framing is strict: request-smuggling shapes are rejected.

   *R1:* JSON is still parsed in place. *R2:* the 64 KB limit and the 501 on chunked disappear with no code.
3. **Timeouts are on by default:**
   - headers 10 s, body progress 10 s, keep-alive idle 650 s, write stall 30 s;
   - a request deadline (`KHRIP_TIMEOUT`, 30 s) that `fetch` and `sql` inherit;
   - `fetch ... timeout 5 s` for a single call.

   *R2:* slowloris and hung-upstream defenses that Go leaves to the programmer (`ReadHeaderTimeout` is zero by default).
4. **Graceful shutdown always:**
   - SIGTERM turns readiness off;
   - a lame-duck period follows (5 s when `KUBERNETES_SERVICE_HOST` is set, else 0);
   - then the server stops accepting, drains for 25 s and ends parked streams with protocol-correct goodbyes;
   - it saves `KHRIP_DATA` and exits.

   *R2:* the Go version of the same service needs about 15 more lines (§14.3).
5. **Observability with no code:**
   - W3C `traceparent` is accepted or generated, and passed on by `fetch` and gRPC;
   - `KHRIP_LOG=requests` writes JSON request logs;
   - `METRICS_PORT` serves Prometheus `/metrics`, `/healthz` and `/readyz`;
   - counters are per thread, with no atomics on the request path.

   *R1:* a gate of ≤ 3% overhead with metrics and ≤ 8% with request logs. *R2:* Go needs +518 tokens for the same (§14.3).
6. **CORS comes from `KHRIP_CORS`**, and the WebSocket origin check uses the same list. *R2:* closes cross-site WebSocket hijacking, a silent hole in most hand-written servers.

### Streams and SSE (stage 1)

7. **One type constructor, `stream T`, and one function, `send(v)`.**
   - A route `-> stream T` serves Server-Sent Events, NDJSON, a streamed JSON array, a WebSocket (GET) and gRPC/Connect/gRPC-Web server streams.
   - The client picks the format.

   *R2:* one handler, five wire formats, and no framing code.
8. **The response head waits** until the first `send`, the first read of the stream parameter, the first wait after `subscribe`, the route's return, or 20 s.
   - Until then, `return 404` and `fail` give real statuses.
   - After that, errors become protocol errors: SSE `event: error`, WebSocket close 4000+status, gRPC trailers, or a truncated chunked body.

   *R2:* no "headers already sent" bug class.
9. **A client that leaves cancels the handler** at its next `send` or wait, and an open streaming `fetch` is closed. *R2:* replaces the forgotten `r.Context()` or `CancellationToken`, which in an LLM proxy silently keeps paying for tokens.
10. **Backpressure.** `send` waits while the connection's queue is over 1 MiB. With the store lock held it does not wait, and queues up to a hard cap of 16 MiB (§4.2). *R1:* memory stays bounded. *R2:* invisible to the AI.
11. **Keep-alive pings every 20 s of silence** (an SSE comment, a WebSocket ping, an HTTP/2 PING). A dead peer is closed after two intervals.
12. **Streaming fetch: `for x in fetch ...`**
    - It yields one SSE `data` payload or one line at a time.
    - A status other than 2xx ends the route with 502.
    - There is an idle timeout instead of a total deadline.

    *R2:* an LLM proxy fits in 6 lines.
13. **`stream T` parameters.** With GET the route is a WebSocket. With POST the body is NDJSON, a JSON array, or (for `stream str`) lines. Items arrive one at a time. *R1:* uploads run in constant memory.

### Memory model for long-lived handlers (stages 1–2)

14. **Per-item memory.**
    - Each pass of a loop over a stream starts with fresh arena memory.
    - A value that outlives the pass is copied into a keep heap owned by the request, or by the connection for the message loop. Such values are the ones assigned to variables from outside the loop, or stored into containers from outside it.
    - This is the store barrier rule, generalised: "variables from outside the loop act like `store`".

    *R1:* hour-long connections do not grow. *R2:* the rule is one the AI already knows.
15. **A parked message loop holds no coroutine, no arena and no store lock.**
    - Its stack snapshot (1.3 KB measured) and context words live in the connection object.
    - A stream that only subscribed holds nothing but the connection.

    *R1:* target ≤ 2.5 KB per idle WebSocket and ≤ 1 KB per idle SSE subscriber (competitors: 6.7–72 KB).

### WebSocket and topics (stage 2)

16. **WebSocket (RFC 6455) carries text messages as JSON for `T`.**
    - The maximum message is `KHRIP_MAX_BODY`.
    - UTF-8 is validated and ping/pong is automatic.
    - There is no permessage-deflate and no subprotocol; binary frames are refused with 1003.
    - The origin is checked.

    *R1:* SIMD unmasking and zero-copy decoding. *R2:* no protocol code.
17. **`topic name: T`**, with `name[key]` channels and `subscribe`, `unsubscribe`, `publish`.
    - Delivery is at most once, in one total order per channel.
    - A subscription is forwarded by the runtime: no user code runs per delivery.

    *R1:* a value is serialized once and fanned out per thread. *R2:* no hub, connection map or mutex, and no leaks on disconnect.
18. **Topic operations are ordered with `store`**: they take the store lock in shared mode. As a result, "subscribe, then read history" and "store, then publish" are atomic. *R2:* nothing is lost or duplicated where history meets live messages.
19. **A slow consumer is disconnected** once it is 1 MiB behind. Messages are never dropped silently. *R2:* the failure is loud.
20. **A replay ring** keeps the last 64 values per channel for 5 minutes, for SSE `Last-Event-ID`. `subscribe` returns true when it replayed, which gives the history idiom `if !subscribe(t) { send history }`.
21. **Topics are per process.** Fan-out across processes is out of scope; it is listed as a silent spot with a planned PostgreSQL `LISTEN/NOTIFY` bridge.

### TLS server and HTTP/2 (stage 3)

22. **TLS 1.3 server in the runtime.**
    - The certificate chain and key are PEM; keys are PKCS#8, SEC1 or PKCS#1; ECDSA P-256 and RSA keys are supported.
    - SNI selects from comma lists; ALPN offers h2 and http/1.1.
    - Files are reloaded when their mtime changes.
    - There is no TLS 1.2.

    *R1:* no proxy hop is needed for TLS. *R2:* two environment variables.
23. **Constant-time signing in compiler-emitted machine code:**
    - P-256 with complete formulas, a fixed-base comb with masked full-table lookups, and hedged RFC 6979 nonces;
    - RSA-PSS with CRT, blinding and verify-after-sign;
    - X25519 and AES-GCM speed-ups as separately gated steps.

    *R1:* handshakes per second per core ≥ Go.
24. **Session tickets with psk_dhe_ke** (forward secret); no 0-RTT. *R1:* returning clients skip the signature.
25. **Optional mTLS** (`TLS_CLIENT_CA`), with the identity available through `client_cert()`.
26. **HTTP/2 server and client:**
    - h2 over TLS by ALPN, and h2c prior knowledge on plain ports (for proxies, gRPC and service meshes);
    - no h2c Upgrade, no push and no priorities (RFC 9218 signal);
    - every stream is a request coroutine, and framing runs in the event loop;
    - defenses against rapid reset, CONTINUATION floods, HPACK bombs, control-frame floods and zero-window stalls.

    *R1:* multiplexing with no per-stream thread. *R2:* no code.
27. **`fetch` speaks h2 when the server offers it.** Streams are multiplexed over one connection per origin per thread.

### gRPC (stage 4)

28. **`rpc Name [METHOD "path"] (params) -> results { }`.**
    - One handler serves gRPC, gRPC-Web and Connect, and optionally a REST route.
    - `service a.b.C` is optional.

    *R2:* the REST + gRPC program costs 254 tokens against Go's 991 (§14).
29. **Protobuf is derived from types.** Field numbers live in the khc-written `app.proto`, which acts as a lock file, and breaking changes are compile errors. *R2:* no `.proto` to write, and numbering mistakes are caught.
30. **Status mapping and call semantics.**
    - Statuses map to gRPC codes (§10.4).
    - `grpc-timeout` becomes the request deadline; cancellation is disconnection; metadata is headers.
    - Health and reflection are built in.
    - There is no compression and no custom trailers.
31. **Connect** (unary and server streaming, JSON or proto) **and gRPC-Web** (binary and text) are built in. *R2:* browsers and `curl` reach the same rpc.
32. **`khc proto x.proto`** imports types, and client stubs (`rpc ... at url`).
33. **A table-driven protobuf codec**, with a backward writer and zero-copy strings. *R1.*

### HTTP/3 (stage 5)

34. **Not implemented: HTTP/3 belongs to the edge.**
    - CDNs and load balancers terminate QUIC, and speak HTTP/1.1 or HTTP/2 to Khrip.
    - Triggers that would change this are in §11.

    *R1:* user-space QUIC costs more CPU per byte than TCP+TLS on data-center links. *R2:* nothing to write.

### Prompt

35. **KHRIP.md grows by 787 o200k (821 Claude).**
    - The gRPC details live in `GRPC.md` (760), given to the model only for gRPC tasks.
    - The streams section enters KHRIP.md only after the eval gate (§18). If the gate fails, it moves to a chapter too (+408 instead of +787).

## 2. Surface: what the AI sees

There are new words in three places only:
- the type constructor `stream T`;
- two top-level declarations, `topic` and `rpc` (and the optional one-line `service`);
- a handful of functions: `send`, `subscribe`, `unsubscribe`, `publish`, `client_cert`; and `open` in tests.

`fetch` gains a `for` form and a `timeout` clause, and `for` gains an optional variable type. Everything else (production behaviour, TLS, HTTP/2, protocol choice) is environment configuration with zero tokens in programs.

All new words are **contextual**: `stream`, `topic`, `rpc`, `service`, `open` and `timeout` keep working as identifiers where they are not in the new position, so no existing program breaks.

### 2.1 Server streams: `-> stream T` and `send`

```khrip
route POST "/chat" (body: Ask) -> stream Token | 400 str {
    if body.prompt == "" {
        return 400 "prompt is required"     // real 400: nothing was sent yet
    }
    send(Token { text: "..." })             // response starts here
}
```

- `stream T` is allowed only as a route or rpc result (the 200 variant) and as one route or rpc parameter (§2.2). It is not a value: it cannot be stored, passed, returned or compared.
- `send(v)` is allowed only lexically in the body of a route or rpc whose result is `stream T`, with `v: T`. Implicit conversions are as for `return`.
- The other variants (`| 400 str | 404`) are the statuses the route can answer *before* the stream starts. When the route returns without sending anything and without subscriptions, the response is an empty stream (200, zero events).
- **Format, picked by the request:**

  | Request | Response |
  |---|---|
  | `Upgrade: websocket` (GET) | WebSocket: one text message per value |
  | `Content-Type: application/grpc*` (HTTP/2) | gRPC server stream |
  | `application/grpc-web*`, `application/connect+json\|proto` | gRPC-Web or Connect stream |
  | `Accept` contains `text/event-stream` | SSE |
  | `Accept` contains `application/x-ndjson` or `application/jsonl` | NDJSON |
  | `Accept` contains `application/json` | one JSON array, streamed |
  | anything else, or no `Accept` | SSE |

  A `stream str` sends text: SSE `data:` lines, raw `text/plain` chunks, WebSocket text, or JSON strings in NDJSON and arrays.

### 2.2 Stream parameters: WebSocket and streamed bodies

```khrip
route GET "/rooms/{room}/ws" (room: str, user: str, msgs: stream Say) -> stream Line {
    for m in msgs {                          // one WebSocket text message at a time
        ...
    }
}

route POST "/import" (rows: stream NewOrder) -> Summary | 400 str {
    var n = 0
    for r in rows {                          // NDJSON lines, or elements of a JSON array
        sql "INSERT INTO orders {r}"
        n += 1
    }
    return Summary { inserted: n }
}
```

- At most one `stream T` parameter, and no other body parameter. Path and query parameters stay allowed.
- **GET** means the route is a WebSocket. A GET route with only `-> stream T` (no stream parameter) also accepts WebSocket clients, for server push; their messages are discarded.
- **POST** means a streamed body:
  - `application/x-ndjson`, `application/jsonl` or `application/json` (a top-level array, split element by element);
  - for `stream str`, any text type, split into lines.
- In an `rpc`, a `stream T` parameter is a gRPC client stream, with no method restriction.
- The parameter is read only with `for m in msgs`. Reading starts the response for a WebSocket: the 101 is sent at the first read. A `break` stops reading. A second loop later in the route continues where the first stopped.
- **Each pass of a loop over a stream counts as a request for the `sql` rules.** One write per pass outside `tx` is allowed, as one write per request is; that is the `INSERT` in the example. Two writes in a pass, or a read then a write, still need `tx { }`. The v0.12 rule against "a write in a loop" exists because a loop's writes would commit piecemeal inside one request. Here each pass is its own unit, and it is processed and acknowledged on its own.

### 2.3 Topics

```khrip
topic chat: Line                 // top level, like store

publish(chat[room], line)        // from any route, rpc, every-block or function
if !subscribe(chat[room]) {      // in a stream route: forward chat[room] to this client
    for l in rooms[room] ?? [] {
        send(l)                  // history only when nothing was replayed
    }
}
unsubscribe(chat[room])
```

- `topic name: T` declares a family of channels carrying `T`. `name` alone is the channel with the empty key; `name[key]` takes a `str` or `int` key.
- A topic is not a value.
- `publish(t, v)` with `v: T` never waits. It can also be written as a method: `chat[room].publish(line)`.
- `subscribe(t) -> bool` works only in a stream route whose element type is `T`. It forwards every value published to `t` afterwards, in publish order, until the client leaves or `unsubscribe(t)`. It returns true when it replayed values a reconnecting SSE client missed (§4.5). The stream stays open after the route returns while it has subscriptions.
- `subscribe`, `unsubscribe` and `publish` take the store lock in shared mode if it is not already held, so they order with store changes (§6.2). They do not make a route a writer.

### 2.4 Streaming fetch and deadlines

```khrip
for data in fetch POST URL req headers {"Authorization": "Bearer {key}"} {
    let c: Chunk? = from_json(data)
    ...
}
let r = fetch GET url timeout 2 s
```

- `for x in fetch METHOD url [body] [headers map] [timeout N unit] { }` gives `x: str` while the response arrives:
  - with `Content-Type: text/event-stream`, each event's `data` (multi-line `data:` joined with `\n`; comments, `event:` and `retry:` skipped);
  - otherwise, each line without its `\r\n`.

  A status other than 2xx ends the route with **502** `upstream answered 401: <first 200 characters of the body>`. That is a real 502 before the stream started, an error event after. Outside a route it is a panic with that text.

  In a `for` header, a literal request body (a map literal `{...}` or a struct literal `T { ... }`) must be bound to a `let` first, because its `{` could be the loop's (E-F3). This is the rule `if` conditions already have. A `headers {...}` literal is fine: `headers` announces it, and the `{` after its closing brace is the loop body.
- `timeout N ms|s|min` after any `fetch` sets that call's deadline:
  - the default is 30 s, and never past the request's own deadline;
  - for `for x in fetch`, the value is an idle timeout between bytes, with no total limit (an LLM may stream for minutes);
  - an expired deadline is `status 0` with body `deadline exceeded` (or 502 in the `for` form).

### 2.5 Typed loop variable, streamed `sql`

`for o: Order in sql "SELECT ..."` reads rows one at a time: a PostgreSQL portal fetching 256 rows per round trip. The type is required because nothing else gives it. `for x: T in xs` is also accepted for lists, and is checked.

### 2.6 gRPC: `rpc` and `service`

```khrip
service shop.v1.Orders          // optional; one per file; default: file stem → shop.Shop

rpc GetOrder GET "/orders/{id}" (id: int) -> Order | 404 { ... }   // gRPC + Connect + gRPC-Web + REST
rpc ListOrders (customer: str) -> stream Order { ... }              // no REST route
rpc Import (rows: stream NewOrder) -> Summary { ... }               // client stream
rpc Chat (msgs: stream Say) -> stream Line { ... }                  // bidirectional
rpc GetQuote (sym: str) -> Quote at env("QUOTES_URL")               // no body: a client stub
```

- An `rpc` with a body is a server method. With `METHOD "path"` it is also a route with exactly the semantics of `route`.
- The method name is UpperCamelCase (E-R1). The full name is `/<package>.<Service>/<Name>`.
- An `rpc` without a body and with `at <str or str? expression>` is a **client stub** (§10.8). It is called like a function. The address is evaluated once at start; none or an invalid URL stops the server with `khrip: rpc GetQuote: no address (env QUOTES_URL is not set)`.

### 2.7 Tests

```khrip
test "chat" {
    let a = open GET "/rooms/1/ws?user=ann"
    let b = open GET "/rooms/1/ws?user=bob"
    a.send(Say { text: "hi" })
    let m: Line? = b.next()
    expect m != none
    expect m.user == "ann"
    expect (call GetOrder(1)).status == 404
}
```

- `open METHOD "path?query" [headers map]` starts a stream route in-process. WebSocket mode is used when the route has a stream parameter and the method is GET; otherwise SSE or NDJSON, decoded for the test. `open Name(args)` does the same for a streaming rpc.
- `s.send(v)` sends one message (for a POST stream, one NDJSON item). `s.close()` ends the client side.
- `s.next()` returns the next value: typed by the annotation like `from_json` (a decode failure fails the test with the text), or JSON text without one. It returns none when the stream ended, or when nothing more can arrive (§7.6).
- `call METHOD "path"` on a stream route runs it to its return and gives the NDJSON body. `call Name(args)` calls an rpc through the protobuf codec; the `Response` has the code's HTTP status and a JSON body.

### 2.9 Alternatives considered

| Question | Chosen | Rejected, and why |
|---|---|---|
| Server streaming | `-> stream T` + `send(v)` | **`yield v`** (Python, C# generators): makes helper functions generators, mixes badly with statuses, and C#/Python habits around `yield` differ. **A `chan T` or returned iterator**: needs a producer task, the Go-style forgotten-close bug class, and more tokens. **A separate `sse` keyword**: one format only; NDJSON, WebSocket and gRPC would need their own. |
| Where `send` is allowed | Lexically in the stream route | **Any function**: the stream type would have to flow into helpers; a helper reused by two routes would be ambiguous. The cost is that helpers return values and the route sends them (E-S2 says so). |
| WebSocket | `stream T` parameter + `for` | **Event handlers** (`on message { }`, Socket.IO style): need closures over connection state and a separate close handler. **A `ws` value with `read`/`write`** (gorilla style): can be leaked, stored or used after close; needs explicit ping and close code. **A `socket` declaration**: duplicates route parsing (params, statuses, auth). The `for` loop is the shape of Go's read loop, Python's `async for` and C#'s `await foreach`, and of gRPC bidi streams. |
| Fan-out | `topic` + `subscribe`/`publish` | **A store map of connections** (what Go, C# and Python programs do): leaks on disconnect, double-close and slow-client bugs, and untyped. **String rooms `join("room")`**: untyped and invisible to the compiler. **SignalR-style groups on a connection id**: needs connection ids as values. |
| Topic keys | `chat[key]` | `chat(key)` reads like a call; `topic chat[str]: T` adds a declaration form; separate topics per room cannot be declared dynamically. |
| SSE resume | `subscribe` returns whether it replayed | **Automatic history suppression**: the runtime cannot know which `send`s are history. **Ignoring `Last-Event-ID`**: silent gaps after every reconnect. **A separate `resumed()`**: one more name. |
| Streaming fetch | `for x in fetch ...` (`x: str`) | **Typed `for c: Chunk in fetch`**: upstream SSE streams mix event types (`[DONE]`, pings, errors), so either undecodable events kill the stream or they are skipped silently. **A response value with `.next()`**: a new type with lifetime rules. |
| gRPC declaration | `rpc Name [METHOD "path"]` | **Derive gRPC from every route** with AIP names (`GetUser`, `ListUsers`): a path change silently renames a method, and singularisation guesses. **`service { rpc ... }` blocks**: more tokens and indentation. **`route ... as Name`**: hides that the route became a gRPC contract. |
| Field numbers | khc keeps them in `app.proto` | **Explicit numbers in types** (`id: int @1`): about 2 tokens per field, new syntax, and AI numbering mistakes. **Declaration order**: reordering silently breaks clients. **Hash of the name**: big numbers (tags up to 5 bytes), possible collisions. |
| Test clients | `open`, `.send`, `.next` | **`call` only**: cannot test WebSocket or broadcast. **A full client API** with timeouts and close codes: more spec tokens for rare needs. |
| Production behaviour | Environment, on by default | **Declarations in code** (`server { timeout 10 s }`): tokens in every program for what is right by default. |

## 3. Semantics: the production server (HTTP/1.1 core, shared by every protocol)

### 3.1 Request bodies, chunked encoding, smuggling

- **Reading.** When the head is complete, the request gets its coroutine at once. Today it waits until the whole body is in the 64 KB buffer. If the body is not already in the input buffer, the coroutine reads the rest itself into its arena, through `__co_wait` on the connection fd:
  - the bytes already in the input buffer are copied once;
  - then `read` goes directly into arena memory sized from `Content-Length`;
  - JSON decoding keeps zero-copy views into that block.

  A body of up to 4 MiB therefore costs one arena block and no per-connection buffer growth.
- **Limit.**
  - With `Content-Length > KHRIP_MAX_BODY`, the server answers `413` at once and closes after the response. It does not read the body.
  - A chunked body is cut off at the limit with `413`.
  - Stream parameters apply the limit per item, not per body.
- **`Expect: 100-continue`.** The server sends `HTTP/1.1 100 Continue` when the coroutine starts reading the body, or answers `413`/`417` instead of reading. Today `curl` waits 1 s for bodies over 1 KB.
- **Chunked decoding** happens in place, in the coroutine's read loop.
  - Chunk extensions are skipped. Sizes are hex, at most 16 digits, and a chunk size that overflows 2^62 is rejected.
  - Trailers are read and discarded, up to the header limit.
  - `0\r\n\r\n` ends the body.
- **Smuggling rules** (answer 400 and close, unless noted):
  - `Content-Length` together with `Transfer-Encoding`;
  - two `Content-Length` headers, or a list value;
  - `Transfer-Encoding` other than exactly `chunked` (501 for `gzip`, `chunked, gzip` and others);
  - obs-fold (a header line starting with SP or HTAB);
  - whitespace before the colon;
  - a bare LF as a line end in the head;
  - a NUL or a control character in a header value;
  - a request target that is not origin-form (CONNECT and absolute-form get 400).

  These are the rules RFC 9112 makes optional. Rejecting them closes the desync classes used against front proxies.

### 3.2 Limits and timeouts

| What | Default | On expiry |
|---|---|---|
| Head (request line plus headers) | 64 KiB (today's buffer); one header line ≤ 8 KiB | 431 and close |
| Head time from the first byte | `KHRIP_HEADER_TIMEOUT` 10 s | 408 and close; a slowloris holds one pooled buffer for at most 10 s |
| Body progress | no byte for 10 s | 408 and close (Kestrel's minimum data rate does the same job) |
| Keep-alive idle | 650 s | close (FIN) |
| Write stall (output not drained) | 30 s with no progress | close |
| Request deadline | `KHRIP_TIMEOUT` 30 s | cancelled at the next wait (§3.3); 503 `Retry-After: 1` if no response was started |
| Connections | `RLIMIT_NOFILE`, raised to the hard limit at start | new connections are accepted and closed with a log line once a minute |
| Pipelined requests in flight per connection | 64 KiB of input | reading pauses (today's behaviour) |

A timer wheel per thread holds connection timers: 1 s slots, O(1) insert and remove. The coroutine deadline heap stays for `sleep` and waits with deadlines. 100k connections cost 100k wheel entries of 32 bytes, with no heap reshuffling.

### 3.3 Deadlines and cancellation

- **Each coroutine has a deadline and a cancel flag** (two ctx words).
  - The deadline comes from `KHRIP_TIMEOUT`, or from `grpc-timeout`/`Connect-Timeout-Ms`, or per message in a message loop.
  - The flag is set by a client disconnect (an `EPOLLRDHUP`/`EPOLLHUP` on the client fd while a stream or a long request runs), by `RST_STREAM`, or by graceful shutdown.
- **`__co_wait` checks both** before parking and after waking. If the deadline has passed or the flag is set, it raises a cancel panic: kind `PANIC_CANCEL`, not logged as an error. The panic unwinds through today's catch path in `__serve_one` and ends in `__store_release_final`.
  - In `tx` this rolls back.
  - Pool connections that were mid-exchange are closed, not returned.
- **Non-stream requests are not cancelled by a disconnect.** They run to their end, as today, because a write half-done outside `tx` is worse than finished work. Only their deadline applies.
- **Stream routes and rpcs** are cancelled by a disconnect at their next `send` or wait.
- **`fetch` inherits the deadline:** `min(timeout clause or 30 s, deadline - now)`.
- **`sql` inherits it too:** `statement_timeout` = `min(DATABASE_TIMEOUT, deadline - now)`, sent with the statement as today's `set_config` is. A cancelled `sql` sends `CancelRequest`, as v0.12 does on its timeout.

### 3.4 Graceful shutdown

1. **Signals are always handled.** SIGTERM and SIGINT are blocked in all threads from start and received by the control thread. That is today's timer thread, now always spawned; it also runs `every` blocks and `KHRIP_DATA` saves.
2. **First SIGTERM:**
   - `/readyz` answers 503 and the gRPC health status becomes NOT_SERVING;
   - the log gets `khrip: draining (lame duck 5 s, budget 25 s)`.
3. **During the lame-duck period** (`KHRIP_LAMEDUCK`) the server keeps accepting, because endpoint removal propagates slowly in Kubernetes. Then every worker closes its listening socket. With `SO_REUSEPORT`, the kernel stops routing to a closed socket at once.
4. **Connections:**
   - Idle HTTP/1.1 keep-alive connections are closed.
   - A busy one gets `Connection: close` on its current response.
   - HTTP/2 connections get a graceful GOAWAY: last stream id 2^31-1 plus PING, then the real last id after one RTT.
   - **Parked streams end at once:** SSE streams are closed (clients reconnect elsewhere with `Last-Event-ID`), WebSockets get close 1001, and gRPC streams that are parked or only subscribed get trailers `UNAVAILABLE "server is shutting down"`.
   - Streams that are running code continue until they park or the budget ends.
5. **`every` blocks** are not started again; a running one is awaited within the budget.
6. **At `KHRIP_DRAIN`**, coroutines still running are cancelled (§3.3) and get one second to unwind. Then the final `KHRIP_DATA` save runs (today's `__save_store`), and the process exits 0.
7. **A second SIGTERM or SIGINT** exits at once with code 1. It does not save, because a save might be what is hanging.

### 3.5 Logs, metrics, trace ids

- **Trace ids.**
  - An incoming valid `traceparent` (version 00, non-zero ids) gives the trace id and the parent span. Otherwise a new trace id is made from a per-thread xoshiro256** generator seeded by `getrandom`.
  - Each request gets a new span id.
  - `fetch` and gRPC client calls send `traceparent: 00-<trace>-<new span>-<flags>` and pass `tracestate` through unchanged. The flags are the incoming ones, or 01 for a new trace.
  - The id is in every log line of the request. It is not exposed to code: `header("traceparent")` gives the incoming value.
- **`KHRIP_LOG=requests`** writes one JSON line per request to stderr, from a per-thread 64 KiB buffer flushed by the event loop every 100 ms or when full:

  ```json
  {"time":"2026-10-25T10:00:00.123Z","trace":"4bf92f3577b34da6a3ce929d0e0e4736","method":"GET","route":"/users/{id}","path":"/users/42","status":200,"ms":0.31,"in":0,"out":512}
  ```

  - **The query string is never logged.** Browsers put WebSocket tokens there.
  - A stream gets one line when it ends, with `"stream":"sse|ws|ndjson|grpc"`, the messages in and out, and the close code.
  - `KHRIP_LOG=json` (and `requests`) also turns panics and `eprint` inside a request into `{"time","trace","route","level","msg"}` lines.
- **Metrics on `METRICS_PORT`.** The port is plain HTTP, served by worker 0's event loop with no coroutines, and gives `/metrics` (Prometheus text 0.0.4), `/healthz` (200 while the process runs) and `/readyz` (200 after start checks, 503 while draining). The series:

  | Series | Labels |
  |---|---|
  | `khrip_http_requests_total` | `route`, `method`, `code` |
  | `khrip_http_request_duration_seconds` | histogram, `route`, `method`; buckets 0.5 ms to 10 s |
  | `khrip_http_inflight` | |
  | `khrip_connections` | `proto` = h1, h2, ws, sse, grpc |
  | `khrip_streams_open` | `route` |
  | `khrip_stream_messages_total` | `route`, `dir` |
  | `khrip_stream_slow_closed_total` | `route` |
  | `khrip_topic_published_total` | `topic` |
  | `khrip_topic_subscribers` | `topic` |
  | `khrip_fetch_requests_total` | `host`, `code` |
  | `khrip_fetch_duration_seconds` | `host` |
  | `khrip_sql_duration_seconds` | `site` |
  | `khrip_db_pool_in_use` | |
  | `khrip_store_heap_bytes` | |
  | `khrip_gc_cycles_total` | |
  | `khrip_tls_handshakes_total` | `result` |
  | `process_resident_memory_bytes`, `process_cpu_seconds_total`, `process_open_fds`, `process_start_time_seconds` | |
  | `khrip_build_info` | `version` |

  - Counters live in a per-thread array indexed by a compile-time slot. A request adds without atomics; a scrape sums the threads.
  - Route labels are the declared path templates, so cardinality is bounded by the program.
  - Topic labels are the declared names, not the keys.

### 3.6 Connection layer changes that everything above needs

- **Buffer pools per thread.**
  - Input buffers start at 16 KiB and grow by doubling to the head limit, or to a frame's or message's size.
  - Output is a queue of 64 KiB segments.
  - Buffers return to the pool when a connection is idle: no partial input, nothing to send.
  - An idle keep-alive connection then holds only its `__Conn` (≈ 160 B) and a wheel entry.
- **The fd table** becomes a growable two-level table, so fds over 65,535 are served.
- **A header index per request.** `header()` uses a (lower-case name hash, offset, length) array, built lazily at the first call. HTTP/2 fills it from HPACK. This is O(1) after the first call instead of a split per call.
- **CORS** with `KHRIP_CORS`:
  - `OPTIONS` with `Origin` and `Access-Control-Request-Method` on a declared path gets 204 with `Access-Control-Allow-Origin` (the origin echoed), `Allow-Methods` (the route's methods), `Allow-Headers` (echoed), `Max-Age: 600` and `Vary: Origin`;
  - responses to allowed origins get `Allow-Origin`, `Vary` and `Expose-Headers` (the names set with `set_header`, plus `grpc-status`, `grpc-message` and `Connect-*` for rpcs);
  - credentials are allowed only for listed origins, never with `*`.

## 4. Semantics: streams and Server-Sent Events

### 4.1 Lifecycle and framing

- **The response head (or the 101, or the gRPC response headers) goes out at the first of:**
  - a `send`;
  - the first read of the stream parameter, for a WebSocket (the 101) or a gRPC/Connect stream. A POST upload with a non-stream result answers at its return, as any route does;
  - the first wait after a `subscribe`;
  - the route's return with live subscriptions;
  - `KHRIP_PING` (20 s) without any of these, so that proxies see bytes during a slow start.

  Before that, the route is an ordinary request: `return 404`, `fail(401)`, a panic (500) and `set_header` behave exactly as today.
- **Head per format:**

  | Format | Head | Notes |
  |---|---|---|
  | SSE | `200`, `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no` | Chunked on HTTP/1.1, so the connection can be kept alive after a finite stream |
  | NDJSON | `200`, `application/x-ndjson` | Chunked |
  | JSON array | `200`, `application/json` | Chunked |
  | `stream str` | `text/plain; charset=utf-8` | Chunked |
  | HTTP/1.0 client | — | No chunking; the body ends with the close |

- **Framing of one value.** The value is JSON-encoded straight into the connection's output segment, behind reserved space for the prefix, which is then written right-aligned. There is no copy.

  | Format | One value |
  |---|---|
  | SSE | `data: <json>\n\n`, plus `id: <topic id>\n` for topic values (§4.5). The JSON encoder never emits a raw newline, so one `data:` line suffices. A `stream str` value with newlines becomes several `data:` lines. |
  | NDJSON | `<json>\n` |
  | JSON array | `[`, then values separated by `,`, then `]` |
  | HTTP/1.1 chunk | `<hex>\r\n` prefix and `\r\n` suffix |
  | HTTP/2 | a DATA frame header |

- **End.** A finite stream ends with the last chunk (`0\r\n\r\n`) or `END_STREAM`, and the request log line is written. The connection then serves the next pipelined request.

### 4.2 Backpressure and queues

- Each stream has a send queue counted in bytes not yet written to the socket (or not yet allowed by HTTP/2 flow control).
- **`send` when the queue is over `KHRIP_STREAM_QUEUE` (1 MiB):**
  - without the store lock, it waits through `__co_wait` until the queue falls under half the limit, or the client leaves (cancel), or 60 s pass with no progress (the stream ends: slow client);
  - with the store lock held, it does not wait. Waiting would release the lock in the middle of a history-plus-subscribe section (§6.2). It queues past the limit up to a hard cap of 16× (16 MiB); beyond that the stream is closed as a slow client.
- **Topic deliveries never wait.** A subscriber whose queue would pass the limit is closed (§6.3).
- Queues hold either private segments (values from `send`) or references to shared, reference-counted topic frames, so 10k subscribers of one message hold one copy.

### 4.3 Client disconnect

- While a stream runs, the client fd is armed for `EPOLLRDHUP`.
  - On HTTP/1.1 SSE and NDJSON, input after the head is not expected. Any input except a valid next pipelined request is discarded, and a FIN means the client left.
  - On a WebSocket, a close frame or FIN means the client left.
  - On HTTP/2, an `RST_STREAM` or the end of the connection does.
- Then the stream is marked dead, and its subscriptions are removed at once, so no more deliveries are queued.
- A handler running in a coroutine gets its cancel flag. It unwinds at its next `send` or wait (§3.3): `fetch` connections, including a streaming `fetch`, are closed, and `sql` is cancelled.
- A parked message loop or a subscribed-only stream is freed at once: no coroutine runs.

### 4.4 Keep-alive pings

After `KHRIP_PING` of silence on a stream:

| Protocol | Ping | Dead peer |
|---|---|---|
| SSE | `:\n\n` | a write error, or a write stall over 30 s |
| WebSocket | PING frame (empty payload) | no frame of any kind received within two intervals: close 1006 locally, socket closed |
| HTTP/2 | PING on an idle connection | no ACK within 2 intervals: closed |

Pings come from the timer wheel, need no coroutine and are not counted in metrics as messages.

### 4.5 Event ids and `Last-Event-ID`

- **Only topic deliveries carry an id:** `id: <epoch>.<seq>`.
  - The epoch is 8 hex digits, random per process start.
  - The seq is the channel's sequence number (§6.1).
  - Values from `send` carry no id. Per the SSE spec the browser keeps the last id it saw.
- **On `subscribe(t)` in an SSE request with `Last-Event-ID: E.S`:** if E is this process's epoch and the channel's replay ring still holds seq S, the values after S are queued immediately (the replay), and `subscribe` returns true. Otherwise it returns false. That covers an id that is too old or one from another process after a restart or another replica.
- **The idiom `if !subscribe(t) { send history }`** gives each case the right result:
  - a fresh client gets history;
  - a resumed client gets only what it missed;
  - an unresumable client gets history again. That may repeat values it saw, but loses none, and the values carry their own fields for a client that wants to deduplicate.
- **The replay ring** keeps, per channel, the last `KHRIP_TOPIC_REPLAY` (64) frames with their ids. The frames are shared with delivery, so the ring holds references, not copies. Entries older than 5 minutes are dropped. A process-wide budget of 64 MiB evicts the oldest entries across channels.

### 4.6 Errors after the head

| Cause | SSE | NDJSON / array / text | WebSocket | gRPC / Connect / gRPC-Web |
|---|---|---|---|---|
| `return 4xx/5xx` or `fail(status, msg)` | `event: error\ndata: {"status":403,"message":"..."}\n\n`, then end | the chunked body ends without its terminator (the client sees a broken response), log line | close `4000 + status` (4403), reason = message (cut to 123 bytes at a UTF-8 boundary) | trailers with the mapped code and `grpc-message` |
| panic | as above with 500 and `Internal Server Error`; the panic text goes to the log only | as above | close 1011 | INTERNAL |
| deadline | 504 / `deadline exceeded` | as above | 4504 | DEADLINE_EXCEEDED |
| shutdown | end (client reconnects) | as above | 1001 | UNAVAILABLE |
| slow client | close | close | 1008 `too slow` | RESOURCE_EXHAUSTED (the client is gone or stuck) |

`set_header` after the head panics with `set_header after the response started` (R-S1 in §12.3). That is loud rather than silently ignored.

### 4.7 Request streams: NDJSON, arrays, lines

- **NDJSON:**
  - a line is split on `\n` (and a trailing `\r` is dropped);
  - an empty line is skipped;
  - each line is decoded with today's JSON decoder into the item's arena. Strings are views into the input buffer, which is not advanced until the item ends.
- **A JSON array body** (`[` first, after whitespace) is split into elements by a structural scanner that tracks depth, strings and escapes, reusing `__find_json_special` (SIMD). Each element is decoded like an NDJSON line.
- **`stream str`:** lines.
- **Error in an item.** The path names the item: `body[3].text: expected str`, with a 1-based line number for NDJSON (`line 3: ...`). If the head has not gone out, the answer is 400 with that text and the connection is closed (the rest of the body is unread). After the head, it is an error per §4.6.
- **Item limit.** An item larger than `KHRIP_MAX_BODY` gets 413, or an error after the head.
- **Constant memory.** Each item runs in fresh memory (§7.1), so a 100 MB upload runs in roughly the arena high-water of one item.

### 4.8 Streaming fetch

- **`__fetch_open`** builds the request bytes before releasing the store lock, like `__fetch` does. The open (connect, send, read the head) is one audited window (§7.3).
- Each step of the loop reads with a wait (the `__co_wait` window) and parses one SSE event or one line:
  - in place, in a per-request read buffer;
  - the payload `str` is a view, valid for the pass;
  - chunked transfer coding is decoded as bytes arrive.
- **The connection is closed, never pooled,** if the loop ends early by `break`, `return`, cancel or panic. After a complete response it goes back to the pool.
- **HTTP/2 upstreams** (decision 27) use one multiplexed stream. An early end sends `RST_STREAM(CANCEL)`, which stops the upstream's generation: for an LLM provider, that saves the remaining tokens.

## 5. Semantics: WebSocket

### 5.1 Handshake

- **When it is a WebSocket request.** A GET with `Upgrade: websocket` (any case), `Connection` containing `upgrade`, `Sec-WebSocket-Version: 13` and a 16-byte base64 `Sec-WebSocket-Key`, on a route whose result is `stream T`.
  - The wrong version gets `426` with `Sec-WebSocket-Version: 13`.
  - A missing or bad key gets 400.
  - An Upgrade request to a non-stream route gets an ordinary response, without upgrading.
- **Origin.** With no `Origin` (non-browser clients) the request is accepted, and so is an `Origin` whose host equals `Host`. Otherwise the origin must be listed in `KHRIP_CORS` (or `*`), or the answer is 403 `origin not allowed`.

  gorilla/websocket and coder/websocket also check by default. Node `ws` and many hand-written servers do not, which lets any page open a cookie-authenticated socket.
- **The route runs before the 101,** so `header()` (cookies, `Authorization`), path and query parameters and `return 401` work as for any request. The 101 (`Sec-WebSocket-Accept: base64(SHA-1(key + 258EAFA5-E914-47DA-95CA-C5AB0DC85B11))`) goes out per §4.1.
- **Subprotocols** (`Sec-WebSocket-Protocol`) are not negotiated: no header is returned. **Extensions** are ignored: permessage-deflate is never accepted (§5.5).
- **The request head** (method, path, query, headers) is copied into the connection's keep heap at the 101, so `header()` keeps working in the message loop after the input buffer is reused for frames.

### 5.2 Frames, fragmentation, UTF-8, sizes

- **The parser runs in the event loop on the pooled input buffer:**
  - FIN, RSV1–3 (must be 0, else 1002), opcode, MASK (must be 1 from clients, else 1002), and 7/16/64-bit lengths;
  - a 64-bit length with the top bit set is rejected (1002).
- **Unmasking** is done in place with `__simd_ws_unmask(p, n, key, offset)`: AVX2 does 32 bytes per step with the key rotated by the offset, with SSE2 and scalar fallbacks.
- **Text messages** must be valid UTF-8, checked with the v0.13 SIMD validator (1007 if not). The check is incremental across fragments; a code point split across fragments is allowed.
- **Fragmentation.** Continuation frames are assembled in the connection's input buffer, which grows up to `KHRIP_MAX_BODY` (1009 beyond). Control frames may interleave between fragments, as the RFC requires.
- **Binary messages** get close 1003 `binary messages are not supported`. There is no `bytes` type; see the D9 note in §19.
- **Control frames:**
  - over 125 bytes, or fragmented, means 1002;
  - PING is answered by a PONG with the same payload from the event loop, even while a handler runs;
  - an unsolicited PONG is ignored.
- **Delivery to the route.** A complete text message becomes one item of `for m in msgs`, decoded as JSON into `T`, or given as a `str` for `stream str`. A message that does not decode gets close 1007 with the decoder's text as the reason, for example `text: expected str`, cut to 123 bytes.
- **Sending.** One unmasked, unfragmented text frame per value, with a 2-, 4- or 10-byte header written right-aligned before the JSON already encoded in the output segment. Topic frames are built once and shared (§6.5).

### 5.3 One message at a time

- A connection's messages are handled in order, one at a time. While an item runs, the event loop parses no further data frames from that connection: TCP pushes back to the client. It still answers PINGs, sees CLOSE and FIN, and sets the cancel flag on FIN.
- This keeps per-connection order without locks, and bounds a connection to one message buffer.
- A handler that needs concurrency per connection does not exist in v0.14. A client that pipelines many messages is served in order.

### 5.4 Close handshake and codes

| Event | Code sent | Then |
|---|---|---|
| Route returns normally, or the message loop ends by `break` and the route returns | 1000 | Wait up to 5 s for the client's close, then close the TCP connection |
| Client sends close (code c) | echo c if valid (1000–1003, 1007–1011, 3000–4999); else 1002 | Close the TCP connection after sending; a running handler is cancelled |
| Invalid close code or payload from the client (1004–1006, 1015, < 1000, > 4999, bad UTF-8 reason) | 1002 | close |
| `return status` / `fail(status, msg)` after the 101 | 4000 + status, reason msg | as for 1000 |
| Panic | 1011 `internal error` | as for 1000 |
| Deadline in an item | 4504 | as for 1000 |
| Message over `KHRIP_MAX_BODY` | 1009 | close |
| Invalid UTF-8 or undecodable JSON | 1007 | close |
| Binary message | 1003 | close |
| Slow consumer | 1008 `too slow` | close at once (no waiting) |
| Server shutdown | 1001 | close |
| No frames for two ping intervals | — (TCP closed) | handler cancelled |

### 5.5 permessage-deflate: no

- **Memory.** zlib with context takeover holds about 300 KB per direction per connection at the default window. Even `server_max_window_bits=10` keeps several KB per connection. That is more than this design's whole per-connection budget (2.5 KB).
- **CPU.** Compression costs more per message than framing does, and broadcast cannot share compressed frames when context takeover is on.
- **Security.** Compressing secrets next to attacker-controlled text leaks them (CRIME/BREACH-style).
- **Practice.** gorilla/websocket (`EnableCompression` false) and Kestrel (`DangerousEnableCompression` must be set) leave it off by default.

*What would change it:* messages over about 4 KiB of repetitive JSON being common in the eval tasks. Then the opt-in would be `KHRIP_WS_DEFLATE=1`, with no context takeover and a shared per-thread compressor.

### 5.6 Authentication on long connections

`header()`, cookies and query parameters are checked once, at connect. The connection then lives on even if the credential is revoked; that is a silent spot in every language (S7 in §14.5).
- **What a program can do in v0.14:** check the credential again for each message inside the message loop (it is just code), and tell clients to leave through a per-user topic that the client obeys.
- **What it cannot do:** a server-side "close every connection of user X" needs a way for a topic value to end a parked stream. That is out of scope (§20).

## 6. Semantics: topics

### 6.1 Delivery guarantees and ordering

- **At most once.** A value is delivered to every subscriber that was subscribed when it was published, unless the subscriber leaves or is closed as slow. There is no persistence, no acknowledgement and no retry.
- **Total order per channel.** Every subscriber of `chat[k]` sees the values of `chat[k]` in the same order: the order of their sequence numbers, which `publish` assigns under the channel's lock. Across channels there is no order.
- **Per stream,** values from `send` and deliveries are interleaved in the order they were queued. Deliveries queued while the route's own code is running (the same thread) come after the route's sends.
- **The subscription start.** A subscription records the channel's sequence number at registration. Deliveries with a seq at or below it are skipped for that subscriber, even if they were already in its thread's inbox. So a value published before `subscribe` is never delivered to it.

### 6.2 Ordering with store: history without gaps or repeats

- `publish`, `subscribe` and `unsubscribe` take the store lock in shared mode when it is not held. A route that only publishes stays a reader and runs in parallel with other readers.
- A writer that stores a value and publishes it with no wait between holds the exclusive lock across both. A subscriber that subscribes and reads history with no wait between holds at least the shared lock across both. So for any value V written and published:
  - either V's write and publish happened before the subscriber's section: V is in the history, and its seq is at or below the subscription start, so it is not delivered;
  - or after it: V is not in the history, and it is delivered.

  Hence "nothing is lost or repeated" in the KHRIP.md text.
- The guarantee needs no wait between the store write and `publish` in the writer, and none between `subscribe` and the history read in the subscriber. `send` never waits while the lock is held (§4.2), so the history loop does not break it.
- A writer that waits between them (`rooms[id] = ...; fetch ...; publish(...)`) loses it. That is S2 in §14.5, with a candidate warning.

### 6.3 Slow consumers

- A delivery that would take a subscriber's queue over `KHRIP_STREAM_QUEUE` closes that subscriber:
  - SSE: the response ends (the client reconnects, and §4.5 replays what it missed if the ring still has it);
  - WebSocket: close 1008 `too slow`;
  - gRPC: RESOURCE_EXHAUSTED.
- The closure is counted in `khrip_stream_slow_closed_total` and logged once a second per route at most.
- Dropping values for a slow client while keeping it connected would be a silent gap. Blocking the publisher would let one slow client stall a room: the Python P2 bug listed in §14.5.

### 6.4 Lifetime and memory

- Channels are created on first use, and dropped when they have no subscribers and their replay ring is empty or expired (checked once a minute).
- **A channel** costs about 96 B plus ring references: the sequence counter, the lock, the thread mask, per-format subscriber counts and the ring head.
- **A subscription** costs 32 B in its thread's table plus 16 B in the stream's subscription list.

### 6.5 Cross-thread fan-out and its cost

**Process-wide state:**
- the channel table, sharded 64 ways by key hash, each shard under a futex mutex;
- `ChannelState { lock, seq, threads: bitmask, json_subs, pb_subs, ring }`, allocated from an mmap heap outside store and the arenas.

**Per thread:**
- a table from channel to the list of local subscriber streams;
- an inbox of `(channel, seq, json_frame, pb_frame)` entries: a multi-producer, single-consumer ring of 4,096 slots, growing on overflow.
  - A producer claims a slot with `lock xadd` on the tail, writes the entry, and marks it ready. The consumer reads in slot order.
  - Entries for a channel are enqueued under that channel's lock, so two publishers on different threads enqueue in seq order, and every consumer sees each channel in seq order.
  - Separate rings per producer would lose this: a consumer could drain thread 2's ring, holding seq 6, before thread 1's, holding seq 5;
- an `eventfd` registered in the thread's epoll.

**`publish(t, v)`:**
1. If `json_subs > 0` or the ring is on, encode v once into a shared frame block: the JSON payload with the WebSocket header, the SSE line and the chunk framing laid out so that each format is a slice of it. If `pb_subs > 0`, encode protobuf with the 5-byte gRPC prefix.
2. Lock the channel, increment `seq`, append to the ring, and for each bit in `threads` push one entry to that thread's inbox (reference count += 1 per thread). Unlock.
3. Threads whose inbox went from empty to non-empty are recorded in the publisher's ctx. The `eventfd` writes are made at the publisher's next store-lock release or event-loop turn, never inside the critical section.

**Delivery in each subscriber thread:**
1. The event loop drains its inbox.
2. For each local subscriber with a start below the seq, it appends a reference to the right slice to that stream's queue. Local references are counted without atomics; one atomic reference is held per thread.
3. It marks the stream writable.
4. At the end of the loop turn, each writable connection gets one `writev` of up to 64 queued slices. For HTTP/2, a 9-byte DATA frame header per stream precedes the shared slice.

**Cost:**
- a publish is one encode plus one inbox push per thread that has subscribers, plus at most one `eventfd` write per thread per loop turn;
- a delivery is one queue append (about 20 ns) plus its share of a `writev` (about 1–2 µs of kernel time, shared across all values queued for that connection in that turn).

The typical Go, C# and Python programs (the hub pattern in §14) encode JSON once per subscriber per message and wake one goroutine or task per subscriber. At 10k subscribers that is 10k encodes and 10k wake-ups per message, against one encode and N_threads hops here.

### 6.6 Processes

- Topics are per process, like store. Two replicas behind a load balancer do not share broadcasts.
- This is decision 21, and S1 in §14.5 is the silent spot it leaves. The planned fix is out of scope: `topic chat: Line shared`, bridging through PostgreSQL `LISTEN/NOTIFY` on `DATABASE_URL` (8,000-byte payload limit, so large values would travel as ids).
- At start, if `KUBERNETES_SERVICE_HOST` is set and the program declares topics, one log line says `khrip: topics are per process; replicas do not share them`.

## 7. Memory and concurrency: arenas, keep heaps, store, GC, tx

### 7.1 Per-item memory and the keep heap

**Where memory lives.** A request has one arena, reset when it ends. Long handlers get three tiers:

| Tier | Holds | Freed |
|---|---|---|
| **Item memory** | the arena above the item mark | after each pass of a loop over a stream |
| **Request keep heap** | values that outlive an item of an inner loop (a `fetch` loop, a `sql` loop, a POST body loop) | when the request, or the current message, ends |
| **Connection keep heap** | values that outlive messages of the route's message loop (`for m in <stream parameter>`) | when the connection closes |

**What the compiler emits for a loop over a stream** (a stream parameter, a streaming `fetch`, or a streamed `sql`):
- **At loop entry:**
  - save `CTX_ITEM_MARK` (a new ctx word, holding the previous mark) and set it to the arena pointer;
  - for the message loop only, copy every non-scalar local in scope (including parameters) into the connection keep heap, `x = __keep(x, desc(x), CONN)`, and release the setup arena (§7.2).
- **At the end of each pass:**
  - `__item_end()` frees the keep values replaced during the pass (deferred frees, below);
  - it zeroes the used bytes, resets the arena pointer to the mark, and clears the string cache (as `__call` does).
- **On an assignment to a variable declared outside the loop:** `x = __keep(v, desc, owner)`, where the owner is CONN if x was declared before the message loop, else REQ. The old value of x goes on the pass's deferred-free list.
- **On a write into an object:** the existing barrier, generalised (lib/api.kh `__barrier`):

  ```
  fn __barrier(obj, v, d) -> int {
      if v == 0 || __in_data(v) { return v }
      if __in_arena(obj) {
          let mark = load64(__ctx() + CTX_ITEM_MARK)
          if mark == 0 || obj >= mark { return v }            // obj belongs to the current item
          return __keep(v, d, REQ)                             // obj is older than the item
      }
      if __in_keep(obj) { return __keep(v, d, __keep_owner(obj)) }   // always a copy, even of store values
      if __in_store(v) { return v }
      return __persist_copy(v, d)                              // obj is in store
  }
  ```

  The fast path (an object in the current item, no loop active) adds one load and one compare. `__alloc_for(h, n)`, which places container growth, gets the same three cases: a keep-heap owner grows in its keep heap, and an arena owner below the mark grows in the request keep heap.
- **The KHRIP.md sentence** "variables from outside it act like `store`: assigning copies" describes exactly this. It is the same copy-on-write-into rule store already has.

**The keep heap allocator:**
- **Shared spans.** One allocator per thread, in an address range `KEEP_REGION` (1 TiB, `MAP_NORESERVE`), so `__in_keep(p)` is one shift and a compare. Spans of 64 KiB each hold one size class (16 B to 32 KiB; larger blocks get their own mmap). Spans are shared by all owners on the thread, so a connection with 200 B of kept state costs about 250 B, not a span.
- **A 16-byte block header** in front of the object (Khrip objects have no headers, but this allocator owns the bytes before the pointer): the owner id with the size class, and the next block of the same owner. `__keep_owner(obj)` is one load.
- **Owners:** a connection (CONN), or a request or one message's pass (REQ). Each has a list head and a byte count.

**Exact frees with no collector.**
- **Values are trees.** `__keep` makes a deep copy: an iterative variant of `__deep_copy` that also copies store values. So keep values form trees owned by one variable or one container slot, apart from DATA pointers.
- **A replaced or removed value is freed exactly, at the end of the pass.** It cannot be freed earlier, because locals of the pass may still point to it. The cases are an overwrite, `remove_at`, `pop`, `clear`, and the old backing array after growth.
  - The free walks the tree by its descriptor.
  - It marks the blocks dead and returns them to their spans.
  - The owner's list drops dead blocks in one sweep per pass that freed something. A typical list is tens of blocks.
- **When an owner's scope ends, all its blocks are freed:**
  - REQ at the end of the request or the message pass;
  - CONN when the connection closes.
- **Accumulation.** `full = full + token` in an LLM loop allocates the new string and frees the old one at the end of the pass, so memory stays at about one copy. As an optimization, `x = x + e` on an outer `str` appends in place when the block's size class has room, which makes accumulation amortized O(n).
- **A cap,** `KHRIP_STREAM_STATE` (64 MiB per owner), turns runaway growth (a per-connection map that only grows) into a panic: close 1011, with a log line naming the route.

**The semantic difference this makes visible.** A value read from store *before* the message loop is a snapshot inside the loop; read store again inside the loop for current data. Inside one pass, store objects are referenced as usual. This is S11 in §14.5.

### 7.2 Connection state; parking without an arena

**A stream connection** (`__Stream`, allocated in the thread heap and freed at close) holds:
- the fd, the protocol and its state;
- the send queue, the subscriptions and a timer wheel entry;
- the copied request head (for `header()`) and a small Worker without its body buffers;
- the connection keep heap.

**Parking at the head of the message loop.** When the next message is not buffered, `__stream_park`:
1. Releases the store lock with `__store_release_final()`. At the loop head no live local holds a store pointer: outer locals were copied into the keep heap at loop entry, and item locals are dead. So no pin record stays linked.
2. Saves the stack frames from the parking frame up to `sch.top` into an exact-size block in the connection (1,312 B measured for a route today, against the 4 KB minimum `__co_evict` allocates now), saves the jump buffer and the ctx words, apart from the arena words.
3. Returns the coroutine (its arena reset, its Worker and its ctx block) to the thread's pool, and counts nothing against `KHRIP_COROUTINES`.

**On the next message:**
1. A free coroutine is taken.
2. The saved frames are copied back to the same stack addresses (as `__co_enter` does today).
3. The ctx words are restored, with the new coroutine's arena.
4. The coroutine resumes in `__stream_park`. It re-reads `CTX_CORO` and holds no reference to the old coroutine object.

**Running frames below the route** (`__co_main`, the stream job, `__serve_one`, `__dispatch`) hold only stable objects after the 101: the `__Stream`, the copied head, the connection and the Worker-lite. Stream routes are dispatched through `__stream_job` instead of `__co_job` for exactly that reason.

**A stream that only subscribed** (its route returned) has no frames at all. Its state is the `__Stream` and its subscription entries.

**Memory targets** (gated in steps 1 and 11):

| | Today (measured) | Target |
|---|---:|---:|
| Idle keep-alive connection | 9.7 KB | ≤ 1 KB |
| Parked request | 8.4–12.8 KB | — |
| Idle WebSocket in a message loop | — | ≤ 2.5 KB (`__Stream` ≈ 400 B, frames ≈ 1.3 KB, kept values ≈ 0.25 KB in shared spans) |
| Idle SSE subscriber | — | ≤ 1 KB |

Kernel socket buffers are extra in every language and are not in RSS.

### 7.3 Store lock windows

- **The store lock is never held across a wait:**
  - `send` waits only without the lock (§4.2);
  - the message-loop park is a final release;
  - topic operations never wait;
  - every other wait goes through `__co_wait`, today's audited window.
- **One new audited release site: `__fetch_open`.** It has the same structure as `__fetch`: request bytes, headers and the URL are built before `__store_release_keep`; inside the window only the exchange runs, writing mmap and arena memory above `hi`. It is added to the lint list in tests/run.sh, as v0.13-store-gc.md §6.6 requires.
- **HTTP/2 framing, WebSocket framing, TLS records, topic fan-out and pings** run in the event loop, outside any request context. They never touch store or arenas.
- **A topic publish serializes v under the lock it took or already held.** The frame bytes go to mmap blocks, so no store pointer escapes.

### 7.4 GC pin records

- **Parked message loops and subscribed-only streams publish nothing.** Their release is final, and the keep heaps hold no STORE pointers, because they are deep copies. So the collector never scans connections, and the "long holders" report (store-gc §8.6) sees streams only while an item is mid-wait.
- **Waits inside an item** (a `fetch` in the message handler) publish and withdraw records exactly as requests do. The item's arena range is published lazily (store-gc §6.4); the item mark only narrows it.
- **Send queues, topic frames and replay rings** are bytes in mmap blocks. The connection object lives in the thread heap, and its saved frames contain no live STORE pointers: dead slots may hold stale values, and they are never dereferenced, because the next pass rewrites them before use.

  Verify mode makes this loud. At park, `__simd_pinscan` (the scan publication uses) finds STORE-range words in the saved snapshot and overwrites them with a poison value. They are dead by construction, so the poison is harmless. A word that was in fact live makes the resumed code fault at its first use, instead of reading freed memory later. This runs only in `KHRIP_GC_VERIFY=1` runs.

### 7.5 `tx`

Inside `tx` (which re-runs on a conflict), these are compile errors:
- `send`, `publish`, `subscribe`, `unsubscribe` (E-S14, E-T7): a re-run would repeat their effect;
- a loop over a stream parameter (E-S13), because it waits on the client;
- streaming `fetch`, as `fetch` already is.

`for o: T in sql` inside `tx` is allowed: it runs on the transaction's connection, through a portal in the same transaction.

The "write after another statement, or in a loop" check of `src/sql.kh` treats each pass of a loop over a stream as a separate request (§2.2). The checker resets its per-request write state at the loop head of such loops, and nowhere else.

### 7.6 Tests: an in-process scheduler

`khc test` stays single-threaded. Streams opened by `open` run as coroutines on a test scheduler attached to the test's context.
- **`s.next()`** runs ready coroutines, delivers topic values synchronously (inboxes are drained after every coroutine step) and polls real fds (`fetch` to a mock, `sql`), until a value is queued for `s`.
- **It returns none** when s ended, or when every coroutine is parked on test-client input or subscriptions with nothing pending and no timer or fd is outstanding. That is the "nothing more would arrive" case, decided deterministically, without sleeps.
- **A 10 s guard** fails the test if a real fd never becomes ready.
- **Store and the database** are shared with the test, as `call` does today. The test's store lock is released while `next()` runs coroutines, and re-taken in exclusive mode afterwards, which mirrors `__call` (store-gc §6.8).

## 8. Semantics: TLS server

### 8.1 Certificates and keys

- **`TLS_CERT`** names PEM files holding the leaf first, then intermediates (the "fullchain.pem" of certbot and cert-manager). **`TLS_KEY`** names the matching private keys. Both take comma lists for SNI, and a value starting with `-----BEGIN` is the PEM text itself (secrets injected as environment variables).
- **Key formats:**
  - `PRIVATE KEY` (PKCS#8, RSA or EC P-256), `EC PRIVATE KEY` (SEC1, `prime256v1`) and `RSA PRIVATE KEY` (PKCS#1);
  - RSA keys of 2048–4096 bits.
- **Checks at start** (each failure stops the server with the message in §12.2):
  - the PEM parses;
  - the key type is supported;
  - the key matches the leaf: sign a test message and verify it with the leaf's public key;
  - each certificate is signed by the next;
  - the leaf has a SAN.
- **Warnings at start:** an expired or not-yet-valid leaf, a leaf expiring within 14 days, a root included in the chain (it is wasted bytes), and a key file readable by group or others.
- **Reload.** Every 60 s the files' mtimes are checked. When they change, the new pair is loaded and checked. On success it replaces the old pair atomically for new handshakes (each thread swaps at its next loop turn); on failure, the old pair stays and an error is logged. This covers renewal without a restart.

### 8.2 SNI and ALPN

- **SNI** selects the first certificate whose SAN matches the name: exact first, then `*.` wildcards one label deep, the same rules as `x509.kh __dns_match`. With no SNI, or no match, the first certificate is used. There is no `unrecognized_name` alert, because browsers would show an error instead of the default site.
- **ALPN:** h2 if offered, then http/1.1. With no ALPN, http/1.1. A client offering only unknown protocols gets the `no_application_protocol` alert.
- `METRICS_PORT` stays plain HTTP.

### 8.3 Handshake

**The state machine runs in the event loop**, with no coroutine per handshake. The states are WAIT_CH, then for mTLS WAIT_CERT and WAIT_CV, then WAIT_FIN, then DONE.

**ClientHello:**
- `supported_versions` must contain 0x0304, else a `protocol_version` alert. TLS 1.2 is not supported: modern clients all speak 1.3, and old ones stay behind a load balancer.
- **Key share.** X25519 is preferred, then P-256. If the client offered no usable share but supports a group, the server sends HelloRetryRequest with a cookie.
- **Cipher.** TLS_AES_128_GCM_SHA256 is preferred when AES-NI is present, unless the client lists ChaCha20 first (mobile clients without AES hardware); then TLS_CHACHA20_POLY1305_SHA256. TLS_AES_256_GCM_SHA384 is used when it is the only one offered.
- **Signature.** `ecdsa_secp256r1_sha256` for P-256 keys; `rsa_pss_rsae_sha256` (then sha384 or sha512 if the client prefers) for RSA keys.
- GREASE values are ignored. A ClientHello may span records, up to 16 KiB in total.

**Server flight, one write:**
- ServerHello, then a dummy ChangeCipherSpec when the client sent a legacy session id (middlebox compatibility, as the client already does);
- EncryptedExtensions (ALPN, `server_name` acknowledgement), then CertificateRequest for mTLS;
- Certificate (the chain), CertificateVerify, Finished.

**After the client's Finished:** NewSessionTicket (§8.4). Then the connection enters the HTTP/1.1 or HTTP/2 state machine on decrypted input.

**Records:**
- Input is decrypted in place in the input buffer, and the HTTP parser runs on the plaintext views.
- Output plaintext is encrypted into a separate ciphertext segment.
- Record size is dynamic, as in Go: about 1,400 bytes per record for the first 1 MB after idle (fast first byte), then 16 KiB.
- KeyUpdate: a request from the peer is answered; the server initiates one every 2^24 records per direction (the AES-GCM safety margin).
- `close_notify` is sent on a graceful close.

**Crypto, all constant-time where secrets are involved:**
- **X25519.** The Montgomery ladder with `cswap`, rewritten on a 4×64-bit field with `mulx` (BMI2) and `adcx`/`adox` (ADX) machine code, with a plain `mul` fallback.
- **ECDSA P-256 signing:**
  - a fixed-base comb over precomputed multiples of G (in DATA), read with masked loads over the whole table, never indexed by a secret;
  - field arithmetic specialised to p-256 (Montgomery with p's special form);
  - complete addition formulas (Renes, Costello and Batina, 2016), so there are no exceptional cases and no branches;
  - inversion modulo n by Fermat with a fixed window;
  - **nonces:** RFC 6979 HMAC-DRBG over the key and the hash, with 32 bytes from `getrandom` added as extra input (the "hedged" variant). A broken random number generator then cannot reveal the key, and a fault cannot repeat a nonce.
- **RSA-PSS signing:**
  - CRT, with two half-size modexps using 5-bit fixed windows and constant-time table gathers;
  - base blinding with a fresh r each time, `r^e · m`;
  - the signature is verified before it is sent: a fault in CRT would otherwise leak the factors (Lenstra's attack);
  - MGF1 with SHA-256, salt length 32, salt from `getrandom`.
- **Checking it.** Constant-time behaviour is tested statistically with dudect (Welch's t-test over fixed and random secret inputs, 10^6 runs per primitive, |t| < 4.5), and by inspecting the emitted machine code: no secret-dependent branches or indexes.

### 8.4 Session tickets: yes, with psk_dhe_ke; 0-RTT: no

- **Tickets.**
  - A ticket is AEAD(ticket key, resumption secret ∥ issue time ∥ cipher ∥ ALPN ∥ SNI ∥ client identity).
  - The ticket key is 32 random bytes per process, rotated every 12 h; the previous key is kept for decryption.
  - A ticket lives 24 h, with `ticket_age_add` as the RFC requires.
- **Resumption requires `psk_dhe_ke`.** An ECDHE exchange still runs (forward secrecy) and only the certificate and signature are skipped. That is the expensive part for RSA keys (about 1 ms) and a sizeable part for P-256.
- **Binders** are checked in constant time.
- **No 0-RTT.** No `early_data` is advertised in tickets. Replays of non-idempotent requests would need application knowledge, and API clients rarely send early data.
- **Scope.** Tickets work only on the process that issued them. Replicas do not share keys in v0.14.

### 8.5 mTLS (optional)

- With `TLS_CLIENT_CA` (PEM roots), the server sends CertificateRequest with `signature_algorithms` and `certificate_authorities` (the roots' subject DNs).
- **`TLS_CLIENT_AUTH`:**
  - `require` (the default): no certificate means the `certificate_required` alert;
  - `optional`: the connection proceeds without one, and `client_cert()` returns none.
- **Verification:**
  - the chain must lead to a `TLS_CLIENT_CA` root, reusing `__verify_chain` with no name check;
  - each certificate must be within its validity dates;
  - the leaf's extKeyUsage must include clientAuth, or there must be no extKeyUsage;
  - basicConstraints and nameConstraints are checked as for servers.
- **`client_cert() -> str?`** gives the leaf's identity: the first URI SAN (for example a SPIFFE id `spiffe://cluster/ns/x/sa/y`), else the first DNS SAN, else the first email SAN, else the subject CN. It is none without mTLS. It is documented in the server chapter, not in KHRIP.md.

### 8.6 Key storage

- A private key is parsed into a dedicated mmap region with `MADV_DONTDUMP` and `mlock` (best effort), never into store, arenas or the thread heap.
- The PEM text buffer is zeroed after parsing. On reload, the old key region is zeroed and unmapped.
- Signing scratch (nonces, blinding factors) lives on the event-loop stack and in that region, and is zeroed after use.
- There is no hardware module or KMS support: a key must be in a file or in an environment variable.

### 8.7 Not supported in v0.14

- **Protocol:** TLS 1.2; 0-RTT; OCSP stapling (Let's Encrypt ended its OCSP service in 2025, and browsers no longer need stapling); certificate compression (RFC 8879).
- **Keys and certificates:** P-384 and Ed25519 server keys; encrypted PEM keys (S-TLS3 gives the `openssl pkey` command to decrypt one).
- **Client side:** certificates for `fetch` (mTLS as a client).
- **Post-quantum key exchange:** the hybrid X25519MLKEM768 group, which Go 1.24 and current browsers offer by default. Browsers also send an X25519 share, so Khrip negotiates X25519 without a HelloRetryRequest. ML-KEM-768 is a later step (§20).

## 9. Semantics: HTTP/2

### 9.1 Connection setup

- **Over TLS:** ALPN `h2`.
- **Plain ports:**
  - the first 24 bytes are compared with the client preface `PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n` (h2c prior knowledge). This is what gRPC clients, Envoy, nginx `grpc_pass`, Cloud Run and service meshes use toward a backend;
  - anything else is HTTP/1.1.
- **No `Upgrade: h2c`:** RFC 9113 deprecates it, and it is a known request-smuggling vector.
- The server sends its SETTINGS (§9.3) and a WINDOW_UPDATE on stream 0 that raises the connection receive window to 1 MiB. Then it reads the client's SETTINGS, and acknowledges them.

### 9.2 Streams are requests

- **Framing, HPACK, flow control and stream states run in the event loop** of the connection's thread, in a per-connection `__H2` object (thread heap).
- **A client HEADERS that ends the header block creates a request:**
  - `:method`, `:path`, `:authority` and `:scheme` go into the `__Req` fields;
  - the other fields go into the header index (§3.6), so `header()` works unchanged;
  - the request then takes a coroutine from the same pool as HTTP/1.1, and runs `__serve_one` and dispatch unchanged.
- **Bodies:** DATA frames are appended to the stream's body block (arena memory reserved once the coroutine exists, or a pooled buffer before that).
  - Non-stream parameters dispatch at `END_STREAM`.
  - Stream parameters dispatch at HEADERS and receive items as DATA arrives.
- **Responses:**
  - `__write_response` produces HPACK-encoded HEADERS plus DATA frames into the connection's output queue, instead of an HTTP/1.1 head;
  - streams use the framing of §4.1 with DATA frame headers;
  - gRPC adds trailers.
- **Scheduling.** Each loop turn, streams with queued data and send window are served round-robin, up to the peer's `MAX_FRAME_SIZE` per frame, and the output is flushed once. There are no priorities: the server sends `SETTINGS_NO_RFC7540_PRIORITIES=1` and ignores PRIORITY frames, which RFC 9113 deprecates.

### 9.3 SETTINGS

| Setting | Value | Why |
|---|---|---|
| `HEADER_TABLE_SIZE` | 4096 (default) | Bounded decoder memory |
| `MAX_CONCURRENT_STREAMS` | 128 (`KHRIP_H2_STREAMS`) | Between Kestrel 100 and Go 250 |
| `INITIAL_WINDOW_SIZE` | 256 KiB | Upload throughput without large per-stream buffers |
| `MAX_FRAME_SIZE` | 16384 (default) | |
| `MAX_HEADER_LIST_SIZE` | 65536 | The same head limit as HTTP/1.1 |
| `ENABLE_CONNECT_PROTOCOL` | not sent | No WebSocket over HTTP/2 (RFC 8441) in v0.14; browsers fall back to HTTP/1.1 for WebSocket |
| `NO_RFC7540_PRIORITIES` | 1 | |

### 9.4 Flow control

- **Receive.**
  - Stream and connection windows are replenished as the application consumes bytes: for buffered bodies, when DATA is appended (up to `KHRIP_MAX_BODY`, then 413 and RST_STREAM); for stream parameters, when items are consumed. This gives backpressure to fast uploaders.
  - WINDOW_UPDATE is sent when half a window has been consumed, to batch updates.
- **Send.**
  - A stream sends while both its window and the connection window allow.
  - Queued bytes beyond the windows count toward `KHRIP_STREAM_QUEUE` (§4.2), so a peer that never opens its window is a slow client.
  - A window of zero with pending data for 30 s gives RST_STREAM(CANCEL) for that stream; a connection window of zero for 30 s gives GOAWAY.
- An overflow past 2^31-1 is FLOW_CONTROL_ERROR, as the RFC requires.

### 9.5 GOAWAY and RST_STREAM

- **GOAWAY from a client:** streams above its last-stream-id are not started; the connection closes when the active streams end.
- **Graceful shutdown:** as in §3.4.
- **A protocol error:** GOAWAY with the error code and the highest processed stream id, then close.
- **RST_STREAM from a client** cancels that stream's coroutine at its next wait (§3.3). The stream id is remembered as closed, so late frames get STREAM_CLOSED handling and are not treated as new streams.
- **The server resets a stream** on stream-level errors: oversize body, a malformed request (pseudo-header rules), or a stall.

### 9.6 Defenses

| Attack | Defense |
|---|---|
| **Rapid reset** (CVE-2023-44487): open and reset streams to make the server start work | Running handlers count against `MAX_CONCURRENT_STREAMS` until they actually end, not until they are reset. Excess streams wait in a per-connection queue bounded at 2× the limit. Client resets of unfinished streams are budgeted: more than 100 in 1 s, or more than half of the last 1,000 streams, gives GOAWAY(ENHANCE_YOUR_CALM) and close. |
| **CONTINUATION flood** (2024 CVE family): HEADERS without END_HEADERS, followed by endless CONTINUATION | The accumulated header block is bounded by `MAX_HEADER_LIST_SIZE` (64 KiB), with at most 32 CONTINUATION frames. Beyond that: GOAWAY(ENHANCE_YOUR_CALM) and close. HPACK is decoded incrementally as frames arrive, and nothing is buffered beyond the bound. |
| **HPACK bomb:** small input referencing large dynamic entries many times | The decoded size counts name + value + 32 per field. Past 64 KiB, decoding continues, counting lengths only to keep the table in sync, and the stream gets a 431 response. CPU stays linear in input bytes, because nothing beyond the limit is copied. |
| **Huffman abuse** | Table-driven decoder (a 4-bit FSM, 256 states); EOS in the data, or padding over 7 bits or not all ones, is COMPRESSION_ERROR. |
| **Dynamic table resizing abuse** | A size update above our SETTINGS is COMPRESSION_ERROR; a size update anywhere but the start of a block is COMPRESSION_ERROR. |
| **Control-frame floods** (PING, SETTINGS, WINDOW_UPDATE, PRIORITY, empty DATA, RST) | A control budget per connection: each such frame costs 1 and useful payload refills it. More than 10,000 without progress, or more than 1,000 per second, gives GOAWAY(ENHANCE_YOUR_CALM). |
| **Unread ACKs** | The output queue is bounded (`KHRIP_STREAM_QUEUE` per connection for control output); beyond it the connection closes. |
| **Slow reading, zero window** | §9.4 stall timers; queues bounded per stream. |
| **Stream id abuse** | Even ids from a client, non-increasing ids, HEADERS on a closed stream, or frames on idle streams are PROTOCOL_ERROR per RFC 9113. |
| **Malformed requests** | Upper-case field names; connection-specific fields (`connection`, `keep-alive`, `proxy-connection`, `transfer-encoding`, `upgrade`); `te` other than `trailers`; missing or duplicated pseudo-headers; pseudo-headers after regular fields; or `content-length` disagreeing with the DATA total. Each gives RST_STREAM(PROTOCOL_ERROR), or 400 where the stream can still answer. |
| **Header timeout** | HEADERS must complete within `KHRIP_HEADER_TIMEOUT`; the connection preface within 10 s. |

### 9.7 HPACK

- **Decoder:**
  - the static table (61 entries) as a DATA array;
  - the dynamic table as a ring of (offset, length) pairs into a 4 KiB byte ring;
  - Huffman by the FSM table (generated once into lib/hpack_tables.kh, as text_tables.kh is).
- **Encoder:**
  - a perfect hash over the static table: `:status` codes, `content-type` values;
  - incremental indexing for `content-type: application/json`, `text/event-stream`, `application/grpc`, `server: Khrip` and `grpc-status: 0`;
  - `date` as a literal with incremental indexing, re-indexed once a second;
  - other fields as literals without indexing.
- **A per-connection cache of whole encoded response heads** keyed by (status, content-type). After the first response, a typical JSON head is 3–5 bytes, and a gRPC trailer block is 1–2.
- **Huffman** is applied only when it is shorter, using precomputed code lengths.

### 9.8 HTTP/2 client in `fetch`

- **https.** ALPN offers `h2, http/1.1`. If the server picks h2, the connection becomes the thread's multiplexed connection for that origin.
- **Each fetch is one stream:**
  - the coroutine queues HEADERS and DATA and parks;
  - the connection reader (event loop) appends response frames to the stream's buffer and wakes it (`__co_notify`).
- **Client settings:** `ENABLE_PUSH=0`, `INITIAL_WINDOW_SIZE` 4 MiB, connection window 16 MiB.
- **Concurrency** is up to the server's `MAX_CONCURRENT_STREAMS`. Beyond it, the thread opens a second connection.
- **GOAWAY:** streams above the last id are retried on a new connection, because the server never processed them. That is safe for any method.
- **Idle connections** get a PING after 30 s; they are closed after 90 s idle or on a missing ACK.
- **http://** stays HTTP/1.1 (pooled), except for gRPC client stubs, which use h2c prior knowledge (§10.8).
- **`HTTPS_PROXY` tunnels** work unchanged: CONNECT first, then TLS with ALPN.

## 10. Semantics: gRPC, gRPC-Web, Connect

### 10.1 Names and messages

- **The package and service** come from `service a.b.C`, or else from the main file name: `shop.kh` → package `shop`, service `Shop`, so the path is `/shop.Shop/GetOrder`. A program with several files has one service per `service` declaration's file; files without one use the main file's.
- **The request message** for `rpc M (p1: T1, ..., pn: Tn)`:
  - a single struct parameter and nothing else: that struct type;
  - otherwise a generated `MRequest` with one field per parameter, in declaration order;
  - a stream parameter is the client stream's element type and does not appear in the message.
- **The response message:**
  - a struct result: the struct;
  - `[T]` gives `MResponse { repeated T items = 1; }`;
  - `str`, `int`, `float` and `bool` give `MResponse { ... value = 1; }`;
  - a map gives `MResponse { map<...> items = 1; }`;
  - no result (204) gives `google.protobuf.Empty`;
  - `stream T` makes `T` the stream element.
- **A REST binding** (`rpc M GET "/path/{id}" ...`) is exactly a route. Its JSON is today's route JSON (a bare array for `[T]`), not the Connect wrapper; Connect JSON follows the proto JSON mapping of the wrapper (`{"items": [...]}`).

### 10.2 Protobuf from Khrip types

| Khrip | proto3 | Notes |
|---|---|---|
| `int` | `int64` | Negative numbers take 10 bytes, as in every int64 proto |
| `float` | `double` | |
| `bool` | `bool` | |
| `str` | `string` | Must be valid UTF-8 on the wire (proto3 rule; INVALID_ARGUMENT otherwise, matching v0.13-utf8 D9) |
| `[T]` | `repeated T` | Packed for scalars |
| `map[K, V]` | `map<K, V>` | `V` that proto cannot hold (a list, an optional, a map) gets a generated wrapper message |
| `T?` | `optional T` | Explicit presence; `[T]?` and `map?` get a wrapper |
| struct | `message` | Spread fields are flattened, as in JSON |
| enum `A \| B \| C` | `enum E { E_UNSPECIFIED = 0; A = 1; B = 2; C = 3; }` | Reading 0 or an unknown number into `E` is INVALID_ARGUMENT `role: missing or unknown enum value`; into `E?` it is none. Proto's default-to-zero never silently becomes the first Khrip value, which would make a missing role read as `Admin`. |
| variants `Circle { r } \| Rect { w, h } \| Empty` | `message Shape { oneof value { Circle circle = 1; Rect rect = 2; Empty empty = 3; } }` with nested messages | The `type` tag of Khrip's JSON is the oneof case |
| field with a non-zero default (`page: int = 1`) | `optional` | Absent → the default; present 0 → 0 |
| other non-optional fields | implicit presence | Absent → zero value, as every proto user expects (S6 in §14.5) |

`json_name` is set to the Khrip field name, so proto JSON (Connect, grpc-gateway, other languages' JSON) uses the same snake_case keys as Khrip's REST JSON.

### 10.3 `app.proto`: the field-number lock

- **When it is written.** khc writes `<main>.proto` next to the main `.kh` file on `khc run`, `khc test` and `khc -o`, whenever it would change. `khc check` never writes. `khc proto --check app.kh` fails if the file would change; that is for CI.
- **The first time,** numbers follow declaration order.
- **Afterwards,** khc reads the file first:
  - an existing message keeps every number;
  - a new field takes the next unused number;
  - a removed field becomes `reserved N; reserved "name";`;
  - a new enum value takes the next number, and a removed one is reserved.

  So reordering fields in Khrip changes nothing on the wire.
- **Breaking changes are errors** (E-P1–E-P6): a type change of a kept field, a singular field becoming repeated or the reverse, a changed service or package name, an rpc changing its request or response type, or the file's own numbers conflicting.
- **Rename candidates are warnings** (W-P7): a field removed and a field of the same type added in one build. A rename keeps its number only if it is renamed in the file too.
- **The file is a normal `.proto`,** with `syntax = "proto3"`, the package, `option` lines for Go, C# and Java packages derived from the package, messages, enums and the service. It needs no imports except `google/protobuf/empty.proto` when used. Other languages generate their clients from it.

### 10.4 Status mapping

| Khrip | gRPC code | Connect HTTP status |
|---|---|---|
| 200/201/204 | OK | 200 |
| 400, 422 | INVALID_ARGUMENT | 400 |
| 401 | UNAUTHENTICATED | 401 |
| 403 | PERMISSION_DENIED | 403 |
| 404 | NOT_FOUND | 404 |
| 409 | ALREADY_EXISTS | 409 |
| 412 | FAILED_PRECONDITION | 412 |
| 429 | RESOURCE_EXHAUSTED | 429 |
| 499 | CANCELLED | 499 |
| 500, panic | INTERNAL (message `Internal Server Error`; the panic text is logged only) | 500 |
| 501 | UNIMPLEMENTED | 501 |
| 503 (database down, `sql` busy) | UNAVAILABLE, with `grpc-retry-pushback-ms: 1000` like `Retry-After` | 503 |
| 504, request deadline | DEADLINE_EXCEEDED | 504 |
| any other 4xx | FAILED_PRECONDITION | the same status |
| any other 5xx | UNKNOWN | the same status |
| `sql` errors | as their HTTP mapping (duplicate 409 → ALREADY_EXISTS, missing foreign key 404 → NOT_FOUND, …) | |

| undecodable message | INVALID_ARGUMENT `orders.v1.NewOrder.amount: wire type 2, expected varint` | 400 |

The `str` of `return 400 "..."` or `fail(403, "...")` is `grpc-message` (percent-encoded) or the Connect `message`. Rich error details (`google.rpc.Status.details`) are out of scope.

### 10.5 Deadlines, cancellation, metadata

- **`grpc-timeout`** (H, M, S, m, u and n units; at most 8 digits) becomes the coroutine's deadline (§3.3), capped by nothing else. So a client's 200 ms budget flows into `fetch` and `sql` in the handler.
- **Past the deadline,** the call is cancelled at its next wait and ends with DEADLINE_EXCEEDED. A handler that finishes late anyway also gets DEADLINE_EXCEEDED, because the client gave up.
- **`RST_STREAM(CANCEL)`** sets the cancel flag. So do a closed connection and a gRPC-Web client abort.
- **Metadata:**
  - request metadata is headers, read with `header(name)`; `-bin` values are returned as their base64 text;
  - `set_header` before the first message adds response headers (initial metadata);
  - trailers are only `grpc-status` and `grpc-message`. Custom trailing metadata is out of scope.
- **Compression.** `grpc-accept-encoding: identity` is advertised, so clients do not compress. A compressed message (flag 1) gets UNIMPLEMENTED `compression is not supported`.

### 10.6 Health and reflection

- **Health.** `grpc.health.v1.Health/Check` and `Watch` are always served. They report SERVING after the start checks, and NOT_SERVING while draining, for the empty service name and for the program's service. Kubernetes' native gRPC probes work with no code. The `.proto` for it is built in, not written to `app.proto`.
- **Reflection.** `grpc.reflection.v1.ServerReflection` (and `v1alpha` for older grpcurl) is on unless `KHRIP_GRPC_REFLECTION=0`.
  - It serves the `FileDescriptorProto` of `app.proto` and of the health service. khc serializes them at compile time into DATA, which costs a few KB.
  - `grpcurl list` and Postman work with no code. In Go and C# it is an explicit registration.

### 10.7 gRPC-Web and Connect

- **gRPC-Web** (`application/grpc-web`, `+proto`, and `application/grpc-web-text` in base64), over HTTP/1.1 or HTTP/2:
  - the same messages;
  - trailers are sent as a final length-prefixed frame with flag 0x80 holding `grpc-status:N\r\ngrpc-message:...\r\n`;
  - CORS per `KHRIP_CORS`, exposing `grpc-status` and `grpc-message`.
- **Connect unary:**
  - POST `/pkg.Svc/M` with `application/json` or `application/proto`, and optionally `Connect-Protocol-Version: 1` and `Connect-Timeout-Ms`;
  - success is 200 with the message;
  - an error has the HTTP status from §10.4 and the body `{"code":"not_found","message":"..."}`.
- **Connect server streaming:** `application/connect+json` or `+proto`; enveloped messages; an end-stream envelope (flag 0x02) with `{"error":{...}}` or `{}`.
- **Connect GET** (idempotent unary methods) and client or bidi streaming over Connect are out of scope; gRPC covers them.
- **The rpc handler is the same in all cases.** Only the codec and framing differ, so the AI writes nothing for browsers or `curl`:

  ```
  curl -H 'Content-Type: application/json' -d '{"id":1}' localhost:8080/shop.Shop/GetOrder
  ```

### 10.8 `.proto` import and client stubs

- **`khc proto quotes.proto [-o quotes.kh]`** writes:
  - Khrip types for the file's messages and enums (oneofs as variants, wrappers as `T?`, `google.protobuf.Timestamp` as `str` RFC 3339, `Empty` as no parameter or no result);
  - one bodiless rpc per method;
  - a `service` line.
- **Integer mapping.** `int32`, `uint32`, `sint*`, `fixed*` and `int64` map to `int`. For `uint64` and `fixed64`, a value above 2^63-1 is a decode error, with a note in the generated file.
- **`bytes` maps to `str` holding base64**, the proto JSON form, consistent with the MongoDB `binary` decision.
- **Refused** with a precise error (E-I1–E-I3): proto2, `Any`, `Struct`/`Value`, groups, extensions, and services with options that change the wire.
- **A stub** (`rpc GetQuote (sym: str) -> Quote at env("QUOTES_URL")`, its address evaluated at start) is called like a function: `let q = GetQuote("ACME")`.
  - The call runs over the h2 client (§9.8): h2c for `http://`, ALPN h2 for `https://`.
  - The deadline is `min(30 s, remaining request deadline)`, sent as `grpc-timeout`. Trace context is propagated.
- **Result typing follows `sql`.**
  - Into `T`: OK gives the value; NOT_FOUND ends the request with 404, so the route must list `| 404`, as E-R9 checks.
  - Into `T?`: NOT_FOUND gives none.
  - UNAVAILABLE and DEADLINE_EXCEEDED end the request with 503 and 504; other codes end it with their mapped HTTP status.
  - The result is never a silent default.
- **A server-streaming stub** is read with `for q in Prices("ACME") { }`.
- **There are no retries.** Hedging and retry policies are out of scope.

### 10.9 Codec performance

- **Decoding is table-driven.** khc emits, per message, a table into DATA: (field number → kind, field offset, child descriptor, packed flag). It is indexed directly for numbers below 64, and searched in sorted order above that. The decoder uses the same descriptors that JSON and store copying use, plus the table, and runs one loop for all messages, as upb does.
- **Strings are zero-copy:** `str` views point into the received frame, as JSON strings point into the request buffer. UTF-8 is validated with the SIMD validator.
- **Encoding writes backwards** from the end of a reserved block: the fields of a nested message are written first, and its length prefix is then known. There is no size pre-pass and no 5-byte padded lengths. Tags are pre-encoded per field in the table.
- **Varints:** decoding has a fast path for one and two bytes and a branch-reduced path for up to ten; encoding uses `lzcnt` to find the length.

## 11. HTTP/3: left to the edge

**Decision:** Khrip does not implement QUIC or HTTP/3. Clients that speak HTTP/3 reach Khrip through the component that already terminates TLS at the edge, and it speaks HTTP/1.1 or HTTP/2 to Khrip. That component is a CDN (Cloudflare, Fastly, CloudFront, Google Cloud CDN) or a proxy (Envoy, nginx, HAProxy, Caddy).

**Why:**
- **Where HTTP/3 helps, Khrip is not.** QUIC's gains are on lossy, high-latency last-mile links: no TCP head-of-line blocking, connection migration across networks, 0-RTT. A backend sits behind a load balancer on a data-center network with sub-millisecond RTT and negligible loss, where those gains are close to zero.
- **It costs CPU, which breaks rule 1.** QUIC runs in user space: per-packet AEAD and header protection for ~1.2 KB packets, ACK processing, loss recovery, and congestion-control and pacing timers.
  - Even with UDP GSO/GRO, published comparisons show HTTP/3 behind HTTP/2 over fast links: up to about 45% lower throughput, with receive-side packet processing as the cause (Zhang et al., "QUIC is not Quick Enough over Fast Internet", WWW 2024).
  - Operators report CPU per byte above TCP+TLS.
  - A Khrip HTTP/3 backend would lose the CPU and throughput comparisons that HTTP/2 can win.
- **It is big.** Production QUIC stacks are 40–100k lines (quic-go, quiche, msquic). Khrip would need the transport, TLS 1.3 over QUIC (key schedules exist; the record layer differs), QPACK, HTTP/3 framing, CUBIC or BBR with pacing, path validation, stateless reset, retry tokens against amplification, and 0-RTT anti-replay. That is an estimated 12–18k Khrip lines, plus continuous interop testing (quic-interop-runner), for a feature the deployment edge already provides.
- **It needs nothing in programs:** no tokens either way.

**What would change the decision:**
1. Evidence from users or the eval that Khrip programs face clients directly over lossy networks at scale with no proxy, such as IoT or mobile game backends.
2. An in-kernel QUIC socket in Linux with user-space handshake offload. An upstream series has been posted since 2024; it would be adopted the way kTLS is, at small cost.
3. WebTransport (bidirectional browser streams beyond WebSocket) becoming a common requirement in backend tasks.
4. A measured user-space QUIC within 1.2× of TCP+TLS CPU per request on backend workloads.
5. Load balancers that speak HTTP/3 to origins becoming the default. None do in 2026.

Until then, `Alt-Svc` stays the edge's job, and Khrip does not advertise HTTP/3.

### 13.3 What makes Khrip faster here

1. **Serialize once.** A topic value is encoded once per wire format into a shared, reference-counted frame block, and WebSocket frames are built once (server frames are unmasked). gorilla, Kestrel and Node hub code encode per subscriber.
2. **No per-subscriber code.** A subscription is a runtime forward. A delivery is one queue append and a share of one `writev`, with no coroutine wake-up and no goroutine or task per client.
3. **Per-thread fan-out.** There is one cross-thread hop per thread with subscribers, through an MPSC inbox and an `eventfd` coalesced per loop turn. Subscriber tables are thread-local and need no locks.
4. **Zero-copy framing.** Values are JSON-encoded straight into output segments behind reserved prefix space (WebSocket header, chunk size, HTTP/2 frame header, gRPC prefix). Incoming WebSocket frames, NDJSON lines and protobuf messages are parsed in place, and strings are views.
5. **SIMD where bytes are touched:** WebSocket unmasking (AVX2, 32 B per step), UTF-8 validation (v0.13 validator), JSON structural scanning for array splitting, header scanning (existing).
6. **Memory per connection close to the protocol state.** Pooled buffers, parking without an arena (an exact-size 1.3 KB snapshot) and subscribed-only streams with no frames. Fewer touched pages also mean fewer cache and TLB misses under load.
7. **One `writev` per connection per loop turn,** batching all queued frames, HTTP/2 control frames and TLS records.
8. **HPACK for servers:** a static perfect hash, indexed common values, and a cached encoded response head per connection, so a typical head is 3–5 bytes after the first.
9. **A table-driven protobuf codec with a backward writer:** no size pass, pre-encoded tags, zero-copy strings.
10. **Timers in a wheel,** O(1) per connection, instead of 100k entries in a heap.
11. **Crypto in compiler-emitted machine code** with BMI2/ADX and AES-NI/PCLMULQDQ (§13.4), and kTLS for transmit as a measured option (`KHRIP_KTLS=1`, AES-GCM only; default off until it wins P-T3).
12. **No proxy hop.** Built-in TLS and HTTP/2 remove the sidecar (Envoy or nginx) that Go and C# deployments often add for HTTP/2, gRPC-Web or mTLS. That is a whole process of CPU and latency per request.

|---|---:|---|
| X25519 | ≤ 60 µs | 4×64 field with `mulx`/`adcx`/`adox`; dedicated squaring; ladder unrolled |
| P-256 fixed-base mult | ≤ 40 µs | Comb with a 64 × 16-entry table of G multiples; complete formulas; masked full-table loads |
| ECDSA P-256 sign | ≤ 50 µs | The base mult, plus inversion mod n with a fixed window and HMAC-DRBG |
| RSA-2048 PSS sign | ≤ 1.2 ms | CRT; 1024-bit Montgomery with 16 limbs, unrolled; 5-bit windows |
| AES-128-GCM | ≥ 2.5 GB/s | 4–8 block interleave; GHASH with 8 precomputed powers and aggregated reduction; VAES/VPCLMULQDQ path when present |
| ChaCha20-Poly1305 | ≥ 1.2 GB/s | AVX2 8-way ChaCha; 64-bit-limb Poly1305 |
| Full server handshake, P-256 key, X25519 | ≤ 200 µs CPU | Above, plus HKDF and transcript hashing (SHA-NI path where present) |

The precise Go and OpenSSL figures are measured on the same machine as part of P-T1, not quoted.

The handshake target is set so that P-T1 (≥ Go per core) holds with margin. If the measured Go number is higher, the gate stands and the step continues; the targets above are the plan, not the gate.

### 13.5 Measurement rules

- Every scenario is in `bench/protocols/run.sh`, with a TSV of raw rows like the interim report, and a report in `bench/results/`.
- A claim of "faster" needs the gate ratio on three runs on an idle machine.
- If a gate fails, the stage does not close. The report says by how much and where the time goes, using `perf stat` and `perf record`, as the v0.11 TLS work did with P-384.

## 14. Rule 2 evidence

### 14.1 The programs

**The specifications.** All four languages implement the same behaviour.
- **P1, LLM token streaming over SSE.**
  - `POST /chat {prompt}` gives 400 when the prompt is empty.
  - It calls an OpenAI-compatible endpoint with `stream: true` and forwards each content delta as an SSE event `{"text": ...}`.
  - A non-2xx upstream status gives 502.
  - A client that disconnects must stop the upstream.
- **P2, chat rooms over WebSocket.**
  - `GET /rooms/{room}/ws?user=` (400 without a user).
  - On connect, the last 100 messages of the room are sent; then the client gets live messages.
  - An incoming `{text}` of 1–500 characters is stored (keeping the last 100 per room) and broadcast to the room as `{user, text, at}`.
  - `GET /rooms/{room}/messages` returns the history.
- **P3, an Orders gRPC service on PostgreSQL.**
  - `CreateOrder` gives INVALID_ARGUMENT on bad input; `GetOrder` gives NOT_FOUND; `ListOrders` streams a customer's orders from the server.
  - The schema is created at start; health and reflection are on.
- **P4, the same Users API as REST and gRPC.**
  - Create: 400 on a bad email, 409 on a duplicate. Get: 404. List: with a limit, default 20. Delete: 404.
  - Data is in memory.

**Khrip.** The Go, C# and Python files are listed in Appendix A. All of them compile, as the introduction says.

P1 (`progs/p1/khrip/main.kh`):

```khrip
type Ask { prompt: str }
type Msg { role: str, content: str }
type ChatReq { model: str, messages: [Msg], stream: bool }
type Delta { content: str? }
type Choice { delta: Delta }
type Chunk { choices: [Choice] }
type Token { text: str }

const URL = "https://api.openai.com/v1/chat/completions"

route POST "/chat" (body: Ask) -> stream Token | 400 str {
    if body.prompt == "" {
        return 400 "prompt is required"
    }
    let key = env("OPENAI_API_KEY") ?? ""
    let req = ChatReq { model: "gpt-4o-mini", messages: [Msg { role: "user", content: body.prompt }], stream: true }
    for data in fetch POST URL req headers {"Authorization": "Bearer {key}"} {
        let c: Chunk? = from_json(data)
        if c != none && c.choices.len() > 0 {
            if let t = c.choices[0].delta.content {
                send(Token { text: t })
            }
        }
    }
}
```

P2 (`progs/p2/khrip/main.kh`):

```khrip
type Say { text: str }
type Line { user: str, text: str, at: int }

store rooms: map[str, [Line]]
topic chat: Line

route GET "/rooms/{room}/ws" (room: str, user: str, msgs: stream Say) -> stream Line | 400 str {
    if user == "" {
        return 400 "user is required"
    }
    if !subscribe(chat[room]) {
        for l in rooms[room] ?? [] {
            send(l)
        }
    }
    for m in msgs {
        if m.text == "" || m.text.len() > 500 {
            continue
        }
        let line = Line { user, text: m.text, at: now() }
        var list = rooms[room] ?? []
        list.push(line)
        rooms[room] = list[list.len() - 100..]
        publish(chat[room], line)
    }
}

route GET "/rooms/{room}/messages" (room: str) -> [Line] {
    return rooms[room] ?? []
}
```

### 14.5 Remaining places for a silent mistake

Silent means: it compiles, starts, passes a quick test, and is wrong under real use.

**Khrip, with this design:**

| # | Mistake | Why the design does not stop it | Mitigation |
|---|---|---|---|
| S1 | Several replicas behind a load balancer: broadcasts reach only the clients on the same process | Topics are per process (decision 21) | Start-up log line under Kubernetes; `topic ... shared` through `LISTEN/NOTIFY` (§20) |
| S2 | A writer waits between the store write and `publish` (`rooms[id] = ...; fetch ...; publish(...)`), so a subscriber may get a value both in its history and live | Atomicity holds only without a wait in between (§6.2) | Candidate warning: `publish` of a value written to store earlier in the route, with a wait in between |
| S3 | SSE history sent without `if !subscribe(...)`: a reconnecting client gets history again plus the replay | `subscribe`'s result may be ignored | The KHRIP.md idiom; candidate warning for a stream route that sends store values after an ignored `subscribe` result |
| S4 | A write in a stream route before a client leaves completes, the rest does not | Cancellation at waits (§3.3) is the price of no `async` | `tx` around multi-statement writes (already required for `sql`) |
| S5 | Mid-stream upstream errors in an LLM stream (an `{"error":...}` event) decode as a chunk with no choices and are skipped: a truncated answer | `from_json` into `T?` gives none for it | Same in all languages; the program can also decode an error type |
| S6 | A required protobuf field missing on the wire reads as zero (`amount: 0`) | proto3 semantics (§10.2); JSON and REST are stricter | Validation in the handler, as in Go and C# |
| S7 | Credentials revoked after a WebSocket connected stay valid for the connection's life | Checked once at connect, in every language | Re-check per message in the loop; a forced close by topic is out of scope (§5.6, §20) |
| S8 | A token in the WebSocket query string ends up in proxy logs | Browsers cannot set WebSocket headers | Khrip never logs query strings; proxies are outside its control |
| S9 | `app.proto` deleted and regenerated: numbers follow declaration order again, and clients break | The lock is a file | Docs; `khc proto --check` in CI catches it only if the file is in version control |
| S10 | A field renamed in Khrip but not in `app.proto`: values from old clients are dropped | Name-keyed lock | W-P7 warning |
| S11 | A value read from store before the message loop is a snapshot inside the loop | Copy semantics of outer variables (§7.1) | KHRIP.md sentence; read store inside the loop |
| S12 | A per-connection map that only grows hits `KHRIP_STREAM_STATE` after hours | Exact frees cover overwrites, not growth | A loud close (R-S3), not silent; still a production surprise |
| S13 | A slow consumer with a big queue is closed and loses messages that are no longer in the replay ring | Bounded memory over unbounded queues | Logged (R-S2); SSE resume covers the last 64 |

**These are loud now, and were silent in at least one of the Go, C# or Python programs:**
- **Cancellation:** the forgotten upstream cancellation (Go without `r.Context()`, C# without `[EnumeratorCancellation]`).
- **SSE plumbing:** `bufio.Scanner` silently stopping at its line limit, because `sc.Err()` is unchecked (Go P1 raised the limit to 1 MiB, and still stops silently beyond it); SSE stopping behind a logging middleware that wraps the writer without `Flush`, a trap the Go production add-on has to avoid by hand.
- **Broadcast:** a slow client stalling a room (Python P2's sequential `await`s); goroutine leaks and double-close panics in hub code (Go P2's close-once logic is easy to get wrong); messages silently dropped when a bounded channel is full and the `TryWrite` result is ignored (C# P2 checks it and disconnects the client, as Khrip does).
- **History and live:** the race between them (Python P2 joins, then awaits between history items, so live messages interleave with the history out of order; SignalR's join and history race).
- **WebSocket framing:** messages over 4 KB or fragmented messages silently ending the C# P2 connection (`!EndOfMessage` → break); C#'s `Text.Length` counting UTF-16 units instead of characters.
- **Origin:** cross-origin WebSocket accepted (Node `ws` and Python by default).
- **REST through gRPC transcoding:** `int64` ids rendered as JSON strings (`"id":"1"`) by grpc-gateway and JSON transcoding (Go P4, C# P4), and create answering 200 instead of 201. Khrip's REST stays numbers and 201.
- **Error details:** database error text leaking to clients in `codes.Internal` (Go P3).
- **Deploys:** Python P4 not stopping its gRPC server gracefully on SIGTERM.
- **Missing defenses:** no header timeout (Go defaults), no body limit (Go, Node), no message size limit (FastAPI WebSocket 16 MB by uvicorn's default; Go P2 sets 4 KB by hand).

## 18. Eval tasks to add, and the promotion gate

The tasks follow `eval/PROMPT.md`:
- the same prompt per language;
- `{RULES}` for Khrip is KHRIP.md with this design's additions, plus GRPC.md for gRPC tasks;
- two attempts with compiler or check output;

| Task | Exercises | Checks (`check.sh`) |
|---|---|---|
| `llm-proxy` | P1-like proxy with a mock upstream (given), plus a per-user daily token budget in store | Token order; 400 and 502; disconnect stops the upstream (the mock counts open streams); budget enforced across concurrent streams |
| `import-ndjson` | NDJSON upload into PostgreSQL with per-line validation; a report of bad lines | 1M lines in bounded RSS; the line numbers of errors; `tx` per batch |
| `chat-ws` | P2 plus `/rooms/{room}/members` (counts) and a kick | Two clients see the same order; reconnect gets history with no gap or duplicate; a slow client does not delay others; 1 MiB message limit; cross-origin refused |
| `feed-sse` | Notifications with topics per user, and `Last-Event-ID` resume | Resume replays exactly the missed events; no duplicates when the idiom is used; heartbeats through a proxy with a 30 s idle timeout |
| `orders-grpc` | P3 plus `UpdateStatus` with optimistic concurrency and a bidi `Watch` | Checked by a Python grpcio client: codes, deadlines (a slow `pg_sleep` method), streaming order, reflection lists the service, health while draining |
| `users-rest-grpc` | P4 plus pagination and PATCH | REST and gRPC see the same data; REST ids are numbers; 201 on create |

**Languages and libraries** are fixed as in §13.1: Go (gorilla/websocket, grpc-go, grpc-gateway), C# (Kestrel, Grpc.AspNetCore, JSON transcoding), Python (FastAPI, grpcio). Project files are given.

**Promotion gate for each KHRIP.md part** (as for the drivers section):
1. **Tokens.** Go/Khrip ≥ 2.5 and Python/Khrip ≥ 1.3 on the tasks the part serves, counting spec tokens at cached-input price.
2. **First try.** Khrip's first-try pass rate is at least its rate on the PostgreSQL tasks.
3. **Silent failures.** `check.sh` finds no more silent failures in Khrip solutions than in the best other language.
4. **Cost to other tasks.** On the 11 existing tasks, the added spec does not lower Khrip's first-try pass rate.

If the streams section passes 1–3 but fails 4, it moves to STREAMS.md behind the 82-token pointer (+408 total).

## 20. Deliberately out of scope, and risks

| Item | Why not now | How it would fit |
|---|---|---|
| HTTP/3, QUIC, WebTransport | §11 | The triggers of §11; kernel QUIC like kTLS |
| WebSocket over HTTP/2 (RFC 8441) | Browsers fall back to HTTP/1.1; low value | `SETTINGS_ENABLE_CONNECT_PROTOCOL`, an extended CONNECT stream feeding the same message loop |
| permessage-deflate | §5.5 | `KHRIP_WS_DEFLATE=1`, no context takeover, shared compressor |
| WebSocket subprotocols and binary messages | No `bytes` type; protocols like graphql-ws are rare in backends | A `protocol` clause on the route; `stream bytes` with a future bytes type |
| Concurrent handling of messages on one connection | Order and simplicity; TCP pushes back | An explicit opt-in clause if an eval task needs it |
| Closing other connections from code (a "kick user X") | Needs topic values that end a parked stream, or connection handles as values | `subscribe(kick[uid], close)`: a delivery on that channel closes the stream with 4401 |
| Topics across processes | Needs a broker | `topic chat: Line shared` over `LISTEN/NOTIFY` (payloads up to 8,000 bytes; larger values travel as ids); later Redis or NATS |
| Durable topics, queues, Kafka-like logs | A different problem (outbox, consumer offsets) | The ROADMAP's "Kafka (outbox)" item after 1.0 |
| TLS 1.2, 0-RTT, OCSP stapling, certificate compression | §8.7 | — |
| P-384 and Ed25519 server keys | Constant-time code for each curve; P-256 and RSA cover Let's Encrypt and most CAs | The same comb code with P-384 field code |
| Post-quantum hybrid key exchange (X25519MLKEM768) | ML-KEM-768 in constant time is its own piece of work (NTT, sampling, about 1.5 KB key shares); clients that offer it also offer X25519 | A group in the key-share preference list ahead of X25519, as Go 1.24 does by default |
| mTLS as a client (certificates for `fetch`) | Not in the stage list | `FETCH_CERT`, `FETCH_KEY` variables |
| Session ticket keys shared across replicas | Needs a shared secret and rotation | `TLS_TICKET_KEY` (a file) |
| h2c Upgrade, server push, priorities | Deprecated or harmful | — |
| gRPC compression, custom trailers, rich error details, retries and hedging, xDS, load-balancing policies | Rarely needed in the eval scope; each needs surface | `fail` with a details value; client policies in `at` |
| Connect GET, Connect client and bidi streaming over HTTP/1.1 | gRPC covers them | Codec variants |
| Several services per file | One `service` per file keeps naming simple | Already possible across files |
| OpenTelemetry span export (OTLP), log sampling | Trace ids and logs cover correlation; exporters belong to the collector | An OTLP exporter on the control thread |
| OpenAPI from routes | Separate item in DESIGN.md | It would also document REST bindings of rpcs |
| io_uring | epoll with batched `writev` meets the gates on paper | Measure after stage B; it would replace `writev` per connection with a submission batch |
| A `bytes` type | Language-wide | Binary WebSocket, protobuf `bytes`, file uploads |
| Server-side `Alt-Svc` | Edge's job | — |

**Risks** are in §15.4. The largest:
- the constant-time crypto (correctness and speed);
- the keep-heap barrier completeness;
- parking without an arena.

Each has its own step and gate before anything depends on it.
