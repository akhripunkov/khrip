# Khrip v0.14–v0.16: protocols — production server, streams and SSE, WebSocket and topics, HTTP/2 and gRPC, TLS server

Revision 2 (2026-10-25). It answers the independent critique (`scratchpad/proto/critique.md`) and the lead's decisions D1–D7 (`docs/design/v0.13-status.md`, commit `6a370dd`). Section 22 has one row per critique item. Section 23 lists what the owner must decide. The first revision is kept as `v0.14-protocols.r1.md`.

**Scope, in the order of the work:**
- **v0.14**: the production server (bodies, limits, timeouts, deadlines, graceful shutdown, logs, metrics, trace ids, CORS), streams and Server-Sent Events, WebSocket and topics. A memory-model spike comes before the streams code.
- **v0.15**: HPACK, the HTTP/2 server (h2c), gRPC, Connect and gRPC-Web, over HTTP/1.1 and h2c.
- **v0.16**: the TLS 1.3 server (ECDSA P-256), the HTTP/2 client in `fetch`, `.proto` import and gRPC client stubs.
- **HTTP/3** stays at the edge (§13).

**The owner's two rules, as this document applies them:**
- **Rule 1.** Every performance gate reads "at least as good as the best of Go, C#, Java, Node/Bun and Python, on the same run, at the same offered load" (§15). Crypto gates read "within 10% of OpenSSL on the same run", or an explicit exception from the owner (§23).
- **Rule 2.** A task costs the tokens the model reads (prompt) plus the tokens it writes (program). This document reports both, per task (§16). Khrip loses one of the four protocol programs, and it loses every task when prompt tokens are priced uncached. §16.3 states this and what would change it.

**What was measured, not argued:**
- **Programs.** Four evidence programs in Khrip, Go, C#, Python and TypeScript, plus the SDK-based Python and TypeScript versions of the LLM proxy. Every competitor builds or type-checks (§16.1).
- **Prompt texts.** Written in full and counted with `bench/tokens/spec_tokens.mjs` (§4).
- **Memory.** Per-connection memory measured on today's runtime and on four competitors (§2).
- **OpenSSL.** Measured on the bench machine (§15.5).
- **Anonymous types.** The proposal of Appendix A, applied mechanically to the 11 eval solutions and by hand to the four programs.

Nothing in `/home/user/khrip` was modified. Scratch files are listed in Appendix B.

## 0. Decisions in brief

**Order (§1).**
1. No protocol code starts before the work the lead put first:
   - the v0.13 GC;
   - a memory stage (peak RSS ≤ Go on every eval scenario);
   - a codegen stage (catalog and bookings ≥ C#);
   - a tokens stage (Appendix A, and a prompt split into a core and chapters), followed by the blind eval;
   - the 0.13.0 release.
2. The versions are split as follows:
   - **v0.14** is the production server, streams and WebSocket, with a memory-model spike as step 6;
   - **v0.15** is h2c and gRPC;
   - **v0.16** is TLS and the HTTP/2 client.

**Production server (v0.14, §5).**
3. One event-loop core per thread for every protocol, with pooled buffers.
4. Bodies:
   - bodies up to 64 KiB are still buffered by the event loop before a coroutine is taken;
   - larger ones are read by the coroutine, at a minimum data rate;
   - chunked bodies are accepted under strict anti-smuggling rules.
5. Timeouts on by default. The request deadline covers the work **before the response starts** (B1).
6. Graceful shutdown always, sized to fit the Kubernetes 30 s grace period.
7. JSON request logs, Prometheus metrics, health endpoints and W3C trace ids, all without code.
8. A process-wide memory budget (`KHRIP_MEMORY`) sheds load before the per-connection limits multiply.

**Streams (v0.14, §6–§9).**
9. One type constructor, `stream T`, and one function, `send(v)`:
   - the route's result is SSE, NDJSON or a gRPC/Connect stream, as the client asks;
   - a GET with Upgrade makes it a WebSocket;
   - there is no streamed JSON array.
10. **Four loop kinds** have per-item memory:
    - a WebSocket or bidi **message loop**;
    - a POST or client-stream **body loop**;
    - a **fetch loop**;
    - a **row loop** over streamed `sql`.

    A pass's garbage is dropped at the end of the pass. Survivors move into an **owner region** by copying with forwarding, so sharing is preserved and the copy is invisible to the program (R4). The only visible rule: `store` values read before such a loop are snapshots inside it.
11. **The end of each pass is the end of a unit of work.** The store lock is released for good there and taken again only at the next store access (P4). A token stream that does not touch store takes no lock.
12. **A parked message loop holds no coroutine, arena or lock.** Every context word has a stated owner (§9.3, B3).
13. **`subscribe(t, history)`** sends the history, or only what a reconnecting SSE client missed, then the live values. The history and the live values neither overlap nor leave a gap (M3).
14. Topics are ordered with store (the lock is taken in the route's own mode, B2), have at-most-once delivery, are serialized once, and close slow clients loudly.

**HTTP/2 and gRPC (v0.15, §10–§11).**
15. h2c prior knowledge and the gRPC/Connect/gRPC-Web codecs over HTTP/1.1 and h2c.
16. Every HTTP/2 denial-of-service defense of §10.4 is a gate of its step:
    - rapid reset, MadeYouReset (CVE-2025-8671) and data dribble (CVE-2019-9511);
    - CONTINUATION floods and HPACK bombs;
    - field-value rules.
17. `rpc Name [METHOD "path"]`, with protobuf derived from types and field numbers locked in `<main>.proto`.
18. Required fields are `optional` on the wire and checked (M4).
19. Errors map to gRPC codes by SQLSTATE (C6).
20. Reflection is off on the public port (S9).

**TLS and the client (v0.16, §12).**
21. A TLS 1.3 server with **ECDSA P-256 keys only** (RSA signing later):
    - field arithmetic transcribed from fiat-crypto;
    - RFC 6979 nonces;
    - a constant-time variable-base multiply for ECDHE;
    - AESKEYGENASSIST key expansion;
    - ctgrind-style tests.
22. Signing runs off the event loop.
23. Records go through kTLS when the kernel has it, and through our AES-GCM otherwise.
24. No session tickets and no ChaCha20 AVX2 in v0.16.
25. `fetch` speaks HTTP/2.
26. gRPC stubs map upstream codes to 404, 503, 504 or 502, never to 401 or 403 (S4).
27. TLS and HTTP/2 code is linked into every server; a `--no-tls` build refuses to start when `TLS_CERT` is set (D7).

**Prompt (§4).**
28. The core prompt gains 49 tokens. Streams, WebSocket and topics are a 451-token chapter, so a streaming task reads exactly +500. gRPC is a 655-token chapter. The SQL chapter gains 37 tokens.

## 3. Surface: what the AI sees

**New words** (all contextual, so existing identifiers keep working):
- the type constructor `stream T`;
- the top-level declarations `topic`, `rpc` and `service`;
- the functions `send`, `subscribe`, `unsubscribe`, `publish` and `client_cert`;
- `open` in tests.

**Extended forms.** `fetch` gains a `for` form and a `timeout` clause, and `for` gains an optional typed variable.

**Everything else is environment configuration,** with zero tokens in programs.

### 3.1 Server streams: `-> stream T` and `send`

```khrip
route POST "/chat" (body: Ask) -> stream Token | 400 str {
    if body.prompt == "" {
        return 400 "prompt is required"     // a real 400: nothing has been sent
    }
    send(Token { text: "..." })             // the response starts here
}
```

- **Where `stream T` may appear:** only as a route or rpc result (the 200 variant), or as one route or rpc parameter (§3.2). It is not a value: it cannot be stored, passed, returned or compared.
- **Where `send(v)` may appear:** only lexically in the body of a route or rpc whose result is `stream T`, with `v: T`.
- **The other variants** are the statuses available before the stream starts.
- **The format is picked by the request:**

  | Request | Response |
  |---|---|
  | GET with `Upgrade: websocket` | a WebSocket: one text message per value |
  | `application/grpc*`, `application/grpc-web`, `application/connect+json\|proto` | a gRPC, gRPC-Web or Connect stream |
  | `Accept` containing `application/x-ndjson` or `application/jsonl` | NDJSON |
  | `Accept` containing `text/event-stream` or `*/*`, or no `Accept` | SSE |
  | an `Accept` with none of these (for example only `application/json`) | **406** `this route streams: accept text/event-stream or application/x-ndjson` |

  Every stream response carries `Vary: Accept`.
- **No streamed JSON array (C3).** Clients that send `Accept: application/json` (axios, many SDKs) would wait forever on an endless stream.
- **`stream str`** sends text: SSE `data:` lines, raw chunks, WebSocket text messages, or JSON strings in NDJSON.

### 3.2 Stream parameters and the four loop kinds

```khrip
route GET "/rooms/{room}/ws" (room: str, user: str, msgs: stream Say) -> stream Line {
    for m in msgs { ... }                    // message loop: one WebSocket message at a time
}

route POST "/import" (rows: stream NewOrder) -> Summary | 400 str {
    var n = 0
    for r in rows {                          // body loop: NDJSON lines or array elements
        tx { sql "INSERT INTO orders {r}" }
        n += 1
    }
    return Summary { inserted: n }
}
```

**Stream parameters:**
- A route has at most one `stream T` parameter, and no other body parameter.
- **GET** makes the route a WebSocket. Its result must be `stream T` (E-S17). A plain GET without `Upgrade` gets 426 (C5).
- **POST** reads the body as NDJSON, as a JSON array split into elements, or, for `stream str`, as lines.
- In an `rpc`, a stream parameter is a client stream, or a bidi stream when the result is a stream too.
- **The parameter is read only by a `for` directly in the route body**, not inside another loop, `if`, `match` or `tx` (E-S18, R3). A second such loop later continues where the first stopped. A `break` stops reading.

**The four loop kinds** (named in the diagnostics and the docs, M6):

| Kind | Form | Pass | Owner of the survivors (§9.1) |
|---|---|---|---|
| **Message loop** | `for m in p`, where `p` is the stream parameter of a WebSocket GET or a bidi rpc | one client message | the connection |
| **Body loop** | `for r in p`, where `p` is the stream parameter of a POST or a client-stream rpc | one body item | the request |
| **Fetch loop** | `for x in fetch ...` | one SSE `data` payload or one line | the request, or the current message |
| **Row loop** | `for o: T in sql "..."` | one row | the request, or the current message |

In all four, each pass starts with fresh memory, and a `store` value read before the loop is a snapshot inside it (§9.1, warning W-S1). The `sql` rules differ by kind (§9.7, M5):
- **in a message loop,** each message is its own request, so one write outside `tx` is allowed per message;
- **in a body loop,** a write needs `tx { }` (E-Q4), and an error after committed items says how many were saved;
- **in a row loop,** no other `sql`, `fetch` or wait is allowed, except `send` (E-Q5).

### 3.3 Topics

```khrip
topic chat: Line                          // top level, like store

publish(chat[room], line)                 // from any route, rpc, every-block or function
subscribe(chat[room], rooms[room] ?? [])  // in a stream route: history, then live values
unsubscribe(chat[room])
```

- **Declaration.** `topic name: T` declares a family of channels carrying `T`. `name[key]` takes a `str` or `int` key, and `name` alone is the channel with the empty key. A topic is not a value.
- **`publish(t, v)`** never waits.
- **`subscribe(t, history)`** is allowed in a stream route whose element type is `T`. `history` is any `[T]` and may be omitted. The call does three things:
  1. it registers the subscription;
  2. it evaluates `history` and queues it, or, for an SSE client whose `Last-Event-ID` is still in the channel's replay ring, it queues only the values that client missed (§6.4);
  3. from then on it forwards every value published to `t`, in publish order, until the client leaves or calls `unsubscribe(t)`.

  The stream stays open after the route returns while it has subscriptions.
- **Exactness.** With a history read from `store` and no wait inside the history expression, nothing is lost or repeated (§8.2). A history read with `sql` may repeat values committed while the client subscribes, but never loses any.
- **Locking (B2).** `publish`, `subscribe` and `unsubscribe` take the store lock in the route's own mode (`__store_lock()`, the same call `store_touch` makes) when the program has a store, and no lock when it has none.

### 3.4 Streaming fetch, timeouts and deadlines

```khrip
for data in fetch POST URL req headers {"Authorization": "Bearer {key}"} {
    let c: Chunk? = from_json(data)
}
let r = fetch GET url timeout 2 s
```

- **`for x in fetch METHOD url [body] [headers map] [timeout N unit] { }`** gives `x: str` per SSE event `data` (multi-line data joined with `\n`), or per line for other content types.
- **Status checks.** A status other than 2xx, an upstream SSE `event: error`, or an end of the body before its terminator ends the route with **502** `upstream answered 401` (or `upstream ended early`, or `upstream sent an error event`). That is a real 502 before the stream's head, and an error event after it. The upstream body text goes to the log, not to the client (S5, C7).
- **A literal request body in a `for` header** must be bound to a `let` first (E-F3).
- **`timeout N ms|s|min`**:
  - on a plain `fetch` it is the deadline (default 30 s, and never past the request's own deadline);
  - on a fetch loop it is the **idle** limit between bytes (default 30 s), and there is no total limit.
- **Header validation.** Header names and values sent by `fetch` are checked at run time: a CR, LF or NUL in a value panics with `fetch: header "X-User" contains a line break` (S2).

**Deadlines (B1).**

| Phase | Deadline |
|---|---|
| A request, until its response head is sent | `KHRIP_TIMEOUT` (30 s), or the client's gRPC/Connect deadline if it is shorter |
| A request waiting for the client's next stream item | the deadline is paused; the body's minimum data rate applies instead (§5.2) |
| A message-loop pass, from the message's arrival to the pass's first `send` | `KHRIP_TIMEOUT` |
| A stream after its head | no request deadline; idle limits apply (write stall 30 s, fetch idle 30 s, ping); a client gRPC/Connect deadline still applies |

### 3.5 Streamed `sql`

`for o: Order in sql "SELECT ..."` reads rows through a PostgreSQL portal, 256 rows per round trip.
- The type is required.
- `for x: T in xs` is also accepted for lists, and is checked.
- Inside a row loop no other `sql`, `fetch`, `sleep` or stub call is allowed; only `send` may wait (E-Q5). The portal holds a pool connection inside an implicit transaction, so a second statement would either deadlock the pool or join that transaction.

### 3.6 gRPC: `rpc` and `service` (v0.15)

```khrip
service shop.v1.Orders          // optional, one per file; default: main file stem → shop.Shop

rpc GetOrder GET "/orders/{id}" (id: int) -> Order | 404 { ... }   // gRPC + Connect + gRPC-Web + REST
rpc ListOrders (customer: str) -> stream Order { ... }              // server stream
rpc Import (rows: stream NewOrder) -> Summary { ... }               // client stream
rpc Chat (msgs: stream Say) -> stream Line { ... }                  // bidi
rpc GetQuote (sym: str) -> Quote at env("QUOTES_URL")               // v0.16: a client stub
```

- An `rpc` with a body is a server method. With `METHOD "path"` it is also a route with exactly the semantics of `route`.
- The method name is UpperCamelCase (E-R1); the full name is `/<package>.<Service>/<Name>`.
- A bodiless `rpc ... at <str?>` is a client stub (§12.7), and calling it looks like a function call.

### 3.7 Tests

```khrip
test "chat" {
    let a = open GET "/rooms/1/ws?user=ann"
    let b = open GET "/rooms/1/ws?user=bob"
    a.send(Say { text: "hi" })
    let m: Line? = b.next()
    expect m != none && m.user == "ann"
}
```

- **`open METHOD "path?query" [headers map]`** starts a stream route in-process: as a WebSocket for a GET route with a stream parameter, otherwise as an NDJSON stream. `open Name(args)` does the same for a streaming rpc.
- **On the handle:**
  - `s.send(v)` sends one message or item;
  - `s.close()` ends the client side;
  - `s.next()` returns the next value, typed by the annotation, or none when nothing more can arrive (§9.8).
- **`call METHOD "path"`** on a stream route runs it to its return and gives the NDJSON body. On a route that calls `subscribe` it is an error (E-X3, C5), because `call` would silently stop at the return; use `open`.
- **`call Name(args)`** calls an rpc through the protobuf codec.

### 3.9 Alternatives considered

| Question | Chosen | Rejected, and why |
|---|---|---|
| Server streaming | `-> stream T` + `send` | **`yield`:** makes helper functions generators. **A returned channel:** the forgotten-close bug class. **An `sse` keyword:** one format only. |
| WebSocket | a `stream T` parameter + `for` | **Event handlers:** need closures over connection state and a close handler. **A `ws` value:** can be leaked or stored. **A `socket` declaration:** duplicates route parsing. |
| Fan-out | `topic` | **A store map of connections:** leaks, double closes, untyped. **String rooms:** invisible to the compiler. |
| History with resume | `subscribe(t, history)` (M3) | **`if !subscribe(t) { send history }`:** its result can be ignored (a silent repeat), and it forced "`send` never waits under the lock" (R2). **Automatic suppression:** the runtime cannot tell which sends are history. |
| Outer values in loops | copying with forwarding at the pass end (invisible; R4) | **A keep heap with exact tree frees** (revision 1): "assigning copies" contradicted KHRIP.md, deep-copied state on every assignment, and was about 650 lines. |
| Streaming fetch | `x: str` | **Typed `for c: Chunk in fetch`:** upstream streams mix event kinds, so either they kill the stream or they are skipped silently. |
| gRPC declaration | `rpc Name [METHOD "path"]` | **Derive from routes:** a path change renames a method. **`service { }` blocks:** more tokens. |
| Field numbers | the `<main>.proto` lock file | **`@1` in types:** tokens, plus numbering mistakes by the AI. **Declaration order:** reordering breaks clients. |
| Production settings | environment | **Declarations in code:** tokens in every program for what is right by default. |

**`STREAMS.md` (complete):**

````markdown
## Streams, WebSocket, topics

```khrip
topic chat: Line

route POST "/ask" (body: Ask) -> stream Token {
    for data in fetch POST LLM_URL body {    // SSE data or lines; not 2xx: 502
        let c: Chunk? = from_json(data)
        if c != none {
            send(Token { text: c.text })
        }
    }
}

route GET "/rooms/{id}" (id: str, user: str, msgs: stream Say) -> stream Line {
    subscribe(chat[id], rooms[id] ?? [])     // history first, then live values
    for m in msgs {                          // WebSocket messages, one at a time
        publish(chat[id], Line { user, text: m.text, at: now() })
    }
}
```

- `-> stream T` sends each `send(v)` as SSE, NDJSON or gRPC, as the client
  asks; before the first `send` the route may `return 404`.
- `msgs: stream T` is a WebSocket with `GET`, an NDJSON body with `POST`; read
  it with `for m in msgs` directly in the route body. Each WebSocket message is
  a request for the `sql` rules; in a `POST` loop a write needs `tx { }`.
- `subscribe(t, history)` sends `history`, or only what a reconnecting client
  missed, then every later `publish(t, v)` in this process until the client
  leaves, even after the route returns.
- A client that leaves ends the route at its next `send` or wait. In a WebSocket
  loop read `store` inside the loop: a value read before it stays as it was.

`let s = open GET "/rooms/1?user=ann"` opens a stream in a test: `s.send(v)`,
`let m: Line? = s.next()` (none at the end).

`yield`, `Flush()` → `send(v)`; `onmessage` → `for m in msgs`; a map of
connections → `topic`.
````

The snapshot sentence names the WebSocket loop only. That is the case where the snapshot lasts across hours and other requests change store in between. For the other three kinds, warning W-S1 fires at compile time.

**`GRPC.md` (complete):**

````markdown
# gRPC in Khrip

```khrip
service shop.v1.Orders                      // optional: shop.kh alone gives shop.Shop

rpc CreateOrder POST "/orders" (body: NewOrder) -> 201 Order | 400 str {
    return 201 sql "INSERT INTO orders {body} RETURNING *"
}
rpc GetOrder GET "/orders/{id}" (id: int) -> Order | 404 {
    return sql "SELECT * FROM orders WHERE id = {id}"
}
rpc ListOrders (customer: str) -> stream Order {
    for o: Order in sql "SELECT * FROM orders WHERE customer = {customer} ORDER BY id" {
        send(o)
    }
}
rpc Import (rows: stream NewOrder) -> Summary { ... }    // client stream
rpc Chat (msgs: stream Say) -> stream Line { ... }        // both ways
```

- `rpc Name` serves gRPC, gRPC-Web and Connect (JSON or protobuf) at
  `/shop.v1.Orders/Name`. With a method and a path it is also a REST route.
- The request message is the parameters (`GetOrderRequest { id }`); a single
  struct parameter is the message itself, so adding a second parameter later
  breaks clients. A result that is not a struct is wrapped:
  `ListUsersResponse { items }`.
- Types: `int` int64, `float` double, `str` string, `[T]` repeated, `map[K, V]`
  map, structs are messages, variants are `oneof`. A missing field that is not
  `T?` and has no default is INVALID_ARGUMENT, as in JSON; a missing list is
  empty.
- Statuses become codes: 400 INVALID_ARGUMENT, 401 UNAUTHENTICATED, 403
  PERMISSION_DENIED, 404 NOT_FOUND, 409 ALREADY_EXISTS, 412 FAILED_PRECONDITION
  (for version conflicts), 429 RESOURCE_EXHAUSTED, 503 UNAVAILABLE, a panic
  INTERNAL; the text is the message.
- `header(name)` reads metadata, `set_header` sends it. The client's deadline
  bounds `fetch` and `sql`; a cancelled call ends at its next wait. Health and
  reflection are built in.
- khc writes `shop.proto` beside `shop.kh` with stable field numbers: commit it
  (`khc -o` needs it). A changed field type is an error; to rename a field,
  rename it in the .proto too.
- `khc proto quotes.proto` writes `quotes.kh`: the types and rpcs to call,
  `rpc GetQuote (sym: str) -> Quote at env("QUOTES_URL")`. `let q =
  GetQuote("ACME")`: NOT_FOUND ends the request with 404 (into `Quote?`: none),
  UNAVAILABLE 503, a timeout 504, any other code 502.
- Tests: `call GetOrder(1)` returns a `Response`; `open ListOrders("ann")` reads
  a stream.
````

## 5. Production server (v0.14)

### 5.1 Bodies, chunked encoding, smuggling

- **Small bodies (S1).** A body of up to 64 KiB, by `Content-Length` or chunked, is still read by the event loop into a pooled buffer before the request gets a coroutine, as today. A slow client then holds a buffer, not a coroutine or an arena slot.
- **Larger bodies** get the coroutine at the end of the head and are read straight into its arena (zero-copy JSON as today), under these limits:
  - the minimum data rate `KHRIP_MIN_RATE` (240 B/s averaged over 5 s windows, after a 5 s grace; Kestrel's rule), else 408;
  - at most 64 coroutines per thread may wait for body bytes; further requests wait in the event loop.
- **Limits.**
  - A `Content-Length` over `KHRIP_MAX_BODY` gets 413 at once, without reading the body.
  - A chunked body is cut off at the limit.
  - Stream parameters apply `KHRIP_MAX_MESSAGE` per item.
- **`Expect: 100-continue`.** The server answers `100 Continue` when the body is first read, or 413/417 instead.
- **Chunked decoding:**
  - in place;
  - hex sizes of at most 16 digits, rejected if they overflow 2^62;
  - extensions skipped;
  - trailers read up to the head limit and discarded.
- **Smuggling rules** (400 and close):
  - `Content-Length` together with `Transfer-Encoding`;
  - duplicate or list `Content-Length`;
  - a `Transfer-Encoding` other than exactly `chunked` (501);
  - obs-fold;
  - whitespace before the colon;
  - a bare LF in the head;
  - NUL or a control character in a field value.
- **Request targets (C9).**
  - Origin-form and **absolute-form** (`GET http://host/path`) are accepted, as RFC 9112 §3.2.2 requires of servers; for absolute-form, the authority replaces `Host`.
  - CONNECT and asterisk-form, other than `OPTIONS *`, get 400.

### 5.2 Limits and timeouts

| What | Default | On expiry |
|---|---|---|
| Head | 64 KiB; one field line ≤ 8 KiB | 431 and close |
| Head time from the first byte | 10 s | 408 and close |
| Body over 64 KiB, or a body loop waiting for its next item | 240 B/s after 5 s | 408 (before the head), or an error after it |
| Keep-alive idle | 650 s | close |
| Write stall (output not drained) | 30 s with no progress | close. The same 30 s for a slow stream client, a row loop waiting on `send`, and an HTTP/2 zero window (C10) |
| Request deadline | `KHRIP_TIMEOUT` 30 s (§3.4) | cancelled at the next wait; 503 `Retry-After: 1` if nothing was sent |
| Open files | `RLIMIT_NOFILE` raised to the hard limit | accept-and-close with one log line a minute. One fd is kept in reserve so that `accept` works at EMFILE (C9) |

Connection timers live in a per-thread timer wheel (1 s slots, O(1)).

### 5.3 Deadlines and cancellation

- **Two new per-coroutine words: a deadline and a cancel flag** (the flag lives in the `__Stream` for streams).
  - The deadline follows §3.4.
  - The flag is set by a client disconnect on a stream or rpc, by `RST_STREAM`, by graceful shutdown, or by a deadline.
- **`__co_wait` checks both** before and after parking. On expiry it raises `PANIC_CANCEL`, which unwinds through the existing catch path and is not logged as an error:
  - `tx` rolls back;
  - pool connections that were mid-exchange are closed;
  - `sql` sends a `CancelRequest`.
- **A non-stream request is not cancelled when its client leaves**: a write half-done outside `tx` is worse than finished work.
- **Inherited by calls.** `fetch` uses `min(timeout clause, deadline - now)`; `sql` uses `statement_timeout = min(DATABASE_TIMEOUT, deadline - now)`.

### 5.4 Graceful shutdown

1. **Signals are always handled.** SIGTERM and SIGINT go to the control thread, which is now always running.
2. **First SIGTERM:**
   - `/readyz` answers 503 and gRPC health becomes NOT_SERVING;
   - the log gets `khrip: draining (lame duck 5 s, drain 20 s)`.
3. **During `KHRIP_LAMEDUCK`** the server keeps accepting. Then the listeners close.
4. **Then, at once:**
   - idle keep-alive connections close;
   - busy ones get `Connection: close`;
   - HTTP/2 connections get a graceful GOAWAY (2^31-1, then the real last id after a PING);
   - parked streams end: SSE closes, so clients reconnect elsewhere with `Last-Event-ID`; WebSocket gets close 1001; gRPC gets `UNAVAILABLE "server is shutting down"`.
5. **After `KHRIP_DRAIN`,** running coroutines are cancelled and get 1 s to unwind. The `KHRIP_DATA` save runs, then the process exits 0.

   The defaults total 5 + 20 + 1 = 26 s, which leaves about 4 s for the save inside Kubernetes' default 30 s grace (C8). The start log names the total.
6. **A second signal** exits at once with code 1.

### 5.5 Logs, metrics, trace ids

- **Trace ids.**
  - A valid incoming `traceparent` is continued; otherwise a new id is made per request.
  - `fetch`, and gRPC stubs from v0.16, send `traceparent` and pass `tracestate` on unchanged.
  - Every log line of the request carries the id.
- **`KHRIP_LOG=requests`** writes one JSON line per request from a per-thread buffer, flushed every 100 ms:

  ```json
  {"time":"2026-10-25T10:00:00.123Z","trace":"4bf92f3577b34da6a3ce929d0e0e4736","method":"GET","route":"/users/{id}","status":200,"ms":0.31,"in":0,"out":512}
  ```

  - **The query string is never logged.** Browsers put WebSocket tokens there.
  - A stream gets one line at its end, with the messages in and out and the close code.
- **Metrics on `METRICS_PORT`.**
  - The series: `khrip_http_requests_total{route,method,code}`, a duration histogram, connections by protocol, open streams, stream messages, slow-client closes, topic publishes and subscribers, `fetch` by host, `sql` duration, pool use, store heap, GC cycles, TLS handshakes, the memory budget (`khrip_memory_bytes{kind}`, `khrip_shed_total{reason}`) and the process series.
  - Counters are per thread with no atomics, and a scrape sums the threads.
  - Route and topic labels are declared names, so the number of series is bounded by the program.

### 5.6 Connection layer and CORS

- **Pooled buffers.**
  - Input buffers start at 16 KiB and grow to the head, frame or message size.
  - Output is a queue of 64 KiB segments.
  - Both return to the pool when the connection is idle.
  - An idle keep-alive connection keeps only its `__Conn` (≈ 160 B) and a wheel entry.
- **The fd table** becomes a growable two-level table, so descriptors above 65,535 are served.
- **A header index per request** (name hash, offset, length), built at the first `header()` call. It is allocated outside item memory (§9.4), and HTTP/2 fills it from HPACK.
- **Event registration (P4).** Stream fds stay registered once with `EPOLLIN|EPOLLOUT|EPOLLRDHUP|EPOLLET` for their whole life. There is no `epoll_ctl` ADD and DEL per wait, and the connection keeps readiness flags.
- **CORS from `KHRIP_CORS`:**
  - preflight `OPTIONS` on a declared path gets 204 with the echoed origin, the route's methods, the echoed headers, `Max-Age: 600` and `Vary: Origin`;
  - responses expose `set_header` names and, for rpcs, `grpc-status`, `grpc-message` and `Connect-*`;
  - credentials are allowed only for listed origins.

  The WebSocket origin rule is in §7.1.

### 5.7 Process memory budget (R5)

Per-connection caps alone multiply with the number of connections. One process budget, `KHRIP_MEMORY`, therefore covers all connection-owned memory:
- send queues;
- owner regions;
- WebSocket message buffers;
- HTTP/2 buffered bodies;
- topic frames and replay rings;
- TLS records.

Each thread keeps a byte count, and a shared total is updated in 64 KiB steps.

| Use of the budget | Action |
|---|---|
| over 85% | New WebSockets, SSE streams and HTTP/2 streams get 503 (gRPC: RESOURCE_EXHAUSTED). The slow-client threshold halves. The replay rings evict their oldest entries |
| over 100% | The connections with the largest queues are closed as slow clients until usage is under 95%. Each close is counted in `khrip_shed_total{reason="memory"}` and logged once a second (R-M1) |

The per-connection defaults are lower than in revision 1:

| Limit | Revision 1 | Now |
|---|---:|---:|
| Stream queue | 1 MiB | 256 KiB |
| Connection region | 64 MiB | 4 MiB |
| WebSocket message | 4 MiB | 1 MiB |
| Buffered request bodies per HTTP/2 connection | 128 × 4 MiB | 4 MiB in total (§10.3) |

## 6. Streams and SSE (v0.14)

### 6.1 Head and formats

- **The head** (or the 101, or the gRPC headers) goes out at the first of:
  - a `send`;
  - for WebSocket and gRPC streams, the first read of the stream parameter;
  - the first wait after a `subscribe`;
  - the route's return with live subscriptions;
  - `KHRIP_PING` without any of these.

  Before that, `return 404`, `fail` and `set_header` behave as in any request.
- **SSE** is sent with:
  - status 200 and `Content-Type: text/event-stream; charset=utf-8`;
  - `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no`;
  - `Vary: Accept`;
  - chunked framing on HTTP/1.1.

  **NDJSON** is `application/x-ndjson`, also chunked.
- **One value** is JSON-encoded straight into the output segment behind reserved prefix space:
  - SSE `data: <json>\n\n`, with an `id:` line for topic values (§6.4);
  - NDJSON `<json>\n`;
  - an HTTP/1.1 chunk header, or an HTTP/2 DATA header.
- **A finite stream ends** with the last chunk or `END_STREAM`, and the connection serves the next request.

### 6.2 Backpressure (R2)

- **`send` waits** whenever the stream's queue is over `KHRIP_STREAM_QUEUE`. The wait goes through `__co_wait`'s audited window, with the store lock released (keep) and taken again, exactly as a `fetch` does.
- **It waits even when the lock is held.** Revision 1's "never wait under the lock" existed only to protect the history idiom. `subscribe(t, history)` now does that job (§8.2), so a large export (`for u in users.values() { send(u) }`) streams with bounded memory instead of failing as a slow client.
- **A send that makes no progress for 30 s** ends the stream as a slow client.
- **Topic deliveries never wait** (§8.3).
- **Queue contents.** Queues hold private segments, or references to shared, reference-counted topic frames.

### 6.3 Disconnect and pings

- **Disconnect.**
  - The client fd is armed for `EPOLLRDHUP`. On HTTP/1.1 streams, input other than a valid pipelined request is discarded.
  - A FIN, a WebSocket close or an `RST_STREAM` marks the stream dead and removes its subscriptions at once.
  - A running handler gets its cancel flag and unwinds at its next `send` or wait; an open fetch loop's connection is closed.
  - A parked message loop, or a stream that only subscribed, is freed at once.
- **Pings** (`KHRIP_PING`, 30 s by default, P6) come from the timer wheel with no coroutine:
  - SSE sends `:\n\n`;
  - WebSocket sends PING, and no frame within two intervals closes the connection;
  - HTTP/2 sends PING on an idle connection.
- **Ping budget.** At 100k connections, 30 s pings mean 3,300 small writes per second. The gate is idle CPU ≤ 1% of a core (§15).

### 6.4 Event ids and `Last-Event-ID` (R1)

- **The id is a vector.** A topic delivery's SSE `id:` carries the stream's position in every channel it subscribed to: `id: 9f3a1c2e.5d41402a:41.7b52009b:7`, that is, the process epoch, then per channel a 32-bit channel hash in hex and that channel's sequence number.
  - At most 8 channels are carried, the most recently subscribed.
  - A value from `send` carries no `id:`. Per the SSE spec, the browser keeps the last id it saw.
- **On `subscribe(t, history)` with `Last-Event-ID`:**
  - if the epoch matches, the id has an entry for t's hash, and t's replay ring still holds the next sequence number, the missed values are queued and `history` is skipped;
  - otherwise `history` is sent. That covers another process, a ring that no longer holds the values, and a channel missing from the id.

  Each channel is therefore replayed or re-sent on its own, so a resume never replays the wrong channel and never loses values. A re-sent history may repeat values the client already saw. They carry their own fields, so a client that cares can drop duplicates.
- **The replay ring** keeps `KHRIP_TOPIC_REPLAY` (64) shared frames per channel for at most 5 minutes, under the memory budget (§5.7).

### 6.5 Errors after the head (C4)

| Cause | SSE | NDJSON | WebSocket | gRPC / Connect / gRPC-Web |
|---|---|---|---|---|
| `return 4xx` or `fail(4xx, msg)` | `event: failed`, `data: {"status":403,"message":"..."}`, `retry: 3600000`, then the end. The long retry stops EventSource from reconnecting every 3 s | the body ends without its last chunk; logged | close `4000 + status` with the reason | trailers with the mapped code |
| `5xx`, or a panic | `event: failed` with 500 and no long retry, so the client reconnects; the panic text goes to the log only | as above | 1011 | INTERNAL |
| Shutdown | the end, with no event; the client reconnects | as above | 1001 | UNAVAILABLE |
| Slow client | close | close | 1008 `too slow` | RESOURCE_EXHAUSTED |

- **Why `failed` and not `error`:** an event named `error` would reach the handler that EventSource also calls for connection errors.
- **`set_header` after the head** panics with `set_header after the response started`.

### 6.6 Request streams (body loops)

- **NDJSON:**
  - lines split on `\n`, with a trailing `\r` dropped;
  - empty lines skipped;
  - each line decoded into item memory.
- **A JSON array** is split element by element by the SIMD structural scanner.
- **Errors in an item** name the line or the index: `line 3: text: expected str`, or `body[2].text: ...`.
  - **Partial progress is loud (M5).** If any earlier pass committed a write, the message adds ` (2 items saved before it)` and the header `Khrip-Items-Saved: 2`.
  - The same suffix is added to any status ≥ 400 that leaves the route after committed passes.
- **Constant memory.** An item larger than `KHRIP_MAX_MESSAGE` gets 413. A 100 MB upload runs in about the arena high-water mark of one item.

### 6.7 Streaming fetch

- **The open is one audited window.** `__fetch_open` builds the request bytes, then connects, sends and reads the head inside one audited window, like `__fetch`. Each later read happens at the loop head, which is the pass boundary (§9.2).
- **Parsing happens in place** in a per-request read buffer that lives outside item memory (§9.4). The SSE or line parser yields a `str` view that is valid for the pass.
- **A truncated upstream is an error (C7).** An upstream EOF before the chunked terminator or `Content-Length` is `upstream ended early`. An SSE `event: error` is `upstream sent an error event`. Both mean 502 before the head and an error after it, never a silent truncation.
- **Connection reuse.** An early end (`break`, `return`, cancel, panic) closes the connection. A complete response returns it to the pool. From v0.16, HTTP/2 upstreams get `RST_STREAM(CANCEL)` instead.

## 7. WebSocket (v0.14)

### 7.1 Handshake and origin

- **Which requests upgrade.** A GET with `Upgrade: websocket`, `Connection: upgrade`, version 13 and a valid key, on a stream route.
  - The wrong version gets 426.
  - A bad key gets 400.
  - A plain GET to a route that has a stream parameter gets 426 `this route is a WebSocket` (C5).
- **Origin (S3).** The request is accepted when any of these holds:
  - there is no `Origin` header (non-browser clients);
  - the `Origin` is the server's own: its host and port equal `Host`, and its scheme is `https` on a TLS connection, or either `http` or `https` on a plain connection, because TLS-terminating proxies are common;
  - the origin is listed **explicitly** in `KHRIP_CORS`.

  Otherwise the answer is 403 `origin not allowed`. **`KHRIP_CORS=*` does not apply to WebSocket**: browsers send cookies with WebSocket handshakes, so `*` would reopen cross-site WebSocket hijacking.
- **The route runs before the 101,** so `header()`, path, query and `return 401` work as usual.
- **Request head (P3).** At the 101, the connection keeps only the request fields the route can read later:
  - path and query parameters are already parsed into locals;
  - the values of the header names used in `header("...")` literals are copied into the `__Stream`;
  - a route that calls `header(x)` with a non-literal name keeps the whole head, and the compiler says so in a note.

  A stream whose route has returned (subscribed-only) keeps none.
- **No subprotocol and no extensions** are negotiated.

### 7.2 Frames and budgets (S11)

- **Parsing** happens in the event loop, on the pooled input buffer:
  - RSV bits must be 0;
  - client frames must be masked;
  - a 64-bit length with the top bit set is a protocol error (1002).
- **Unmasking** is done in place with AVX2 (`__simd_ws_unmask`).
- **Text messages** must be valid UTF-8, checked incrementally (1007).
- **Size and fragment limits.**
  - A message larger than `KHRIP_MAX_MESSAGE` gets 1009.
  - **A fragmented message may have at most max(16, size / 1 KiB) fragments**, else 1008, so a flood of 1-byte fragments costs the attacker as much as it costs the server.
- **Binary messages** get 1003.
- **Control frames:**
  - larger than 125 bytes, or fragmented, gives 1002;
  - **budget:** each PING or PONG costs one token, refilled by data bytes; more than 100 per second or 10,000 without data gives 1008;
  - **PONGs are coalesced**: if several PINGs arrive while a PONG is pending, only the latest is answered.
- **Server frames** are unfragmented and unmasked, with the header written right-aligned before the encoded JSON. Topic frames are built once and shared.

### 7.3 One message at a time (C11)

- **Order.** A connection's messages are handled one at a time, in order. While a pass runs, the event loop parses no further data frames from that connection, so TCP pushes back. It still answers PINGs and sees CLOSE and FIN.
- **Consequence.** A client cannot interrupt a running pass with another message (an interactive "stop").
- **The pattern to use instead** (written in SERVER.md and TUTORIAL.md): stream the answer over SSE, so that closing it cancels the work; or send "stop" to a separate POST route that sets a flag in store, which the loop reads at each pass.

### 7.4 Close codes (C2, C5)

| Event | Code | Then |
|---|---|---|
| The route returns and has no subscriptions | 1000 | wait up to 5 s for the client's close |
| The route returns with subscriptions | — | the socket stays open and forwards until the client leaves; when its last channel is unsubscribed: 1000 |
| A data message on a socket whose route reads no messages: a route without a stream parameter, or after its loop ended | 1003 `this socket does not read messages` | close |
| The client sends close c | echo c if valid, else 1002 | a running pass is cancelled |
| `return status` or `fail(status, msg)` after the 101 | 4000 + status | as for 1000 |
| Panic | 1011 | |
| Deadline in a pass | 4504 | |
| Message too large / invalid UTF-8 or JSON / binary | 1009 / 1007 / 1003 | |
| Slow consumer / memory shedding | 1008 `too slow` | close at once |
| Shutdown | 1001 | |
| No frames for two ping intervals | — (TCP closed) | |

### 7.5 No permessage-deflate; authentication

- **No permessage-deflate,** for three reasons:
  - **memory:** zlib holds about 300 KB per direction per connection with context takeover, more than the whole per-connection budget;
  - **CPU:** compressed frames cannot be shared in broadcast;
  - **security:** compression next to secrets leaks them (BREACH).

  gorilla and Kestrel leave it off by default too.
- **Authentication** is checked once, at connect.
  - A program may re-check per message inside the loop.
  - Closing all connections of a user from server code is out of scope (§21).

## 8. Topics (v0.14)

### 8.1 Guarantees

- **At most once.** Every subscriber that was subscribed when a value was published gets it, unless it leaves or is closed as slow.
- **One total order per channel:** sequence numbers are assigned under the channel lock. There is no order across channels.
- **Start of a subscription.** The subscription records the channel's sequence number at registration, and older values are skipped even if they are already in the thread's inbox.

### 8.2 `subscribe(t, history)` and store (M3, B2)

**What the compiler emits for `subscribe(t, h)`:**
1. `__store_lock()` in the route's mode, if the program has a store (B2);
2. `__sub_begin(t)`: registers the subscription with start S = the channel's current sequence number and puts it in the *history pending* state, in which deliveries are held aside in order;
3. `h` is evaluated;
4. `__sub_history(h)`: queues h's values with normal backpressured sends, which may wait (§6.2), then appends the held deliveries and leaves the pending state.

For SSE with a usable `Last-Event-ID`, step 3 is skipped, and step 4 queues the ring's values after the client's position.

**Why nothing is lost or repeated with a store history:**
- A writer stores V and publishes it with no wait in between, while holding the exclusive lock.
- The subscriber's steps 2–3 run under at least the shared lock, with no wait in between when h reads only store.
- So either V's write and publish come before the subscriber's section (V is in h, and its sequence number is ≤ S, so it is not delivered), or after it (V is not in h, and it is delivered).
- Waits during step 4 do not matter: h has already been read, and the store objects it references stay valid through the pin records published at the wait.

**Holes that remain:**
- **A writer that waits between the store write and `publish`** loses the guarantee (§16.5 S2).
- **A history read with `sql`** gives "no loss, possible repeats". The writer commits and then publishes, and the subscriber registers and then queries, so a value committed before the query but published after the registration arrives twice.

**Taking the lock in the route's mode** (B2) matters for a writer route that publishes and later writes store in the same unit of work: a shared-mode lock taken by a topic operation would leave that later write running under the shared lock. Programs without `store` take no lock for topics.

### 8.3 Slow consumers and lifetime

- **A delivery that would take a subscriber's queue over the limit** closes that subscriber:
  - SSE ends, and the client resumes;
  - WebSocket gets 1008;
  - gRPC gets RESOURCE_EXHAUSTED.

  The close is counted and logged once a second at most.
- **Channels** are created on first use. One is dropped when it has no subscribers and its ring has expired.
- **Costs:** a channel is about 96 B plus ring references; a subscription is 48 B.

### 8.4 Cross-thread fan-out (R10)

**Process-wide state.**
- The channel table is sharded 64 ways.
- Each `ChannelState { lock, seq, threads (bitmask), json_subs, pb_subs, ring }` lives outside store and the arenas.

**Per thread.**
- A table from channel to local subscriber streams.
- An inbox of `(channel, seq, frames)` entries: a **segmented MPSC queue**, a linked list of 4,096-slot segments. A producer claims a slot with `lock xadd` on the segment's tail; the producer that fills a segment links the next one with a CAS, and the consumer frees segments it has drained.
  - Entries for a channel are enqueued under that channel's lock, so every consumer sees each channel in sequence order.
- An `eventfd` in the thread's epoll.

**`publish(t, v)`:**
1. Encode v once into a shared frame block (JSON with the WebSocket, SSE and chunk framing as slices of it; protobuf with the gRPC prefix if there are gRPC subscribers).
2. Under the channel lock: increment seq, append to the ring, push one entry to each subscribed thread's inbox.
3. Release the channel lock, then **write the eventfd at once** for each thread whose inbox went from empty to non-empty, never inside the lock.

**Delivery.**
- The subscriber thread's event loop drains its inbox and appends a reference to each local subscriber's queue, about 20 ns per subscriber.
- Each connection gets one `writev` per loop turn.

### 8.5 Processes

- **Topics are per process, like store.** Two replicas do not share broadcasts.
- **Start log:** every start of a program that declares topics logs `khrip: topics are per process; replicas do not share them` (C10).
- **The planned bridge** (out of scope): `topic chat: Line shared` over PostgreSQL `LISTEN/NOTIFY`.

## 9. Memory and concurrency (v0.14)

### 9.1 Item memory and owner regions (R4, M6)

**Item memory.**
- At the entry of any of the four loop kinds, the compiler saves `CTX_ITEM_MARK` and sets it to the arena pointer.
- Everything a pass allocates lies above the mark. At the end of the pass the arena pointer returns to the mark, `__strc_clear()` runs (rule I1), and in verify mode the freed bytes are filled with 0xDB.

**Owner regions.** Values that must outlive a pass move into a region:
- **CONN** is the connection's region, for message loops. It lives until the connection closes.
- **REQ** is the request's region, or the current message pass's. It lives until the request, or the message pass, ends.
- **Allocation.** Regions are bump-allocated in chunks that start at 256 B and double up to 64 KiB, taken from the thread's small-block allocator in a dedicated address range, so `__in_region(p)` is a range check. A connection with 200 B of state costs about 256 B.

**Roots.** For each loop the compiler emits a table of its **roots**: the frame slots of non-scalar locals and parameters declared outside the loop and visible in it. Each root's owner follows from where it was declared: before the message loop means CONN, otherwise REQ.

**Loop entry.** At the entry of each loop the roots are evacuated into their owners' regions:
- a deep copy with forwarding (`__deep_copy` extended with a forwarding table), so two roots that share an object still share its copy;
- values already in a region stay where they are;
- store values reachable from the roots are copied too.

After this step the roots reach nothing in the arena and nothing in store.

**The generalized barrier** (`__barrier`, `__alloc_for`) gains two cases, linked only into programs that have stream loops (R7):
- **writing an item-memory pointer into a region object** (an outer `list.push(x)`) appends the slot to the pass's remembered set;
- **writing a store pointer into a region object** replaces it with a copy in that region, so regions never hold STORE pointers.

  A region container grows inside its region.

These cases are designed together with GC step 6's SATB pre-write barrier, in one function with one fast path. The fast path for an object in the current item, the common case, is one load and one compare.

**End of each pass** (`__item_end`):
1. Evacuate from the roots and from the remembered slots: every pointer into item memory (for CONN roots, anywhere in the arena, since the arena is released at park) is deep-copied into the owner's region with forwarding, preserving sharing. Store pointers that a root picked up during the pass are copied too (the snapshot). Values in regions, DATA and `__Stream`-owned memory (the header copy) stay where they are.
2. Move the pass's `CTX_JNULLS` bits to the evacuated copies (§9.4).
3. Reset the arena to the mark.

**Full region compaction.** When a region has allocated more than max(64 KiB, 2 × its live bytes after the last compaction), it is copied semispace-style from all its owner's roots with forwarding, and the old chunks are freed. The cost is amortized O(live). Accumulating `full = full + token` therefore stays at about two copies of `full`.

**What the program can observe:** nothing, apart from one rule. Sharing and identity are preserved, so "assigning shares" (KHRIP.md) stays true, and revision 1's "assigning copies" sentence is gone (M6). The rule is that **a store value held in a root is a snapshot from the loop's entry or the pass that read it.** Read store inside the loop for current data. Warning W-S1 fires when a root initialized from a store read is used inside the loop. STREAMS.md states the rule for the WebSocket loop.

**Caps.**
- **CONN regions** are capped at `KHRIP_STREAM_STATE` (4 MiB). Past the cap, the connection closes with 1011 and the log line R-S3 names the route.
- **REQ regions** count toward the request's arena limit.

**Both kinds** count toward `KHRIP_MEMORY`.

**Cost:** about 500 lines (`lib/region.kh`). Revision 1's keep heap with exact tree frees was 650 lines and deep-copied state on every assignment.

### 9.2 The pass boundary: the end of a unit of work (P4)

At the head of each loop, before the wait for the next item, evacuation (§9.1) has left the roots with no STORE pointers, and the item's locals are dead. So:
- **The store lock is released with `__store_release_final()`**. No pin record stays linked, and the GC never scans a waiting loop.
- **The wait does not take the lock again.** The next store access in the pass takes it, in the route's mode, through `store_touch`.
- **A fetch loop that never touches store** holds no lock and publishes no pins, even when its route writes store elsewhere. A store-writing LLM proxy pays nothing per token. Revision 1 paid an exclusive lock plus a pin publish and withdraw per token.

Waits inside a pass (a `fetch` in a message handler, a backpressured `send`) are ordinary `__co_wait` windows: keep release, pins published, the lock taken again eagerly, as today.

### 9.3 Context words (B3)

The table covers every word in [8, `CTX_CO_END`), plus the new words and the thread-shared words a stream can touch. It defines what happens at a message-loop park, at resume on another coroutine, and at each pass.

| Word | Class | At park | At resume on a new coroutine | Per pass |
|---|---|---|---|---|
| `CTX_PTR`, `CTX_END` | coroutine (allocator) | dropped | the new coroutine's arena | reset to the item mark |
| `CTX_SAVE_PTR`, `CTX_SAVE_END` | coroutine | dropped | the new coroutine's | — |
| `CTX_ARENA`, `CTX_ARENA_END` | coroutine | the arena is released to the pool | the new arena | — |
| `CTX_PSAVE_PTR`, `CTX_PSAVE_END` | must be 0 | asserted 0 (not in persist mode) | 0 | — |
| `CTX_STORE_HELD` | must be 0 | 0 after the final release | 0 (taken lazily) | 0 at the loop head |
| `CTX_WORKER` | **stream-owned** | points to the Worker-lite inside `__Stream` | restored | — |
| `CTX_CATCH` | **stream-owned** | the jump buffer inside `__Stream`'s Worker-lite, never in an old coroutine's frame | restored | — |
| `CTX_PANIC` | must be 0 | asserted 0 | 0 | — |
| `CTX_SERVER` | thread value | — | the new coroutine's (the same server) | — |
| `CTX_STORE_MODE` | **stream-owned** (the route's mode) | saved | restored | — |
| `CTX_CORO` | coroutine | — | the new coroutine; `__stream_park` reads it again after resuming | — |

**Verify mode** (`KHRIP_GC_VERIFY=1`), at park:
- `__simd_pinscan` scans the saved frames and the `__Stream` for words that point into the released arena, the old `__Co`, the old Worker or the STORE range;
- each such word is overwritten with a poison value, so a live use faults at once on resume instead of reading reused memory later.

The "must be 0" words are asserted, both in verify mode and in debug builds.

### 9.4 Lazily allocated per-request state (B3 audit)

| State | Where it lives now | Rule |
|---|---|---|
| `CTX_JNULLS` (JSON nulls per struct address) | arena | Item entries die with the pass. Evacuation moves an evacuated struct's bits into the owner's map, so `sql "UPDATE t SET {r}"` on a value kept from an earlier pass still knows which fields were sent as null |
| Header index (§5.6) | allocated with `__alloc_outside_item()` (REQ region, or the `__Stream` for message loops) | Never in item memory, so a first `header()` call inside a loop does not dangle |
| String cache | the start of the arena | Cleared on every reset and on resume |
| `CTX_JPATH` / `CTX_JDEPTH` | arena / word | Reset per pass |
| Fetch read buffer, SSE parser state | mmap block owned by the open fetch | Freed when the fetch closes |
| PostgreSQL portal and row buffers | the pool connection's mmap buffers | The row loop's lifetime |
| WebSocket partial message | the connection's input buffer | The event loop's |
| Stream parameter item decoding | item memory | The pass |

A test (`tests/api/stream_lazy.kh`) makes the first use of each lazily allocated structure inside a pass, then uses it again in a later pass under GC verify and stress.

### 9.5 Parking without an arena

**A stream connection** (`__Stream`, in the thread heap) holds:
- the fd and the protocol state;
- the send queue and the subscriptions;
- the header copy (§7.1);
- the Worker-lite with its jump buffer;
- the CONN region;
- the cancel flag.

**`__stream_park`,** at the head of a message loop when no message is buffered:
1. Run the pass end (§9.1) and `__store_release_final()` (§9.2).
2. Save the frames from the parking frame up to the stack top into an exact-size block in the `__Stream` (1,312 B measured), and save the words of §9.3.
3. Return the coroutine, its arena reset and released (the memory stage's policy), to the pool. Parked loops do not count against `KHRIP_COROUTINES`.

**Resume:**
1. Take a free coroutine.
2. Copy the frames back to the same stack addresses (`__co_enter` already does this).
3. Restore the words of §9.3.
4. Continue in `__stream_park`.

**Frames below the route** (`__co_main`, `__stream_job`, `__serve_one`, `__dispatch`) hold only the `__Stream`, the connection and the Worker-lite. Stream routes are dispatched through `__stream_job` for exactly this reason.

**What may stay live across the loop (R3).**
- The loop sits directly in the route body (E-S18), so no hidden iterator of an enclosing `for` can be live.
- Values that own sockets, pool connections or growable buffers may not be live across a message loop: `MongoCursor`, `BsonBuilder`, `Buf`, an open row loop or fetch loop (E-S19, reusing `store_raw_type`).

**Idle memory targets** (design targets; the gates of §15 compare with competitors):

| | Today (measured) | Target |
|---|---:|---:|
| Idle keep-alive connection | 9.7 KB | ≤ 1 KB |
| Idle WebSocket in a message loop, browser-like head (1.5 KB of cookies) | — | ≤ 2.5 KB: `__Stream` ≈ 400 B, frames ≈ 1.3 KB, region ≈ 0.25 KB, header copy ≈ 0.1 KB |
| Idle SSE subscriber | — | ≤ 1 KB |
| The same over TLS with our record layer (keys, GHASH tables, IVs) | — | + ≈ 1 KB; with kTLS the keys live in the kernel |
| An idle HTTP/2 connection | — | ≤ 6 KB (a 4 KiB HPACK decoder ring, allocated at first use) |

### 9.6 Store lock, GC records, barrier

- **Waits under the lock.** The store lock is held across a wait only through the audited windows:
  - `__co_wait` (today's);
  - `__fetch_open` (new; same structure as `__fetch`);
  - `__test_run_streams` (new, R9: the test's own context releases with `__store_release_keep` while `s.next()` runs stream coroutines, and takes the lock again exclusively afterwards).

  All three are on the lint list in `tests/run.sh`.
- **Event-loop code never touches store or arenas:** framing, fan-out, pings and TLS records.
- **Publication (R8).** Revision 1's "the item mark narrows publication" is withdrawn: arena memory below the mark can hold store pointers. A wait inside a pass publishes the whole arena range lazily, as store-gc §6.4 does. Regions are never published, because they never hold STORE pointers (§9.1).
- **Parked and subscribed-only streams** publish nothing.

### 9.7 `sql` and `tx` rules in loops (M5)

| Loop | One write outside `tx` | Other rules |
|---|---|---|
| Message loop | allowed per pass: each message is its own request | `tx` inside a pass is allowed |
| Body loop | not allowed. A write needs `tx { }` inside the pass (E-Q4), so each item is one visible transaction | partial progress is loud (§6.6) |
| Fetch loop | the route's rules, as today | — |
| Row loop | no `sql` at all inside it | no `fetch`, `sleep`, stub call or other wait, except `send` (E-Q5) |
| Any of the four | — | the loop cannot sit inside `tx` (E-S13). `send`, `publish`, `subscribe` and `unsubscribe` inside `tx` are errors (E-S14, E-T7) |

The checker in `src/sql.kh` resets its per-request write state at the head of a message loop, and nowhere else.

### 9.8 Tests: the in-process scheduler

- **Single-threaded.** `khc test` stays single-threaded. Streams opened with `open` run as coroutines on a test scheduler, through the audited `__test_run_streams` window.
- **`s.next()`** runs ready coroutines, delivers topic values synchronously, and polls real fds (mocks, `sql`) until a value is queued for `s`.
- **It returns none** when s has ended, or when every coroutine is parked on test input or subscriptions with no timer or fd outstanding. This is decided deterministically, without sleeps.
- **A 10 s guard** fails the test if a real fd never becomes ready.

## 10. HTTP/2 and HPACK (v0.15)

### 10.1 Setup and streams

- **Plain ports.** The first 24 bytes are compared with the h2c prior-knowledge preface; anything else is HTTP/1.1.
- **TLS ports** (v0.16) use ALPN `h2`.
- **Not supported:** `Upgrade: h2c` (deprecated, and a smuggling vector), push, and priorities (`SETTINGS_NO_RFC7540_PRIORITIES=1`).
- **Framing, HPACK, flow control and stream states run in the event loop,** in a per-connection `__H2` object.
- **A complete HEADERS block creates a request:**
  - pseudo-headers go into `__Req`;
  - the other fields go into the header index;
  - `__serve_one` and dispatch are unchanged.
- **Dispatch timing.**
  - A non-stream body dispatches at `END_STREAM`.
  - A stream parameter dispatches at HEADERS, and its DATA arrives as items.
- **Responses** are HPACK HEADERS plus DATA frames into the output queue. gRPC adds trailers.
- **Scheduling.** Streams with data and window are served round-robin each loop turn.

### 10.2 SETTINGS

| Setting | Value |
|---|---|
| `HEADER_TABLE_SIZE` | 4096 |
| `MAX_CONCURRENT_STREAMS` | 100 (`KHRIP_H2_STREAMS`) |
| `INITIAL_WINDOW_SIZE` | 64 KiB |
| Connection receive window | 1 MiB |
| `MAX_FRAME_SIZE` | 16384 |
| `MAX_HEADER_LIST_SIZE` | 65536 |
| `ENABLE_CONNECT_PROTOCOL` | not sent: no WebSocket over HTTP/2 |

### 10.3 Flow control (S2)

- **Receive.** Windows are replenished when the **application consumes** bytes: a stream item is decoded, or a body is handed to a dispatched handler. They are not replenished when bytes are merely appended.
  - Bodies of streams waiting for dispatch count toward a **per-connection buffered-body budget of 4 MiB**. Past it, the server stops replenishing windows and the peer blocks.
  - `KHRIP_MEMORY` bounds the total across connections.
  - WINDOW_UPDATE is sent at half a window.
- **Send.** A stream sends while both its window and the connection window allow.
  - Queued bytes count toward `KHRIP_STREAM_QUEUE`.
  - A zero window with pending data for 30 s gives RST_STREAM (stream) or GOAWAY (connection).
- **Data dribble (CVE-2019-9511).** The server does not send a DATA frame smaller than min(1 KiB, the rest of the message) while it waits for more window. A WINDOW_UPDATE that adds less than 1 KiB, and does not cover the rest of the message, costs control budget (§10.4).

### 10.4 Defenses (each one a gate of step 16)

| Attack | Defense |
|---|---|
| **Rapid reset** (CVE-2023-44487) | A reset stream's handler keeps counting against `MAX_CONCURRENT_STREAMS` until it actually ends. Excess streams wait in a queue bounded at 2× the limit |
| **MadeYouReset** (CVE-2025-8671): frames that make the *server* reset streams | Server-sent resets caused by the client's protocol errors count in the same reset budget as client resets. Their handlers keep counting until they end |
| **Reset budget that does not break proxies** | A token bucket per connection: every completed stream earns a token, every reset of an unfinished stream costs one; it starts at 1,000. Envoy aggregating many users, with a few percent of legitimate cancels, stays positive; an open-and-reset attacker drains it and gets GOAWAY(ENHANCE_YOUR_CALM). Revision 1's fixed "100 per second" would have cut off such proxies |
| **Coroutines per connection** | At most 32 handlers run per connection; the rest wait in the per-connection queue. Stream parameters dispatch at HEADERS, so without this cap, 256 connections could exhaust the arena slots |
| **CONTINUATION flood** | The header block is bounded by `MAX_HEADER_LIST_SIZE`, with at most 32 CONTINUATION frames; HPACK is decoded incrementally |
| **HPACK bomb** | Decoded size counts name + value + 32 per field. Past 64 KiB, decoding only keeps the table in sync, and the stream gets 431 |
| **Huffman and table-size abuse** | An FSM decoder. Invalid padding or EOS, or a size update in the wrong place or above the setting, is COMPRESSION_ERROR |
| **Control-frame floods** | A budget: PING, SETTINGS, WINDOW_UPDATE, PRIORITY, empty DATA and RST each cost 1, and payload bytes refill it. More than 10,000 without progress, or 1,000 per second, gives GOAWAY |
| **Field values** (RFC 9113 §8.2.1) | Names must be lower case with no SP, controls or `:` (except pseudo-headers). Values may not contain NUL, CR or LF, or start or end with SP or HTAB. Connection-specific fields and `te` other than `trailers` are rejected. A violation is malformed: RST_STREAM(PROTOCOL_ERROR), or 400 |
| **Stream id abuse, header timeout, unread ACKs, zero window** | As RFC 9113 requires; 10 s for the preface and headers; output queue bounds; the stall timers of §10.3 |

### 10.5 HPACK

- **Decoder:**
  - the static table;
  - the dynamic table as a 4 KiB byte ring, allocated at the first insertion;
  - a Huffman FSM (generated into `lib/hpack_tables.kh`).
- **Encoder:**
  - a perfect hash over the static table;
  - incremental indexing for common content types, `server` and `grpc-status: 0`;
  - a per-connection cache of encoded response heads, so a typical head is 3–5 bytes after the first;
  - Huffman only when it is shorter.

## 11. gRPC, Connect, gRPC-Web (v0.15)

### 11.1 Names and messages

- **Package and service** come from `service a.b.C`, else from the main file's stem: `shop.kh` gives `shop.Shop`.
- **The request message** is a single struct parameter itself, or a generated `MRequest` with one field per parameter. Adding a second parameter to a single-struct rpc therefore changes its request type, which is breaking (E-P6; GRPC.md says so).
- **The response message:**
  - a struct is itself;
  - `[T]`, scalars and maps are wrapped (`MResponse { items }`);
  - a 204 result is `google.protobuf.Empty`.
- **A REST binding** is exactly a route, with today's JSON.

### 11.2 Protobuf from types (M4)

| Khrip | proto3 |
|---|---|
| `int`, `float`, `bool`, `str` | `int64`, `double`, `bool`, `string` (valid UTF-8 required) |
| `[T]`, `map[K, V]` | `repeated` (packed), `map` (wrappers where proto cannot hold V) |
| `T?` | `optional T` |
| **a non-optional field with no default** | **`optional T`**. A message that lacks it is INVALID_ARGUMENT `orders.NewOrder.amount is required` (the wire format is unchanged) |
| a field with a default | `optional T`; absent means the default |
| a struct field | a message field (presence is native); missing is INVALID_ARGUMENT |
| enum | `E_UNSPECIFIED = 0` first; reading 0 or an unknown value into `E` is INVALID_ARGUMENT, into `E?` it is none |
| variants | `oneof` |
| `[T]` missing | empty, as proto cannot tell |

`json_name` is the Khrip field name, so Connect JSON matches REST JSON.

**The cost of M4:** Go and C# clients generated from the `.proto` see presence wrappers for required fields (Go `*int64`). §23 asks the owner to accept this.

### 11.3 `<main>.proto`: the field-number lock (C10)

- **The file is named after the main file:** `app.kh` gives `app.proto`, and `shop.kh` gives `shop.proto`. It sits beside the main file.
- **When it is written.** `khc run` and `khc test` write it when it would change. `khc check` never writes.
- **`khc -o` (a release build)** writes nothing, and fails if the file is missing or out of date (E-P10, E-P9). A release never invents field numbers.
- **Numbering.** The first numbers follow declaration order. After that:
  - kept fields keep their numbers;
  - new fields take the next free number;
  - removed fields are `reserved`.
- **Breaking changes are errors** (E-P1–E-P6), and rename candidates get a warning (W-P7).

### 11.5 Deadlines, metadata, health, reflection

- **Deadlines (S8).** `grpc-timeout` and `Connect-Timeout-Ms` set the deadline:
  - for unary calls, `min(client deadline, KHRIP_TIMEOUT)`;
  - for streams, `KHRIP_TIMEOUT` caps only the phase before the head, and the client's own deadline applies throughout.
- **Cancellation.** `RST_STREAM(CANCEL)` and client aborts set the cancel flag.
- **Metadata.**
  - Request metadata is read with `header(name)`; `-bin` values come as base64 text.
  - `set_header` before the first message sends initial metadata.
  - Trailers carry only status and message.
- **Compression** is not supported: identity is advertised, and a compressed message gets UNIMPLEMENTED.
- **Health.** `grpc.health.v1` is always served, NOT_SERVING while draining.
- **Reflection** (`grpc.reflection.v1` only, O3) is **off by default** (S9). It is on with `KHRIP_GRPC_REFLECTION=1` and under `khc run`.

### 11.6 Connect and gRPC-Web

- **gRPC-Web** is binary only (`application/grpc-web`, `+proto`; text mode is cut, O3), over HTTP/1.1 or h2c, with trailers as a final frame and CORS from `KHRIP_CORS`.
- **Connect** covers unary and server streaming, JSON or proto, over HTTP/1.1 or h2c. The error body is `{"code":"not_found","message":"..."}` with the status from §11.4.
- **Not supported:** Connect GET, and client or bidi streams over Connect (gRPC covers them).

### 11.7 Codec

- **Table-driven,** with per-message tables in DATA. Strings are zero-copy views, validated as UTF-8 with SIMD.
- **Backward writer:** no size pass, tags pre-encoded.

## 12. TLS server, HTTP/2 client, client stubs (v0.16)

### 12.1 Certificates and keys

- **Certificates and keys.** `TLS_CERT` is a PEM chain (leaf first); `TLS_KEY` is the matching key. Both take comma lists for SNI, or PEM text from the environment.
- **Only ECDSA P-256 keys** are accepted (PKCS#8 or SEC1).
  - RSA keys stop the start with S-TLS4, which shows the `certbot --key-type ecdsa` and `openssl ecparam` commands.
  - RSA-PSS signing is deferred past v0.16 (D3).
- **Start checks:** the PEM parses; the key matches the leaf (sign and verify); each certificate is signed by the next; the leaf has a SAN. Expiry within 14 days, an included root, or a world-readable key file each get a warning.
- **Reload (S10).**
  - Every 60 s the files' (mtime, size, inode) are compared with the last attempt, not with the last success.
  - A failed load is **retried every 60 s until it succeeds**. A certificate renewed before its key is a transient mismatch that heals by itself.
  - On success, new handshakes use the new pair.
- **Key memory** is a dedicated mmap with `MADV_DONTDUMP` and `mlock`, zeroed on reload. **PEM text taken from the environment is zeroed in place** in the process's environment block after parsing, so `/proc/<pid>/environ` no longer shows it (S10).

### 12.2 Handshake

**The state machine runs in the event loop.** Expensive steps (ECDHE, signing, certificate verification for mTLS) run **off the loop** as handshake jobs (P5):
- a per-worker queue, run between loop turns;
- a CPU budget per turn: when requests are waiting, handshake jobs use at most half of the turn;
- established connections therefore wait at most one handshake job (about 0.1 ms) behind a flood.

**Defenses (S7):**
- at most 64 concurrent handshakes per client IP (/64 for IPv6) per process;
- at most 2,048 handshakes in progress per thread;
- beyond either: close, and count.

**Protocol choices:**
- TLS 1.3 only;
- X25519 preferred, then P-256; HelloRetryRequest with a cookie;
- `ecdsa_secp256r1_sha256` signatures;
- SNI selects a certificate by SAN (exact, then one-level wildcard), defaulting to the first;
- ALPN offers h2, then http/1.1;
- `METRICS_PORT` stays plain.

**Cipher.**
- TLS_AES_128_GCM_SHA256 always: it is mandatory for every TLS 1.3 client.
- TLS_AES_256_GCM_SHA384 only if it is the only one offered.
- ChaCha20-Poly1305 only if it is the only one offered, using the existing scalar code. **No ChaCha20 AVX2** (O3).

**Not in v0.16:** session tickets (O3; ECDSA signing is cheap, so resumption saves little), 0-RTT, TLS 1.2, OCSP stapling, certificate compression, P-384 and Ed25519 keys, post-quantum groups, and RSA keys.

### 12.3 Constant-time crypto (S6, D3)

| Piece | How |
|---|---|
| P-256 and Curve25519 field arithmetic | **Transcribed from fiat-crypto** (formally verified, constant time), emitted with `mulx`/`adcx`/`adox` in `src/cx.kh` following the CryptOpt-generated schedules (formally checked against fiat), with a plain `mul` fallback. Licenses checked at step 23 |
| P-256 fixed-base multiply (signing, keygen) | A comb over precomputed multiples of G in DATA; masked loads over the whole table; complete addition formulas (Renes–Costello–Batina) |
| **Variable-base multiply (ECDHE with P-256)** | A new constant-time ladder over the same field code. Today's `__ecdh_shared` → `__pt_mul` branches on each bit (lib/pk.kh:603) and is never used by the server |
| X25519 | The Montgomery ladder with `cswap`, on the fiat field |
| ECDSA nonces | RFC 6979 HMAC-DRBG, hedged with 32 bytes from `getrandom`. **An unhedged KAT mode** (test builds only) reproduces the RFC 6979 vectors exactly |
| AES key expansion | **`AESKEYGENASSIST`.** Today's S-box indexing by key bytes (lib/cipher.kh:24–45) is removed from the server path, and from the client path too |
| Inversion mod n | Fermat with a fixed window |
| Checking | **ctgrind**: test builds emit Valgrind client requests that mark keys, nonces and scalars as undefined, and memcheck flags any branch or address that depends on them. **dudect** runs nightly as a statistical second check. The emitted code is reviewed for secret-dependent branches and indexes. **Wycheproof** vectors and random cross-checks against Python `cryptography` and OpenSSL run every time |

### 12.4 Record layer and kTLS (D3)

- **kTLS first.** After the handshake, the server tries `setsockopt(TCP_ULP, "tls")` with TLS 1.3 AES-GCM keys for TX and RX. On success the kernel encrypts and decrypts, `writev` and `sendfile` work unchanged, and no keys stay in user memory.
- **KeyUpdate under kTLS.** Rekeying a kTLS socket needs a recent kernel (support for TLS 1.3 rekey landed around Linux 6.14; to verify at step 22). Where the kernel cannot rekey, a peer KeyUpdate ends the connection gracefully, and the server never starts one; a key lasts 2^24 records.
- **Our own record layer otherwise:**
  - decrypt in place;
  - encrypt into a ciphertext segment;
  - a dynamic record size, about 1,400 B after idle, then 16 KiB;
  - `close_notify` on a graceful close.
- **AES-GCM implementation:**
  - first, 8-way AES-NI with aggregated GHASH (PCLMULQDQ);
  - VAES/VPCLMULQDQ widening only if the parity gate needs it and the owner wants it (§23).
- **Measured first.** **The bench VM has no kTLS** (§2), so kTLS is measured on a host that has the `tls` module (§15.4) before step 26 decides how much of our own AES-GCM to build.

### 12.5 mTLS (optional)

- **Configuration.** `TLS_CLIENT_CA` gives the roots, and `TLS_CLIENT_AUTH` is `require` or `optional`.
- **Verification** reuses `__verify_chain` with no name check, checks the validity dates, and requires clientAuth in extKeyUsage when that extension is present.
- **`client_cert() -> str?`** gives the first URI SAN (SPIFFE), else the first DNS SAN, else the first email SAN, else the CN. It is documented in SERVER.md.

### 12.6 HTTP/2 client in `fetch`

- **Upgrade to h2.** For `https://`, ALPN offers h2 and http/1.1; an h2 connection becomes the thread's multiplexed connection for that origin.
- **Each fetch is one stream.** The connection reader runs in the event loop and wakes the coroutine.
- **GOAWAY.** Unprocessed streams are retried on a new connection.
- **Idle connections** get a PING at 30 s and are closed at 90 s.
- **`http://`** stays on HTTP/1.1, except for gRPC stubs, which use h2c.
- **Header validation (S2)** happens before encoding, as in §3.4.

### 12.7 `.proto` import and client stubs (S4)

- **`khc proto quotes.proto`** writes types, bodiless rpcs and a `service` line.
  - It refuses proto2, `Any`, `Struct`, groups and extensions (E-I1–E-I3).
  - `bytes` becomes base64 `str`.
  - `uint64` values above 2^63-1 are decode errors.
- **A stub call** runs over the h2 client.
  - Its deadline is `min(30 s, the remaining request deadline)`, sent as `grpc-timeout`.
  - The trace context is passed on.
  - **`int32` fields are range-checked** when encoding: an out-of-range value panics with `GetQuote: qty = 3000000000 does not fit int32` (C10).
- **Upstream codes are never passed through (S4):**

  | Upstream code | Result |
  |---|---|
  | OK | the value |
  | NOT_FOUND | 404 (none when read into `T?`; E-R9 requires `\| 404` otherwise) |
  | UNAVAILABLE | 503 |
  | DEADLINE_EXCEEDED | 504 |
  | **any other code**, including UNAUTHENTICATED and PERMISSION_DENIED | **502** |

  The upstream code and message are logged (`khrip: rpc GetQuote: upstream PERMISSION_DENIED "..."`), never sent to the client: an upstream credential problem must not look like the caller's own 401 or 403.
- **No retries or hedging.**

## 13. HTTP/3: at the edge

**Decision:** no QUIC or HTTP/3 in Khrip. CDNs and load balancers terminate HTTP/3 and speak HTTP/1.1 or HTTP/2 to Khrip.

**Reasons:**
- **The gains are elsewhere.** QUIC's gains are on lossy last-mile links, not on data-center links.
- **CPU per byte is higher.** User-space QUIC costs more CPU per byte than TCP+TLS: published measurements show up to about 45% lower throughput than HTTP/2 over fast links (Zhang et al., WWW 2024). That would break rule 1.
- **The stacks are large:** 40–100k lines in other projects, an estimated 12–18k Khrip lines.
- **Zero tokens either way.**

**Triggers that would change the decision:**
- direct client-facing deployments over lossy networks;
- an in-kernel QUIC (to be adopted the way kTLS is);
- WebTransport demand;
- a measured user-space QUIC within 1.2× of TCP+TLS CPU;
- load balancers that speak HTTP/3 to origins.

## 15. Performance plan (rule 1)

### 15.1 Method v2 (D6, P2)

- **Open-loop load at a constant rate:**
  - `wrk2 -R` for HTTP/1.1 and TLS (latency from the intended send time, corrected for coordinated omission);
  - `h2load --rps` for HTTP/2;
  - `ghz --rps --async` for gRPC;
  - for WebSocket and SSE, our Go clients (`bench/ws/load`, `bench/sse/fanout`), which send on a fixed timetable and measure from the scheduled time.

  wrk2, h2load and ghz are built from source into `bench/tools/`. Only `wrk` is installed today.
- **The same offered load for every server:**
  1. A sweep finds the best mainstream server's highest sustainable rate: p99 within the scenario's latency target, and no errors.
  2. Every server then runs at 50%, 80% and 95% of that rate.
  3. Khrip's own highest sustainable rate is measured too.
- **Durations.** 60 s of warm-up at the 80% rate for every server; this is what Java C2, .NET tiered PGO, V8 and JSC need, and the same applies to all. Then ≥ 60 s of measurement per rate: at 10k req/s that is 600k samples, of which 600 lie above p99.9. Three repetitions, with servers interleaved; the median is reported with its range.
- **Placement on the 4-core machine.** The server runs on cores 0–1 and the load on cores 2–3 (`taskset`). Each server gets two cores' worth of workers:

  | Server | Two-core setting |
  |---|---|
  | Khrip | `THREADS=2` |
  | Go | `GOMAXPROCS=2` |
  | .NET | `DOTNET_PROCESSOR_COUNT=2` |
  | Java | `-XX:ActiveProcessorCount=2` |
  | Node | `cluster`, 2 workers |
  | Bun | 2 processes with `reusePort` |
  | Python | `uvicorn --workers 2` |

  The load generator's CPU is reported. A run whose generator exceeds 80% of its cores is marked *client-bound* and goes to the two-host list.
- **Metrics:**
  - latency p50, p99 and p99.9 at each common rate;
  - **CPU per operation**: the server's utime plus stime from `/proc` over the measurement, divided by the operations;
  - the highest sustainable rate;
  - peak RSS under load.
- **Memory per connection** is an **RSS slope**:
  1. open 10k, 50k and 100k idle connections (WebSocket, SSE, keep-alive) with browser-like heads (1.5 KB of cookies);
  2. force a GC in each runtime (Go `debug.FreeOSMemory`, .NET `GC.Collect` with compaction, Java `System.gc()`, Node `--expose-gc`, Bun `Bun.gc(true)`, Python `gc.collect`), wait 10 s, and read RSS summed over the server's processes;
  3. report ΔRSS/Δconnections from 10k to 100k, and the base.

  Runtime settings are the idiomatic defaults (GOGC 100, ASP.NET Server GC, Java G1 with its default heap) and are printed in every report.
- **100k connections from one host.** The client binds to 16 loopback source addresses (127.0.0.2–17), each with up to 64k ports, with raised `RLIMIT_NOFILE` and `fs.nr_open`.
- **The gate rule.** Every gate in §15.3 means *at least as good as the best of Go, C#, Java, Node, Bun and Python on the same run*: latency and CPU per operation at each common rate, the highest sustainable rate, and the RSS slope. Rust is reported, not gated. Gates marked *internal* compare Khrip with itself.

### 15.4 What needs a second host

- **Fan-out and broadcast above about 200k deliveries/s,** including revision 1's 10k subscribers × 1,000 msg/s (10M/s): the clients need more than 2 cores.
- **TLS handshake floods at full server capacity.** The client's P-256 verify (87 µs in OpenSSL) costs about 3× the server's signature (27 µs), so saturating 2 server cores takes about 6 client cores.
- **WebSocket echo above about 200k msg/s, and HTTP/2 and gRPC highest-rate runs** that turn out client-bound.
- **kTLS** (the bench VM's kernel has no `tls` module).
- **Anything with a real NIC** (interrupts, GRO/GSO), and 1M connections.

**Request (§23):** a second machine with ≥ 16 cores and the `tls` module, on a ≥ 10 Gbit/s link to the first.

### 15.5 Crypto targets (D3, P1)

OpenSSL 3.0.13 was measured on the bench machine (`openssl speed -seconds 1 -elapsed`, 2026-10-25). Each step measures again in the same run as Khrip.

| Primitive | Khrip today | OpenSSL | Gate: ≥ 0.9× OpenSSL |
|---|---:|---:|---:|
| X25519, one operation | 240 µs | 39.2 µs (25,512/s) | ≤ 43.6 µs |
| P-256 ECDH, one operation | — (variable time) | 63.8 µs (15,669/s) | ≤ 70.9 µs |
| ECDSA P-256 sign | — | 26.8 µs (37,264/s) | ≤ 29.8 µs |
| ECDSA P-256 verify (mTLS only) | 480 µs | 86.8 µs (11,518/s) | ≤ 96.5 µs |
| AES-128-GCM, 16 KiB records | 537 MB/s | 14.1 GB/s (VAES, AVX-512) | ≥ 12.7 GB/s |
| AES-128-GCM, 1 KiB records | — | 9.1 GB/s | ≥ 8.2 GB/s |
| RSA-2048 sign | — | 372 µs | deferred past v0.16 |

**Assessment:**
- **Curves.** Parity for the curves is plausible: CryptOpt reports performance on par with hand-written assembly for these fields, and we transcribe its schedules.
- **AES-GCM.** OpenSSL uses VAES with AVX-512 on this CPU. An 8-way AES-NI and PCLMULQDQ implementation reaches, as an estimate to be measured, a third to a half of that.
- **kTLS** would put the record layer at kernel speed, but it is not available here.

So the AES-GCM gate is likely to need either a VAES-512 implementation, or deployment on kernels with kTLS, or an owner exception. §23 asks now rather than at step 26.

### 15.6 Where the speed comes from

- **Serialize once:** topic values are encoded once per wire format into shared frames.
- **No code per subscriber:** a delivery is one queue append plus a share of one `writev`.
- **One hop per thread** through a segmented MPSC queue, with eventfd writes coalesced.
- **Zero-copy framing** into reserved prefix space, and in-place parsing.
- **SIMD unmasking, UTF-8 validation and array splitting.**
- **No lock per token** (§9.2).
- **Memory per connection close to the protocol state:** pooled buffers, and parking without an arena.
- **One `writev` per connection per loop turn.**
- **A cached HPACK head per connection.**
- **A table-driven protobuf codec with a backward writer.**
- **A timer wheel.**
- **kTLS, or our AES-GCM,** with handshake jobs off the loop.
- **No proxy hop** for HTTP/2, gRPC-Web or TLS.

### 16.3 Prompt plus program per task

**The weight.** The model reads the prompt and writes the program, and the two are priced differently. Let w be the price of one prompt token over the price of one output token. At Anthropic's list prices:
- **w = 0.02** for a cached prompt (a cache read costs a tenth of input, and input a fifth of output). The eval sends the same Khrip prefix for every task, so it is cached after the first.
- **w = 0.2** uncached.
- OpenAI's ratios are lower, about 0.0125 and 0.125.

**The prompts.**
- Khrip: the planned core (3,000) plus the task's chapters: streams 451; SQL 896; gRPC 655.
- Competitors: one rule line of about 25 tokens.

### 16.5 Places for a silent mistake

**Khrip, with this design:**

| # | Mistake | Status |
|---|---|---|
| S1 | Several replicas: broadcasts reach only one process | The chapter says "in this process"; a start log line every time; a `shared` bridge later |

| S9, S10 | The `.proto` deleted and regenerated / a field renamed in Khrip only | E-P10 (release builds need the file); W-P7 |
| S11 | A store value read before a loop is a snapshot | Warning W-S1; one chapter sentence |
| S12 | A history read with `sql` may repeat values committed during `subscribe` | Documented; never a loss |
| S13 | A POST import fails at line 500 after 499 commits | **Loud now**: E-Q4 needs `tx` per item, and the message says how many items were saved |

**Loud in Khrip, silent in at least one competitor program:**
- **Cancellation:** the forgotten upstream cancellation (Go without `r.Context()`; C# without `[EnumeratorCancellation]`).
- **Upstream parsing:** `bufio.Scanner` stopping at its line limit (Go P1).
- **Middleware:** SSE stopping behind a middleware that hides `Flush` (Go production add-on).
- **Slow clients:**
  - a slow client stalling a room (Python P2);
  - messages silently dropped for a slow client: Bun's defaults (`backpressureLimit` 16 MB, `closeOnBackpressureLimit` false) drop silently (Bun P2), and C#'s `TryWrite` result is easy to ignore.
- **History:** a race between history and live messages (Python P2; SignalR).
- **WebSocket framing:** fragmented messages ending the connection (C# P2).
- **Origin:** a cross-origin WebSocket accepted (Node `ws`, Bun P2, Python).
- **REST through gRPC transcoding:** `int64` ids rendered as JSON strings, and 200 instead of 201 (Go P4, C# P4).
- **Error details:** database error text leaking in `codes.Internal` (Go P3).
- **Backpressure in Node:** `call.write` ignoring backpressure (TS P3).
- **Bad path ids:** a non-numeric path id answering 404 instead of 400 (TS P4).
- **Missing defenses:** no header timeout or body limit (Go and Node defaults).

## Appendix A. Language proposal: anonymous struct types and literals (D5)

A separate proposal for the tokens stage (§1). This design assumes it lands before v0.14. It is not part of the protocol surface.

**A1. Anonymous struct types.**
- **Where they may be written:** anywhere a type is written (fields, list and map elements, parameters, results, `stream`, `topic`, `store`, `let` annotations).
- **Grammar:**

  ```
  type      := name | '[' type ']' | 'map' '[' type ',' type ']' | type '?' | 'stream' type
             | '{' field (',' field)* [','] '}'                       // new
  field     := ident ':' type ['=' expr]
  ```

- **Identity.** Anonymous types are structural: the same field names with the same types and defaults, **in the same order**, are the same type (revised in the tokens stage, part 1: the order is part of the type, because fields go to JSON and BSON in that order — a MongoDB sort `{ score: -1, name: 1 }` is not `{ name: 1, score: -1 }`). A literal with a target takes the target's order, as `T { ... }` does; a literal without one keeps its own. Types that differ only in order or in a default do not mix, and the error says which. Named types stay nominal. A value of an anonymous type converts to a named type with the same fields only through a literal or spread (`User { ...x }`).
- **Names in errors and generated files.** Diagnostics print the type (`{ token: str }`). gRPC and the `.proto` name an anonymous message by position: `<Rpc>Request` or `<Rpc>Response` for parameters and results, `<Parent><Field>` for nested ones. Renaming a field renames its nested message, which the lock reports as W-P7.

**A2. Anonymous struct literals with a known target type.**
- **Grammar:**

  ```
  primary   := ... | '{' sfield (',' sfield)* [','] '}'               // new, in expression position
  sfield    := ident ':' expr | ident | '...' expr
  ```

  In expression position, `{` followed by an identifier and then `:`, `,` or `}`, or followed by `...`, starts a struct literal. A string key starts a map literal, as today, and `{}` is a map unless the target is a struct type. In statement position `{` is still a block.
- **The target type comes from:**
  - a typed `let` or `var`;
  - assignment to a store variable, field or index;
  - an argument for a typed parameter;
  - `return` with the declared result;
  - `send` in a `stream T` route;
  - `publish` to a topic;
  - an element of a list literal whose own target is known;
  - a field value inside another literal.
- **Checks.** The literal is checked exactly like `T { ... }`: missing required fields, unknown fields, types.

**A3. A literal with no target type (option, §23).** `let req = { model: "m", stream: true }` gets the closed anonymous type of its fields. It is accepted as a `fetch` body, by `to_json` and in `send` to `stream str`. Field access on it is checked against that type.

**Traps:**

| Trap | Assessment |
|---|---|
| A misspelled field in an A3 literal sent upstream (`modle`) | Silent, as in a Python dict or a TypeScript object; also as with today's map literals. Only A3 has it |
| Structural identity mixes unrelated shapes (`{ id: int }` from two places) | Possible, as in TypeScript; low risk in handlers |
| Field order: with order-insensitive identity, the first place a type is written fixes the JSON and BSON order of every value of it (an unrelated helper's `{ name: 1, score: -1 }` reorders a later sort document) | **Removed** in the tokens stage, part 1: the order is part of the type; a mismatch is an error naming it |
| `{k: v}` without a target was a map keyed by the value of `k` and is now a struct with field `"k"` (`to_json`, `fetch` and `call` bodies, `to_bson`, sql jsonb) | **Loud** since the tokens stage, part 1: a bare name as a map key is an error, and a literal that would have been such a map (field names are int or str variables, values do not mention them) is an error with the hint `{(k): v}` or `{"k": v}` |
| `Circle c => { area: 1 }` in a `match` arm parses as a block | A targeted error, **E-A1** `a struct literal as a match arm needs parentheses or its type: ({ area: 1 })` |
| `{}` for an empty struct whose fields lack defaults | An error listing the missing fields |
| Wrong named type for a literal (`NewUser { ... }` where `User` is expected) | **Removed** by A2: the target decides |
| Long anonymous types in signatures hurt readability | A style hint: name a type used twice (warning W-A2 when an identical anonymous type is written three times) |

**Prompt text** (core, "Values"; 96 o200k, 94 Claude):

```markdown
- `{ text: t }` (names without quotes) is a struct literal whose type comes from
  where it goes: `return`, `send`, a typed parameter, field or list; with no
  such place, its type is its fields. `{"k": v}` stays a map. A struct type can
  be written in place: `-> { token: str }`, `choices: [{ delta: { text: str? } }]`.
```
