# PR #1 «MongoDB и ClickHouse»: итоговый анализ

**Объект:** https://github.com/akhripunkov/khrip/pull/1, ветка `pr1` (6e945fc, основана на 1bc4605): 61 файл, +5237/−43.
**Пробное слияние с main** (57b0f5a, работа v0.13): локальная ветка `pr1-merged` (4488dd7).
**Номера строк** даны по `pr1`. В lib/bson.kh, lib/mongo.kh, lib/clickhouse.kh, lib/db_http.kh и src/drivers.kh они совпадают с `pr1-merged`.

**Как проверяли.** Пять независимых проверок:
- язык и API для ИИ;
- протокол MongoDB;
- ClickHouse и HTTP;
- интеграция с рантаймом и v0.13;
- производительность и тесты.

Затем каждую существенную находку отдельно перепроверили. Использовали:
- настоящие MongoDB 8.0 и ClickHouse 25.8 (те же образы, что закреплены в PR);
- собственные контейнеры: replica set, mongod с TLS, ClickHouse с TLS;
- враждебные mock-серверы на Python;
- фаззинг;
- сравнение с официальными Go-драйверами.

Все временные базы, пользователи, контейнеры и worktree удалены. На GitHub ничего не публиковалось.

**Обозначения:**
- «Подтверждено» — находку независимо воспроизвели при перепроверке.
- «Не перепроверялось» — находка низкой важности, её видел только один проверяющий.
- Оценки и предложения помечены как мнение отдельно от фактов.

## 1. Итог

1. PR добавляет два нативных драйвера, написанных как библиотечный код на Khrip:
   - MongoDB: OP_MSG, BSON, SCRAM-SHA-256, пул, курсоры;
   - ClickHouse: HTTP(S), RowBinaryWithNamesAndTypes.

   Кроме того, в PR есть:
   - типизированные кодеки `to_bson`/`from_bson`/`ch_encode`/`ch_decode` на существующих дескрипторах типов;
   - запрет сетевых операций драйверов внутри `tx`;
   - очистка ресурсов при `fail` и panic;
   - попутные исправления: optional-map, SIGPIPE, пустая TLS-запись.
2. Низкоуровневая часть сделана сильно:
   - фаззинг 225 тыс. испорченных BSON-документов и ~56 тыс. OP_MSG-кадров не дал ни одного падения, а решения валидатора на 100 % совпали с независимым эталоном;
   - разбор HTTP строгий, SCRAM корректен;
   - повторов записи нет, `unknown_outcome` выставляется честно.
3. Все тесты PR проходят на настоящих серверах. Пробное слияние с main даёт 295 пройденных тестов из 295. Программы без драйверов выросли на 160 байт, время запуска и память в простое не изменились.
4. Найдена и подтверждена одна критическая ошибка памяти: `MongoCursor` в `store` указывает в освобождённую арену, процесс падает.
5. Найдено и подтверждено восемь проблем высокой важности:
   - тихая порча и потеря данных через `to_bson` (вложенный `Bson`, `none` → null);
   - SQL-инъекция — самый короткий путь написать запрос к ClickHouse;
   - проигнорированный результат записи выглядит как успех;
   - `ch_insert` не пишет в типичные схемы таблиц;
   - TLS к настоящему mongod не работает;
   - BSON расходует арену примерно в 100 раз больше объёма данных: запрос падает примерно на 12 МБ.
6. API для ИИ получился низкоуровневой библиотекой. Программы на MongoDB лишь в 1,4–1,6 раза короче Go, у задач на PostgreSQL — в 2,31 раза. KHRIP.md, который и есть промпт, не называет ни одной функции драйверов.
7. **Вливать в текущем виде не стоит.** Вливать можно после одного раунда исправлений (шаг А в разделе 8): в основном это небольшие правки в lib/bson.kh, lib/mongo.kh, lib/tls.kh, src/api.kh и src/drivers.kh. Форму API (fail-closed, типизированные выборки, форма `ch "..."`) должен решить владелец. До этого драйверы лучше пометить экспериментальными.
8. С v0.13 при слиянии был только конфликт в константах ctx. При вливании нужно обновить проекты GC (§3.3, §6.5) и UTF-8 (таблица D9), а два новых окна снятия блокировки store переделать к шагу 4 GC.

## 2. Сильные стороны

**Архитектура и владение ресурсами**
- Драйверы написаны библиотечным кодом, без libc, FFI и процесса-посредника; бинарник остаётся статическим.
- Кодеки выводят тип по аннотации, как `from_json`, и нового синтаксиса не требуют: `let e: Event? = from_bson(doc)`, `let rows: [Row]? = ch_decode(body)`. Простые фильтры пишутся в одну строку: `to_bson({"_id": id})`.
- Время жизни данных чётко разделено:
  - соединения, таблица пула и приёмные буферы лежат в mmap;
  - заголовок `Buf` хранится внутри блока соединения (mongo.kh:277-292);
  - ответы копируются в арену запроса.

  Указателей из пула в арену и обратно не найдено.
- Очистка в конце запроса генерируется для каждого используемого драйвера отдельно и не выделяет память. Она срабатывает после `fail` и panic, до сброса арены.
  - Проверено настоящими паниками по памяти: 5 подряд в маршруте с MongoDB, fd 6→5, следующий запрос успешен.
  - В программах без драйверов `__db_end` пуст.
- Состояние драйверов лежит в coroutine-local части ctx. `CTX_TLS_PENDING` регистрируется аккуратно: каждый ранний выход идёт через `__tls_fail` → `__tls_free`.
- На время сетевого ожидания блокировка `store` отпускается, как у `fetch`. Читатель store отвечал за 0,4 мс, пока пишущий маршрут 1 с ждал ClickHouse.

**MongoDB**
- BSON-валидатор безопасен по памяти и точно следует спецификации:
  - через `bson_valid`, все `bson_get_*`, `from_bson` в 6 форм и `__mongo_response` прогнали 225 020 мутированных документов и ~56 тыс. кадров OP_MSG — 0 падений;
  - решения на 100 % совпали с независимым валидатором BSON 1.1 на Python;
  - все проверки длины выполняются до разыменования.
- OP_MSG разбирается строго: `responseTo`, маска флагов, CRC32C, лишние байты, уникальность ключей, тип `ok`, форма `writeErrors` и `writeConcernError`.
- SCRAM-SHA-256 корректен против враждебного peer:
  - чужой nonce, неверная подпись, отсутствие `done` и 1 000 001 итерация отклоняются;
  - 1M итераций занимают 1,47 с, но сопрограмма при этом уступает управление.
- `unknown_outcome` устроен разумно:
  - ошибка рукопожатия или аутентификации → false;
  - потерянный или испорченный обмен → true;
  - на настоящем replica set `w=2` даёт code 100 и `unknown_outcome=true`;
  - устаревшие сокеты пула обнаруживаются, команда доставляется ровно один раз;
  - `w:0` отклоняется до отправки.
- Пул держит лимит и изоляцию:
  - под 200 одновременными запросами у сервера ровно 32 соединения;
  - соединения разделены по учётным данным;
  - при THREADS=4 3 200 пар вставка+чтение с кириллицей, CJK, emoji, Int64 min и −0.0 прошли без единой ошибки.
- Типы точно переживают запись и чтение через сервер, что проверено серверными `$type`/`$toString`/`$binarySize`:
  - Int64 на границах, −0.0, ±Inf, NaN, 5e-324;
  - Decimal128, Binary со всеми 256 значениями байта, ObjectId, Date на крайних int64;
  - NUL внутри строк, типы-суммы, `[bool?]`, `map[str, float?]`;
  - null отличается от отсутствующего поля.

**ClickHouse и HTTP**
- Разбор ответа в db_http.kh строгий. На враждебном mock правильно обработаны все случаи, кроме одного (Н10):
  - зависание посреди тела и посреди чанка, подача по 1 байту (таймаут ровно 300–301 мс);
  - голый LF, CL вместе с TE, `Content-Length: +2`, отрицательный CL, 24-значный размер чанка;
  - `gzip, chunked`, RST посреди ответа, три промежуточных ответа 102.

  65 535 однобайтовых чанков разбираются за 61 мс.
- Декодер RowBinary проверяет границы каждого чтения. Каждый неподдержанный тип ClickHouse (Map, Tuple, UUID, Enum8, Decimal, Int128, JSON, Variant и другие) даёт понятную ошибку с именем типа, а не мусор.
- Экранирование параметров верно для всех 256 значений байта, невалидного UTF-8, завершающей обратной косой черты и кавычек.
- Вставка и обратное чтение точны: Int64 min/max, NaN, ±Inf, −0.0, Nullable, вложенные массивы. Хранимые байты проверены на сервере.
- Учёт допуска (admission) без утечек. При THREADS=4 и max_inflight=2:
  - 200 вставок и 200 выборок прошли успешно;
  - 40 принудительных таймаутов честно разделились: 20 запросов ушли на сервер (`unknown_outcome=true`), 20 не были отправлены.
- Keep-alive работает после ошибок сервера (400/403/404, в том числе с телом вставки 9,9 МБ) и после простоя 11 и 31 с.
- TLS к настоящему ClickHouse 25.8 с частным CA работает.

**Честность и проверки компилятора**
- Защиты от ошибок записи:
  - автоматических повторов нет, `w=0` отклоняется;
  - неизвестные опции URI не игнорируются молча;
  - параметры ClickHouse передаются отдельно от SQL;
  - идентификаторы таблиц проверяются.
- `driver_io` запрещает сетевые вызовы драйверов в `tx`: прямые, в форме метода и транзитивные через пользовательские функции. Сообщение понятное, отрицательных fixtures 17.
- Исправление optional-map верное: `[]`, `.get`, `.remove`, включая `str?` и вложенные map (на main вложенный случай был сломан).
- `sendto(MSG_NOSIGNAL)` с повтором при EINTR: CLI больше не погибает от SIGPIPE. Пустая TLS-запись больше не отправляется.
- Новые lib-файлы проходят системный режим (`khc check --all-lib`, rc=0). Тесты PR пользуются байтовым API, поэтому переживут шаг E UTF-8.
- Описание PR честно перечисляет ограничения: нет SDAM, sessions, SRV; `max_bytes` не ограничивает память арены.

### 3.1 Критическая

**К1. `MongoCursor` в `store`: библиотека пишет указатели арены в объект store.** Подтверждено, воспроизведено двумя проверяющими.
- *Суть.*
  - Тип `MongoCursor` разрешено хранить в `store`: src/api.kh:505 запрещает только `Buf` и `__*`.
  - `mongo_next` и `mongo_close` меняют поля аргумента: `cursor.documents = []`, `push`, `cursor.error`, `cursor.id` (mongo.kh:814-850, 908).
  - Для lib-файлов барьеры store не генерируются: src/api.kh:990, `barrier_on = ... && !files[...].is_lib`.
  - После конца запроса арена обнуляется и переиспользуется, а объект store по-прежнему указывает в неё. Это нарушает и инвариант I1 проекта GC (замкнутый граф store), и сохранение KHRIP_DATA.
- *Доказательство.* Проба `store pages: map[str, MongoCursor]`, THREADS=1:
  - `/start` → `/peek` даёт `peek 3 row-0-;row-1-;row-2-`;
  - `/next` даёт `next true 3 196`, после чего каждый `/peek` даёт `peek 0`, хотя пользовательский код store не менял;
  - параллельно запустили `/slow` (заполняет арену 1 МБ и спит) и `/peek`: оба получили пустой ответ (curl rc=52), процесс стал `<defunct>`, в dmesg `traps: ... general protection fault`;
  - контрольный прогон без `mongo_next` стабильно отвечает 200.
- *Исправить.*
  - Запретить в `store` типы, содержащие `MongoCursor`, так же как `Buf` (src/api.kh:505), и добавить регрессионный тест.
  - В DATABASES.md написать, что курсор живёт один запрос.
  - Общее правило на будущее: lib-функции не пишут в объекты, достижимые из пользовательского кода, либо компилятор вставляет для таких записей барьер. Это правило понадобится и для SATB-барьеров шага 6 GC.

### 3.2 Высокие

**В1. Вложенный `Bson` в `to_bson` кодируется как структура `{data, error}`: тихая порча документа.** Подтверждено.
- *Суть.* `__bson_encode_value` (bson.kh:596-607) особо обрабатывает BsonObjectId, BsonDate, BsonBinary, BsonDecimal128 и BsonTimestamp, но не `Bson`. Компилятор такой код пропускает: src/drivers.kh:67 требует лишь struct или `map[str, T]`.
- *Доказательство.*
  - `to_bson({"amount": to_bson({"$gt": 100})})` даёт `error='' found=0`; тот же фильтр через builder находит документ (found=1).
  - `mongo_update(..., to_bson({"$set": to_bson({"title":"b"})}))` даёт `error=''`. mongosh показал, что в документе появились поля `data: '\x12\x00..title..b'` и `error: ''`, а `title` не изменился.
  - Исход зависит от данных: при некоторых значениях сервер отвечает `invalid nested BSON document`.
  - Проверяющий, писавший программы «как ИИ», наткнулся на это во второй же программе (агрегация с `$group`).
- *Исправить.* Добавить ветку `D_STRUCT && name == "Bson"`, которая встраивает сырой документ так же, как `bson_doc`. Заодно `map[str, Bson]` станет коротким способом собирать неоднородные документы и конвейеры. Альтернатива — ошибка компиляции.

**В2. `none` записывается как BSON null: PATCH-идиома стирает поля.** Подтверждено.
- *Суть.* KHRIP.md учит, что `SET {patch}` меняет только присланные поля, а `{...old, ...patch}` копирует только поля, отличные от none. Та же идиома в виде `to_bson({"$set": patch})` обнуляет все поля, которые клиент не прислал (bson.kh:577-580). После этого документ перестаёт декодироваться в исходный тип. А `_id: BsonObjectId?` со значением none записывается как `_id: null` вместо того, чтобы id назначил сервер.
- *Доказательство.*
  - Вставили документ `{_id:'n1', title, body, tags}`.
  - `NotePatch{title: str?, body: str?, tags: [str]?}` получили из `{"title":"new title"}` и выполнили `mongo_update(..., to_bson({"$set": p}))` → `error=''`.
  - `body` и `tags` стали null, `from_bson` в `Note` вернул none: `BSON field 'body' has an incompatible type`.
  - Вторая вставка `Item{_id: none}` → `E11000 duplicate key ... { _id: null }`.
- *Факт и оценка.* DATABASES.md:55 документирует `T?` как «значение или Null», то есть поведение задумано. Но оно противоречит идиоме KHRIP.md (:110, :245, :267), поэтому данные теряются молча.
- *Исправить (предложение).* По умолчанию пропускать поля со значением `none`: так устроены spread и PATCH в Khrip и `omitempty` в Go. Явная очистка — через `bson_null`/`$unset`. Правило описать в KHRIP.md. Решать нужно до вливания: позже это будет ломающая смена семантики.

**В3. Запрос ClickHouse из обычной строки с `{x}` — рабочая SQL-инъекция.** Подтверждено двумя проверяющими независимо.
- *Суть.*
  - `ch_query` и `ch_query_params` (clickhouse.kh:165, 169) принимают любую `str`. Внутри `sql "..."` выражение `{x}` — безопасный параметр, а в обычной строке — интерполяция.
  - Самая «кхриповая» запись `ch_query(c, "... WHERE page = '{page}'")` компилируется без предупреждений.
  - Правильная форма ClickHouse `{name:Type}` в обычной строке даёт сбивающую ошибку: `unknown name 'n'` с подсказкой `did you mean 'c'?` или `expected ')', found ':'`. Нужно знать про `\{` или обратные кавычки.
- *Доказательство.*
  - Таблица из трёх строк ('/a', '/a', '/b'): `page="/a"` → 2, а `page="x' OR 1=1 OR page='"` → 3 (все строки), `ok=true`.
  - Тот же ввод через `ch_query_params` с `\{p:String}` → 0.
  - Второй проверяющий воспроизвёл то же на `system.users`.
- *Документация.* Правило `\{` есть только в DATABASES.md:142-145 (на русском). В KHRIP.md:283-291 нет ни сигнатур `ch_*`, ни предупреждения.
- *Исправить.*
  - Минимум: компилятор (src/drivers.kh уже знает эти имена) требует, чтобы запрос в `ch_query`/`ch_query_params`/`ch_cancel` был литералом без интерполяции или `const`.
  - Лексеру добавить подсказку для `{ident:Type}` внутри строки.
  - Лучше — форма `ch "..."` на лексере `sql` (раздел 5).

**В4. Ошибки по умолчанию «проглатываются»: забытая проверка даёт ложный успех.** Подтверждено.
- *Суть.* Все сетевые операции возвращают структуру-результат. Ничто не завершает запрос, а результат можно отбросить, вызвав функцию как оператор, без диагностики. У `sql` наоборот: сбой завершает запрос с кодом (дубликат → 409, база недоступна → 503). Соглашений об ошибках в PR пять:
  - `MongoResult`: `error` и `code`, но нет `ok`;
  - `ChResult`: `ok`, `status`, `error`, но нет `code`. Заголовок `x-clickhouse-exception-code` читается (clickhouse.kh:155) и используется только как булево;
  - `Bson.error` внутри самого значения;
  - `none` плюс общий слот `bson_error()`/`ch_error()`;
  - `""` плюс `ch_error()` у `ch_encode`; кроме того, ошибка BsonBuilder «липкая».
- *Доказательство.*
  - Маршрут `POST /users`, где `mongo_insert(db(), ...)` вызван как оператор и затем `return 201 body`, компилируется.
  - Два POST с одинаковым `_id` дают `201 201`, а `countDocuments` показывает 1 документ: второй получил E11000.
  - С неверным паролем ответ тоже 201.
  - Fixture самого PR tests/errors/tx_mongo_helper.kh:4 отбрасывает результат.
  - В программе 1 (CRUD заметок) 6 из 76 строк — ручные `if r.error != "" { return 503 r.error }`.
- *Исправить (предложение).*
  - По умолчанию fail-closed, как у `sql`: ошибка транспорта или аутентификации → 503, код 11000 → 409.
  - Явная форма для кода, которому нужны `unknown_outcome` или `writeErrors`.
  - Компилятор отвергает неиспользованные `MongoResult`/`ChResult`.
  - Единые поля `ok`, `error`, `code` в обоих результатах.

**В5. Протокол курсора провоцирует тихую потерю данных.** Подтверждено.
- *Суть.*
  - Первая порция уже лежит в `cursor.documents` (mongo.kh:866), а `mongo_next` получает следующую. Привычный цикл итератора `while mongo_next(c) { for d in c.documents {...} }` (как `cur.Next` в Go или `rs.next()` в JDBC) компилируется и молча теряет первую порцию. Для маленьких выборок это значит — всё.
  - `mongo_cursor` берёт коллекцию отдельно от команды (:899). Если они расходятся, первая порция читается, а getMore ломается: маленькие тесты проходят, ошибка проявляется только с ростом данных.
- *Доказательство.*
  - 250 документов, цикл итератора: `saw 150 of 250, error=''`.
  - Выборка из одного документа: `saw 0 of 1`.
  - aggregate по `docs` с аргументом `items` и batch 50: 50 документов, затем `Requested getMore on namespace '...items', but cursor belongs to a different namespace ...docs`.
- *Документация.* Правильный порядок описан в DATABASES.md:90-91, то есть поведение задокументировано, но ловушка тихая.
- *Исправить (предложение).*
  - Типизированные `mongo_all`/`mongo_one`, которые сами дочитывают курсор.
  - У низкоуровневого курсора `documents` пуст до первого `mongo_next`.
  - Коллекцию брать из `cursor.ns`.
  - `cursor: {}` в aggregate добавлять автоматически.

**В6. `ch_insert` пишет только в столбцы Int64/Float64/Bool/String.** Подтверждено двумя проверяющими.
- *Суть.*
  - `__ch_type` (clickhouse.kh:238-257) выводит типы только из типов Khrip, а `input_format_with_types_use_header=1` (:127) требует точного совпадения. Так задумано: см. комментарий в clickhouse.kh:173-174, а client.kh проверяет, что Int32 отвергается.
  - В итоге нельзя писать в DateTime, Date, UInt32/UInt64, Int32, Float32, LowCardinality(String) и даже вставить `str` в `Nullable(String)`, то есть в большинство реальных аналитических схем.
  - Обхода в API нет: у `ch_query` нет тела запроса, `INSERT ... FROM input()` не выразить. Остаётся собирать VALUES строкой, а это возвращает инъекцию (В3).
- *Доказательство.* Настоящий ClickHouse 25.8, строки `Ev{id:int, name:str, note:str}`:
  - вставка успешна только в таблицу `(Int64, String, String)`;
  - остальные случаи дают HTTP 400 Code 117: `Type of 'id' must be UInt64, not Int64` (то же для Int32 и DateTime), `must be LowCardinality(String), not String`, `must be Nullable(String), not String`.
- *Уточнение по чтению.*
  - Date, Date32, DateTime и DateTime64 читаются в `int` (clickhouse.kh:445), но не в `str`.
  - Decimal, UUID и Float32 не читаются ни во что.
  - LowCardinality(String) → `str` работает.
- *Исправить.*
  - Кодировать под реальную схему таблицы: один раз сделать DESCRIBE и сужать с проверкой диапазона (int → UInt32/DateTime, str → LowCardinality/Nullable). Либо отправлять `INSERT INTO t (cols) SELECT <приведения> FROM input('<структура>')`.
  - Минимум до вливания: считать LowCardinality(T) и Nullable(T) совместимыми с T и явно описать ограничение в KHRIP.md и DATABASES.md.

**В7. TLS к настоящему MongoDB 7/8 не работает.** Подтверждено на собственных контейнерах.
- *Суть.*
  - Начиная с SERVER-72839, mongod не запускает TLS без цепочки доверия (tlsCAFile или tlsUseSystemCA). С ней он всегда присылает CertificateRequest, даже когда клиентский сертификат необязателен.
  - Общий TLS-клиент Khrip на сообщении 13 прерывает рукопожатие (tls.kh:704-705; так было и до PR, в 1bc4605 tls.kh:684).
  - PR проверял TLS для Mongo только против Python-peer и этого не заметил, хотя в описании заявлены `tls=true`/`tlsCAFile`.
- *Доказательство.* Контейнер mongo:8.0 с `--tlsMode requireTLS`:
  - без CA mongod не стартует: «The use of TLS without specifying a chain of trust is no longer supported»;
  - с `--tlsCAFile ... --tlsAllowConnectionsWithoutCertificates` openssl s_client показывает «Acceptable client certificate CA names»;
  - Khrip получает `tls: the server asks for a client certificate` в 200 попытках из 200, а mongosh в том же контейнере подключается;
  - временная правка (ответить пустым Certificate по RFC 8446 §4.4.2) сделала путь рабочим: первая команда 29 мс, 200 пингов по одному переиспользуемому соединению без ошибок, find на 2000 документов, отказ при чужом CA.
- *Исправить.*
  - В `__tls_connect` принимать CertificateRequest: добавить его в транскрипт и отправить `Certificate{context, пустой список}` перед Finished клиента. Это улучшение общего TLS, полезное и для `fetch`.
  - Добавить тест CI с настоящим mongod в режиме requireTLS.
  - Пока не исправлено — убрать TLS для MongoDB из заявленных возможностей.

**В8. BSON перепроверяется десятки раз и выделяет память: арена расходуется примерно в 100 раз больше объёма данных.** Подтверждено тремя проверяющими.
- *Суть.*
  - Каждый ответ проходит `__bson_valid_doc` ~20–25 раз, команда вставки — ~14 раз.
  - Каждый `bson_get*` заново проверяет весь документ (bson.kh:454-458) и строит BsonField на каждое поле.
  - Проверка массива выделяет две строки на элемент: `__str_new(...) != index.to_str()` (bson.kh:218).
  - `__mongo_response` и `__mongo_cursor_batch` (mongo.kh:427-487, 821-845) вызывают ~10 таких функций на каждый ответ, путь запроса (:497-512) — ещё 6–7.
  - Всё это идёт без уступания управления другим сопрограммам.
  - Бюджет курсора `max_bytes` (по умолчанию 64 МиБ) недостижим: запрос раньше упирается в арену 1 ГБ.
- *Доказательство.*
  - find 100k документов `{_id, s:'item'}` (~3 МБ BSON) одной порцией: 1,0–1,1 с и ~300 МБ арены; вместе с `from_bson` — ~385 МБ. mongosh делает то же за 188 мс.
  - Маршрут сервера (THREADS=1, batch 100): 3 прохода по коллекции — 200 за 4,8 с; 4 прохода (~12 МБ BSON, без декодирования) — HTTP 500 `panic: out of memory: the request used all of its 1 GB arena`.
  - Запрос `/ping` во время find+decode 100k документов отвечает 0,82 с (в простое — 0,0004 с).
  - `bson_get_int` отсутствующего ключа в документе 3,5 МБ стоит ~80 мс за вызов.
  - `from_bson` документа 8 МБ с вложенностью 64 занимает 3 073 мс, а один проход валидации — 37 мс: зависимость от глубины квадратичная.
  - Вставка 100k документов одной командой (10,8 МБ) — 835 МБ RSS.
- *Пробная правка* из двух мелких изменений: индексы массива сравниваются на месте, а `bson_get` стал однопроходным и не выделяет память.
  - find+decode 10k документов: CPU 256 → 96 мс, RSS 104 → 17 МБ;
  - вставка 10k документов: RSS 83 → 32,5 МБ;
  - 47 + 56 проверок PR проходят.
- *Исправить.*
  - Проверять BSON один раз на границе доверия (`bson_parse` ответа, результат `to_bson`) и хранить признак «проверено».
  - Аксессоры и `__bson_fields` должны обходить документ без проверки и без выделений.
  - Ключи массива проверять сравнением цифр, без построения строк.
  - В `__mongo_response`/`__mongo_cursor_batch` читать верхний уровень за один проход.
  - Заменить `__bson_utf8` (bson.kh:62) на `__utf8_scan`/`__utf8_bad_at` из main: на 167 837 952 входах решения совпадают, а SIMD-вариант в 4–28 раз быстрее.
  - Добавить тесты на масштаб: курсор больше 20 МБ в одном запросе и вставка 100k документов.

### 3.3 Средние

**С1. Ответ больше 16 МиБ считается испорченным** (bson.kh:200; mongo.kh:427-429). Подтверждено, важность понижена с высокой.
- *Суть.* Сервер вправе прислать ответ размером maxBsonObjectSize + 16 КиБ: документы плюс обёртка курсора.
- *Доказательство.*
  - 40 документов по 1 048 568 байт, batch 100: ответ 16 777 217 байт → `invalid BSON document`, docs=0; с batch 15 читаются все.
  - Легальный документ размером 16 777 138 байт не читается.
  - findAndModify на таком документе возвращает `unknown_outcome=true`, хотя запись применена.
  - Окно узкое (переполнение бывает, когда сумма документов в пределах ~100 байт от лимита), но для таких данных результат детерминированный.
- *Исправить.* Для ответов использовать лимит `MB_DOC + 16384`, весь ответ ограничивать `max_message_bytes`, в тексте ошибки указывать размер.

**С2. Строгие числа в `from_bson` и `bson_get_int`** (bson.kh:698-713, 477-491). Подтверждено.
- *Суть.* mongosh и Node пишут целые числа как Int32, а большие — как Double. Go-драйвер такие значения принимает, Khrip — нет.
- *Доказательство.* После `insertOne({price: 10, qty: 2.0, big: 5000000000})`:
  - `price` как float → «incompatible type», `qty` — так же;
  - `big` как int — ошибка, `bson_get_int` → none.
- *Исправить.* float принимает Int32/Int64; int принимает целый Double в диапазоне int64; отвергать только случаи с потерей точности. Описать соответствие в документации.

**С3. Одна строка с невалидным UTF-8 рушит всю порцию** (bson.kh:127; mongo.kh:427-429). Подтверждено.
- *Суть.* MongoDB хранит такие строки (например, записанные другими драйверами). Ошибка не называет поле, соединение сбрасывается, выставляется `unknown_outcome=true`.
- *Доказательство.* Вставили сырым OP_MSG 10 документов, один из них с байтами `\xff\xfe`:
  - batch 3 → `got 3 of 10 docs, err='invalid BSON document'`;
  - batch 100 → 0 документов.
- *Исправить.* На уровне ответа проверять только структуру, а UTF-8 — при превращении значения в `str` (`from_bson`, `bson_get_str`), с путём поля в ошибке.

**С4. Пользователь ClickHouse с `readonly=1` не может выполнить даже `SELECT 1`** (clickhouse.kh:123-128). Подтверждено.
- *Суть.* Каждый запрос безусловно меняет около 10 настроек сервера.
- *Доказательство.*
  - `ch_query(..., "SELECT 1")` → `Code: 164 Cannot modify 'max_result_bytes' setting in readonly mode`, а curl от того же пользователя возвращает 1.
  - Профиль с `max_execution_time ... MAX 5` ломается при `timeout_ms` по умолчанию (Code 452).
- *Исправить.* Отправлять только настройки, нужные операции (`input_format_*` — только для вставки), а серверные лимиты сделать необязательными.

**С5. `max_result_bytes` равен клиентскому лимиту байт** (clickhouse.kh:125). Подтверждено.
- *Суть.* Сервер измеряет несжатые блоки в памяти (у String это ещё смещения по 8 байт), а не байты на проводе. Для строковых результатов реальный лимит примерно в 4 раза меньше заявленного.
- *Доказательство.* `SELECT toString(number % 10) FROM numbers(2000000)` — 4 000 014 байт по сети, но сервер отвечает Code 396 «max bytes: 16.00 MiB, current bytes: 16.28 MiB».
- *Исправить.* Не связывать серверный лимит с клиентским: клиентский и так проверяется в `__dh_take`.

**С6. Декодер RowBinary разбирает строку типа на каждом значении** (clickhouse.kh:417-423, 469, 533-552). Подтверждено.
- *Суть.* `__ch_unwrap` на каждом вызове выделяет память под `name + "("`, а ширина значения находится цепочкой сравнений строк.
- *Доказательство.*
  - `[int]`, 1M строк (8 МБ тела): сам запрос 61–67 мс, декодирование 283–384 мс и 48,8 МБ арены.
  - `[Ev]`, 6 полей, 200k строк (6,2 МБ): 427–509 мс и 113 МБ.
  - С `__ch_unwrap` без выделения памяти: 16,8 МБ / 175–211 мс и 44,7 МБ / 190–217 мс.
- *Исправить.* Один раз после заголовка собрать план столбца: ширина, знак, nullable, глубина массива, LowCardinality.

**С7. Ожидание слота — опрос `sleep(1)` без очереди** (db_http.kh:18-29; mongo.kh:336-341). Подтверждено.
- *Суть.* Каждый ожидающий просыпается 1000 раз в секунду. Порядок не FIFO, а ожидание идёт в счёт deadline, поэтому под нагрузкой ранние запросы могут истечь, пока поздние проходят. Лимиты при этом соблюдаются, утечек нет.
- *Доказательство.*
  - 300 ожидающих — около 40 % ядра впустую.
  - 30 запросов при `max_inflight=1`: запрос №1 завершился 21-м, №4 — последним.
- *Исправить.* FIFO-список сопрограмм и `__co_notify`, как уже сделано в pg.kh.

**С8. Библиотеки драйверов подключаются в каждую API-программу: конфликт имён** (src/api.kh:80-93, 113). Подтверждено, важность понижена с высокой.
- *Суть.* PR добавляет 55 публичных имён; у библиотек api/http/fetch/x509/tls/pg/db на main их 6. `database_api_name` определяет использование драйвера по префиксам имён.
- *Доказательство.*
  - Программа с `type Mongo {...}` или собственной `fn ch_query` компилируется на main и не компилируется после PR: `lib/mongo.kh:6:6: error: 'Mongo' is already defined`. Ошибка указывает в библиотеку, а не в код пользователя.
  - CLI-программа, где есть только `let ch_count = 3`: компиляция 20 → 51 мс, бинарник 9 040 → 9 616 байт.
  - `store ch_total: int` вставляет очистку ClickHouse в `__db_end` каждого запроса.
  - Компиляция tests/api/crud.kh — 57 → 71 мс.
  - Сломанных программ в репозитории нет.
- *Исправить.* Подключать драйверы только при реальном использовании, имена сравнивать точно после разрешения имён.

**С9. Серверные курсоры утекают при `fail`/panic** (mongo.kh:267-272). Подтверждено.
- *Суть.* `__mongo_request_end` освобождает только соединение. В Khrip нет defer, поэтому вызвать `mongo_close` на этом пути пользователь не может.
- *Доказательство.* 20 запросов `mongo_find(batch 2)` + `fail(409)`: `metrics.cursor.open.total` 0 → 20. Курсоры живут до cursorTimeoutMillis (10 мин).
- *Исправить.* Запоминать id курсоров запроса и в конце посылать killCursors, либо ставить его в очередь на следующую команду через тот же пул.

**С10. Маршруты с драйверами берут эксклюзивную блокировку store** (src/rw.kh:36, 257-259). Подтверждено.
- *Суть.* В безопасный список добавлены только кодеки. Цена — пропускная способность, корректность не страдает.
- *Доказательство.* `khc check --locks`:
  - маршрут, который читает store и вызывает `ch_query`, — `write`;
  - маршрут только с `bson_new/bson_str/bson_finish` — тоже `write`;
  - `to_bson` и `fetch` — `read`.
- *Исправить.* Добавить в безопасный список чистые `bson_*` и сетевые функции (они отпускают блокировку на время ожидания). `mongo_next`/`mongo_close` считать функциями, изменяющими аргумент.

**С11. Двоичные данные в `str` и шаги E/F UTF-8** (bson.kh:8, 20, 24; clickhouse.kh:21, 325). Подтверждено, важность понижена с высокой.
- *Суть.* `Bson.data`, `BsonBinary.data`, `BsonDecimal128.bytes`, `ChResult.body` и результат `ch_encode` хранят сырые байты в `str`. Такие типы можно класть в store и отдавать в `to_json`.
- *Доказательство.* `store docs: [Bson]` сегодня переживает перезапуск: в снимке лежит сырой байт 0xF8. Это работает только потому, что JSON-писатель main копирует старшие байты как есть.
- *Перспектива.* По v0.13-utf8.md §2 после шагов E/F `to_json` и сохранение KHRIP_DATA заменят невалидные байты на EF BF BD, а восстановление станет мягким, так что данные испортятся молча. Шага E на main пока нет, сценарий нишевый.

### 4.2 Окна снятия блокировки store

**Факт.** PR добавляет два места с прямым `__store_unlock()`/`__store_lock()`.

**Что сделать:**
- Переделать `mongo_command` по образцу `__fetch`. До освобождения блокировки:

- На шаге 4 GC превратить оба места в пары `__store_release_keep`/`__store_lock` и добавить их в список §6.5 и в линт. Переделка небольшая, её можно попросить у автора PR сейчас.

### 5.2 Сравнение с интеграцией PostgreSQL

| | PostgreSQL (`sql`) | MongoDB / ClickHouse (PR) |
|---|---|---|
| Форма | конструкция языка `sql "..."` | библиотечные функции и строки времени выполнения |
| Параметры | `{expr}` — всегда параметр | Mongo: builder или map; CH: `\{name:Type}` + `map[str,str]`, а `{x}` — интерполяция |
| Тип результата | из аннотации или маршрута; `T` без строки → 404 | ручной цикл курсора, `from_bson`/`ch_decode`, проверка на none |
| Ошибки | завершают запрос с кодом 409/404/400/503 | структура-результат, которую можно проигнорировать |
| Проверка при старте | каждое `sql` сверяется с базой | нет |
| Подключение | `DATABASE_URL` неявно | `fn db() -> Mongo {...}` в каждой программе; URI разбирается на каждом вызове (mongo.kh:739) |
| Схема | `migration N` | нет хука для индексов и DDL |
| Вставка | `INSERT INTO t {v}`, `{[v]}` | CH: только столбцы Int64/Float64/Bool/String |
| PATCH | `SET {patch}` меняет только присланные поля | `$set` с none стирает поля |
| Объём в KHRIP.md | ~853 токена o200k, достаточно для кода | абзац без имён функций |

*Оценка (мнение).*
- Wire-драйверы как библиотечный код — правильный фундамент, их стоит сохранить.
- Но то, что видит ИИ, сейчас ближе к паре «Go + драйвер», чем к «Khrip + `sql`». Всё, что `sql` делает конструкцией языка, здесь пишется вручную, и каждое такое место — источник тихой ошибки.

**2. MongoDB: типизированные функции, которые сами завершают запрос при сбое.**

До (работает; 742 токена на 5 маршрутов; показаны два):
```khrip
fn db() -> Mongo {
    return Mongo { uri: env("MONGODB_URI") ?? "mongodb://127.0.0.1:27017" }
}

route GET "/notes/{id}" (id: str) -> Note | 404 | 503 str {
    let c = mongo_find(db(), DB, "notes", to_bson({"_id": id}), 1, 1)
    if c.error != "" {
        return 503 c.error
    }
    if c.documents.len() == 0 {
        return 404
    }
    let n: Note? = from_bson(c.documents[0])
    return n ?? 404
}

route GET "/notes" (tag: str?, limit: int = 20) -> [Note] | 503 str {
    let cmd = bson_new()
    bson_str(cmd, "find", "notes")
    if tag != none {
        bson_doc(cmd, "filter", to_bson({"tags": tag}))
    }
    bson_doc(cmd, "sort", to_bson({"created": -1}))
    bson_int(cmd, "limit", limit)
    let c = mongo_cursor(db(), DB, "notes", bson_finish(cmd))
    var out: [Note] = []
    while true {
        for d in c.documents {
            let n: Note? = from_bson(d)
            if let v = n {
                out.push(v)        // недекодируемый документ здесь молча пропускается
            }
        }
        if !mongo_next(c) {
            break
        }
    }
    if c.error != "" {
        return 503 c.error
    }
    return out
}
```

После (эскиз; оценка для 5 маршрутов — ~356 токенов, версия на PostgreSQL — 318):
```khrip
// подключение и база — из MONGODB_URI, как DATABASE_URL у sql

route GET "/notes/{id}" (id: str) -> Note | 404 {
    return mongo_one("notes", {"_id": id})       // нет документа → 404, сбой → 503
}

route GET "/notes" (tag: str?, limit: int = 20) -> [Note] {

    return mongo_all("notes", {"tags": tag}, Find { sort: {"created": -1}, limit })
}

route PATCH "/notes/{id}" (id: str, body: NotePatch) -> 204 | 404 {
    if mongo_update("notes", {"_id": id}, {"$set": body}) == 0 {   // меняются только присланные поля
        return 404
    }
    return 204
}
```

Принципы эскиза:
- тип результата берётся из аннотации или маршрута;
- сбой завершает запрос с кодом (11000 → 409, транспорт → 503), а для кода, которому нужны `unknown_outcome` и `writeErrors`, есть явная форма;
- `none` опускается, `Bson` встраивается;
- курсор дочитывается внутри функции, а низкоуровневый курсор остаётся для потоковой обработки;
- опции передаются структурой, потому что именованных аргументов в Khrip нет;
- клиент берётся из окружения;
- есть `object_id()`.
