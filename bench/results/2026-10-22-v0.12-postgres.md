# v0.12: PostgreSQL

Свой клиент PostgreSQL в библиотеке Khrip (протокол 3.0, SCRAM, TLS через свой
TLS 1.3, пул соединений на сопрограммах) и запросы как часть языка: `sql "..."`
с параметрами `{x}`, тип результата из ожидаемого типа, `tx { }` —
SERIALIZABLE с повтором при конфликте. Intel Xeon 2,8 ГГц, 4 ядра; PostgreSQL 16
на той же машине.

## Задачи бэкенда на базе

`eval/perf.sh ledger shop tracker`: три задачи, решения на четырёх языках,
сервер на ядрах 0 и 1, `wrk` (64 соединения) на ядрах 2 и 3, PostgreSQL не
привязан к ядрам и делит машину со всеми. Перед каждым запуском — пустая база,
затем одинаковые данные (`load/seed.py`: 100 счетов; 10 категорий и 500
товаров; 50 пользователей и 5 проектов по 200 задач), 3 с прогрева и 10 с
замера; после — проверка инвариантов: деньги не теряются, остаток и проданное
сходятся, номера задач идут без пропусков. Три полных прогона подряд; в таблице
— прогон с медианой запросов в секунду. Все таблицы —
[eval/results/perf_db.md](../../eval/results/perf_db.md).

Инварианты сохранились во всех прогонах, ошибок нет. Разброс между прогонами —
до 20% (у Khrip в tracker 3,7–4,6 тыс.): база делит процессор с сервером и `wrk`.

Процессор PostgreSQL на запрос — всё время процессов базы за замер, делённое на
число запросов (вместе с соединениями, закрытыми в конце: их время учитывается
у главного процесса). У Khrip он выше, чем у Go, по двум причинам:

- **ledger, +16%**: повторы. Go, C# и Python держат строки блокировками
  (`SELECT ... ORDER BY id FOR UPDATE` в READ COMMITTED) — так пишет опытный
  разработчик, и порядок блокировок — его забота. На Khrip — `tx { }`,
  SERIALIZABLE: код читает и пишет так, будто он один, конфликты находит база,
  блок повторяется. Около 15% переводов откатываются и тут же повторяются.
- **shop и tracker**: Khrip за те же 13 с создаёт больше заказов и задач, и
  сводки, которые читают их все, дорожают. По отдельности маршруты tracker стоят
  базе столько же или меньше, чем у Go: чтение 47 мкс против 52, правка 190
  против 238, новая задача 311 против 299, сводка 493 против 574.

Двоичный формат результатов (его используют pgx, Npgsql и asyncpg) серверу не
дешевле текстового: 51–54 мкс на запрос в одну строку против 55, 154–160 на 20
строк против 146–170 (`SELECT *` из таблицы с двумя `timestamptz`).

p99 у Khrip в shop и tracker хуже, чем у Go (60 мс против 47, 36 против 30): в
хвосте — тяжёлая сводка по категориям (5% запросов); размер пула (`DATABASE_POOL`
8 или 16) на него не влияет.

## Повторы транзакций и горячие строки

Первая версия ledger на Khrip работала в двух режимах: то 4 тыс. запросов в
секунду, то 1,1 тыс. с цепочками по сотне повторов. Причин было две.

1. **Последовательный просмотр.** На таблице счетов из 100 строк (2 страницы)
   планировщик выбирает Seq Scan даже для `WHERE id = $1`. В SERIALIZABLE
   последовательный просмотр ставит предикатную блокировку на всю таблицу, и
   любая запись в неё конфликтует с каждой открытой транзакцией: отказы
   «read/write dependencies ... pivot» лавиной. Когда статистика менялась,
   планировщик переходил на индекс — отсюда два режима. Блоки `tx` теперь
   выключают последовательный просмотр (`set_config('enable_seqscan', 'off',
   true)` тем же пакетом, что BEGIN, без лишнего обмена).
2. **Очередь повторов на весь блок.** Проигравший конфликт блок ждал на одной
   advisory-блокировке своего места в коде, и под нагрузкой в эту очередь
   вставали все переводы, даже между разными счетами. Теперь компилятор
   выписывает для каждого запроса «таблица.столбец» из `WHERE col = {x}`, и
   повтор ждёт только на строках своей попытки (блокировки берутся по порядку
   одним оператором до BEGIN, снимаются вместе с COMMIT). Первая попытка, чей
   первый запрос касается строки, которую в этом процессе ждёт повтор, встаёт в
   ту же очередь до BEGIN; запрос посреди попытки на такой строке уступает
   (откат и повтор в очереди), а не идёт на верный конфликт.

| ledger, Khrip, 8 с | запросов в секунду | p99, мс | откатов |
|---|---:|---:|---:|
| очередь на блок, прогоны подряд | 1 918–2 683 | 93–95 | 6–7 тыс. |
| без очереди | 2 298–4 723 | 194–888 | 6–43 тыс. |
| очередь по строкам и без Seq Scan | 3 650–3 990 | 36–62 | 3,4–3,6 тыс. |
| Go (FOR UPDATE), для сравнения | 3 521–3 797 | 35–45 | 0 |

Одна горячая строка — счётчик, который увеличивает каждый запрос (64
соединения): без очереди первых попыток 1 070–1 390 запросов в секунду, p99
180–210 мс, отдельные запросы повторялись до 174 раз; с очередью — 1 100–1 170,
p99 82–97 мс, повторов почти нет: запросы идут по одному, как с `FOR UPDATE`.

## Чтение больших результатов

[bench/pg](../pg/run.sh): 300 тыс. чисел и 100 тыс. строк по три столбца
(число и две строки, ~120 байт), лучшее из пяти, программа на одном ядре:

| мс | Khrip | Go (pgx) | Python (asyncpg) |
|---|---:|---:|---:|
| 300 тыс. `int` | 87–99 | **65–67** | 102–116 |
| 100 тыс. строк в структуры | 80–97 | 99–113 | **65–70** (Record без разбора по полям) |

Значения разбираются по плану, собранному при запуске сервера. Числа пока
медленнее, чем в pgx: каждое приходит текстом и проходит общий путь разбора
строки результата.

## Что ещё нашёл замер

- Решение shop на Khrip хранило строки заказа в jsonb и на каждую сводку
  разворачивало JSON всех заказов: 70 мс процессора базы на запрос против 9 у Go.
  Теперь у него таблица строк заказа, как у остальных, и страницы поиска — в SQL.
- Новый заказ перечитывался после вставки, и в SERIALIZABLE это чтение
  блокировало последнюю страницу индекса, куда пишут все новые заказы: ложные
  конфликты у четверти заказов. Решение отвечает данными из `RETURNING`.
- Замер процессора базы терял время соединений, закрытых в конце нагрузки (Go
  отменяет запросы, когда `wrk` закрывает соединения): у Go выходил ноль.
  Теперь второй снимок — через секунду, когда главный процесс PostgreSQL их
  дождался.
