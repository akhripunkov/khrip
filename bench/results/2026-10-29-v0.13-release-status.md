## Сделано

- **Решения Java и Node для всех 11 задач** (`eval/solutions/*/java`,
  `eval/solutions/*/node`). Java 21: Spring Boot 3.5.16, MVC на Tomcat с
  виртуальными потоками, JdbcTemplate + HikariCP + pgjdbc для ledger, shop,
  tracker; JVM без флагов. Node 22: Fastify 5.12.7 со схемами, `pg` 8.23.1,
  `package-lock.json` в git. Bun 1.4.2 запускает тот же `server.js` с Fastify
  без изменений. Node ×2 (`node-cluster`, `eval/node_cluster.mjs`) — только
  задачи с базой: данные в памяти процессы не делят.
- **Проверки eval: 80 из 80** (11 задач × Khrip, Go, C#, Python, Java, Node,
  Bun + Node ×2 на трёх задачах с базой) — `checks.tsv`, `check_logs/`.
- **Токены**: Java и Node в `eval/results/tokens.md` и `eval/README.md`. Со
  скиллом и кэшем (w = 0,02, глава 0,25), все 11 задач: Khrip 10 077, Java
  16 167 (×1,60), Node 12 282 (×1,22); Node дешевле на ratelimit (416 против
  451); без кэша Khrip дороже Node (×0,77) и вровень с Java (×1,02).
- **Обвязка** (проверена пробными прогонами всех режимов): `eval/server.sh`,
  `run.sh` (java, node, bun, node-cluster), `perf.sh`, `perf_rate.sh`,
  `rss_sample.py` (процессор и RSS — сумма по дереву процессов),
  `bench/mem/long.sh` (варианты csharp, java, node, bun), `bench/tokens/*.mjs`.
- **A/B `synchronized` против `ReentrantLock`** у Java: bank +3–5 %, inventory
  −8 % — оставлен `synchronized` (`java_lock_ab_*.tsv`).
- **Замкнутый цикл закончен**: 13 сценариев, прогрев 60 с, замер 60 с, два
  круга в противоположном порядке языков (Python — в первом), все 175
  инвариантов `ok`. Таблицы и пороги — `tables.md`. Пороги (Khrip ≥ лучшего из
  Go, C#, Java, Node, Bun, Node ×2; среднее двух кругов):
  - **процессор на запрос — 13 из 13** (самый узкий запас: catalog 0,97 от C#,

## Как продолжить

```bash
git -C /home/user/khrip fetch origin v013-rel2
git -C /home/user/khrip worktree add <папка> origin/v013-rel2   # или checkout ветки
cd <папка> && ./build.sh
# после перезапуска контейнера: service postgresql start; docker start khrip-mongo1 khrip-ch1
docker update --cpuset-cpus 0-3 khrip-ch1 khrip-mongo1
pgrep -af 'tests/run|wrk|perf.sh'        # должно быть пусто: одна партия за раз
B=bench/results/2026-10-29-v0.13-release-data
# партии дольше 2 ч — отдельной сессией: setsid nohup ... &
D=/tmp/v013r2-data $B/batch.sh rate        # ≈ 3 ч, 81 прогон
D=/tmp/v013r2-data $B/batch.sh conn        # ≈ 1,5 ч
D=/tmp/v013r2-data $B/batch.sh long-bank   # ≈ 1 ч
D=/tmp/v013r2-data $B/batch.sh long-notes  # ≈ 1 ч
cp /tmp/v013r2-data/{rate,conn,long}.tsv $B/   # ряды RSS: /tmp/v013r2-data/rss, rss-conn, long
(cd $B && python3 tables.py > tables.md)       # пороги по сценариям
```

Перед каждой партией `batch.sh` сам ничего не проверяет: смотреть `pgrep`
выше; `quiet.sh` возвращает ядра контейнеров по выходе (и при `kill` группы
процессов), но после аварии — `docker update --cpuset-cpus 0-3 khrip-ch1
khrip-mongo1`.
