| Язык | Стек | Версии | Настройки |
|---|---|---|---|

| Java | Spring Boot MVC на встроенном Tomcat, виртуальные потоки, Jackson; JdbcTemplate + HikariCP + pgjdbc | OpenJDK 21.0.12.1, Spring Boot 3.5.16 (Spring 6.2.19, Tomcat 10.1.55, Jackson 2.21.4), HikariCP 6.3.3, pgjdbc 42.7.11 | JVM без флагов (G1, куча до ¼ памяти); Tomcat и Hikari (10 соединений) — по умолчанию |
| Node | Fastify 5 с JSON-схемами тел и строк запроса, `pg` | Node 22.22.0, Fastify 5.12.7, pg 8.23.1 | один процесс; пул `pg` — 10 соединений |
| Bun | тот же `server.js` с Fastify | Bun 1.4.2 | по умолчанию, без `--smol` |

| Python (для сведения) | FastAPI на uvicorn (uvloop, httptools) | Python 3.13.16, FastAPI 0.115.12, uvicorn 0.34.0 | один процесс |

- **Java** (`eval/solutions/*/java`): один файл `App.java` на задачу
  (`@SpringBootApplication` и `@RestController` вместе, записи `record`),
  `application.properties` (порт, `spring.threads.virtual.enabled=true`,
  snake_case в Jackson) и `pom.xml` от `spring-boot-starter-parent` 3.5.16 —
  версии всех зависимостей закреплены его BOM. Данные в памяти — за монитором
  контроллера (`synchronized`), как у Go и C# — за одной блокировкой; задачи с
  базой — `TransactionTemplate` и `SELECT ... FOR UPDATE` в порядке id, как у Go
  и C#. JVM запускается без единого флага (`-Xmx`, `-XX:` и т. п.).
- **`synchronized` или `ReentrantLock`.** В JDK 21 виртуальный поток, который
  ждёт монитор, держит поток-носитель. Проверено A/B (замкнутый цикл, 20 + 20 с,
  3 круга по очереди; `java_lock_ab_*.tsv`): в bank `ReentrantLock` быстрее на
  3–5 % (медиана 26 824 против 25 636 запросов/с), в inventory — медленнее на
  8 % (19 468 против 21 205). Систематического проигрыша нет, поэтому оставлен
  обычный `synchronized`.
- **Node** (`eval/solutions/*/node`): один `server.js` на задачу,
  `package.json` с точными версиями и `package-lock.json`. Данные в памяти —
  `Map` и массивы одного процесса. **Несколько процессов** (`node:cluster`,
  pm2) данные в памяти не делят: в восьми задачах без базы второй процесс видел
  бы свои счета, ссылки и заказы — это уже другая программа (нужен Redis или
  база). Поэтому вариант Node ×2 (`eval/node_cluster.mjs`: главный процесс
  принимает соединения и раздаёт двум рабочим) есть только у ledger, shop и
  tracker, где состояние — в PostgreSQL; там он проходит те же проверки (две
  копии сервера и перезапуск). Процессор и память Node ×2 — сумма трёх
  процессов.
- **Bun** запускает тот же Fastify без изменений: все 11 задач проходят
  проверки, `Bun.serve` не понадобился.
- **Окружение.** Переменные этой машины, которые меняют поведение сред, серверу
  не передаются: `BUN_OPTIONS=--smol` (режим экономии памяти Bun),
  `JAVA_TOOL_OPTIONS` (прокси и хранилище сертификатов для Maven),
  `NODE_OPTIONS`. Сборка: Java — `mvn package` в папке сборки, Node и Bun —
  `npm ci` по `package-lock.json`; `target/` и `node_modules/` в git не
  попадают.
- Машина: 4 vCPU Intel Xeon 2,3 ГГц, 16 ГБ; PostgreSQL 16 на ней же (без
  привязки к ядрам). Сервер — на ядрах 0–1, `wrk`/`wrk2` и выборка RSS — на
  2–3; `bench/tools/quiet.sh` на время каждой партии переносит контейнеры
  ClickHouse и MongoDB на ядра 2–3 и потом возвращает. Машина заметно быстрее
  той, на которой мерили 26.10 (в замкнутом цикле Go shortener — 71 тыс.
  запросов/с против 44 тыс., C# — 110 тыс. против 49 тыс.), поэтому абсолютные
  числа с прежними отчётами не сравниваются — только отношения внутри одного
  прогона.

В скобках — во сколько раз дороже, чем Khrip; меньше 1 — Khrip дороже.

- С кэшем Khrip дешевле Java и Node в сумме и в каждой группе; по отдельности
  Node дешевле на ratelimit (416 против 451 — как и Python, 396), Java дороже
  на каждой задаче.
- Если считать главу `postgresql.md` полным весом, на задачах с базой Khrip
  дороже Node (×0,91) — как и Python (×0,82). Без кэша промпта Khrip дороже
  Node (×0,77) и почти равен Java (×1,02).
- Файлы проекта не считаются ни у кого (`go.mod`, `.csproj`, `pom.xml` с
  `application.properties`, `package.json`); у Java это ещё 337–404 токена на

- Все решения Java и Node написаны тем же ИИ, что и Khrip, и это не слепая
  проверка; размер одного правильного ответа — не стоимость его получения.

## Метод

Метод v2 ([точка отсчёта](2026-10-26-memory-baseline.md)), все языки одной
партией на сценарий, одни и те же данные `load/seed.py` и смеси
`load/<сценарий>.lua`, 64 соединения:

- **Замкнутый цикл** (`eval/perf.sh`, `wrk`): прогрев 60 с всем языкам (одно
  правило для всех, хотя JIT нужен только C# и Java), замер 60 с, **два круга**
  в противоположном порядке языков (Khrip … Node ×2, затем Node ×2 … Khrip);
  Python — только в первом круге, для сведения. Запросы в секунду, процессор
  сервера на запрос (utime + stime за замер), p50 и p99 (`wrk --latency`, без
  поправки на координированное упущение), пиковый RSS (VmHWM за всё время
  процесса, вместе с прогревом), запуск (медиана трёх: от запуска до первого
  ответа, у задач с базой — с созданием таблиц) и размер.
- **Одинаковая частота** (`RATE_MODE=1`, `wrk2 -R` из `load/rates.tsv`, та же
  частота всем, прогрев 60 с + замер 60 с): p50, p99, p99,9, процессор на
  запрос, пик и среднее RSS (выборка каждые 100 мс), достигнутая частота.
  Частоты выбраны 26.10 как min(0,7 · Go, 0,8 · C#) на прежней машине и здесь
  не менялись; если язык не держит частоту (достигнуто < 98 %), прогон помечен
  `behind` (⚠), частоту ради него не снижали.
- **Память от числа соединений** (`CONN_SCALE="64 1000 10000"`, 500
  запросов/с) — shortener, bank, ledger; RSS — среднее за последние 30 с, когда
  открыты все соединения; наклон — КБ на соединение.
- **10 минут** (`bench/mem/long.sh`) — bank и notes при одинаковой частоте:
  прогрев 60 с, замер 600 с; пик RSS, среднее за последние 300 с и наклон.
- **Пороги** (бриф выпуска, правило 1): в каждом сценарии Khrip ≥ лучшего из
  основных языков (Go, C#, Java, Node, Bun; в задачах с базой ещё Node ×2) в
  том же прогоне — по запросам в секунду и процессору на запрос в замкнутом
  цикле (среднее двух кругов; отдельно — в скольких кругах), по p99 и пиковому
  RSS при одинаковой частоте. При одинаковой частоте сравниваются только
  прогоны, которые её удержали: у отставшего меньше запросов, данных и памяти,
  и это не та же нагрузка.
