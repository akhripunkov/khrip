## Пункты

1. **Быстрые пути библиотеки** (633e9b2).
   - `lower()`/`upper()` строки ASCII **до 31 байта** — одним проходом по
     словам (последнее слово — внахлёст; короче 8 байт — одно слово из
     байтов) и одним выделением короткой строки (`__tx_case_ascii`). С 32 байт
     прежний путь с блоками AVX2 дешевле (callgrind: 397/402 команды на 32
     байта, 418/626 на 64), поэтому порог — 31, а не 256, как в патче части 1.
     На 14 байтах — 487 → 282 команды на вызов, на 4 — 381 → 258
     (`micro/lowbench.kh`, с циклом замера).
   - `x.lower().contains(y)`: компилятор вызывает `__text_contains_lower(x, y)`
     (src/atom.kh, `parse_lower_contains`). Если в x нет байтов ≥ 0x80, y
     ищется в x с каждым байтом в нижнем регистре, без копии; первый байт y —
     словами по 8 мест (точная проверка нулевого байта, без ложных мест);
     иначе — прежний путь (lower, затем поиск). От патча части 1 отличается
     поиском по словам и ранним «нет», если первый байт y — заглавная или
     ≥ 0x80. Пустая y — сразу «да». 460–570 → 200–260 команд на имя
     (`micro/clbench2.kh`, имена по 14–20 байт).
   - `__str_cmp`: первый неравный байт — `ctz` по xor первого неравного слова,
     хвост — словом внахлёст (без побайтового цикла от 8 байт). Встраивать
     сравнение первого слова не стал: у строк времени bookings первые 8 байт
     («2026-11-») равны почти всегда, и встроенная проверка вела бы к тому же
     вызову; сам вызов — генерация кода (часть 3).
   - `__memeq` (вне брифа, в том же духе): хвост — словом внахлёст, 4–7 байт
     — двумя кусками по 4. Строковые ключи и `==` дешевле: свёртка, как в
     /categories (`micro/mapbench.kh`), — 714 → 635 команд на товар.
   - Хеш `map[str]`: по 8 байт за шаг (xor, умножение, сдвиг), хвост —
     внахлёст, в конце — перемешивание как у splitmix64; тело — прямо в
     `__map_hash` (отдельная функция стоила вызова). Хеш живёт только в
     процессе: снимок KHRIP_DATA — JSON, таблицы при загрузке строятся заново,
     порядок записей — порядок вставки (от хеша не зависит). Моделирование
     (`hash_sim.py`, линейные пробы, загрузка ≤ ½): прежний хеш давал 4,4 пробы
     на номерах-строках «1»…«100000» (макс. 182) и тысячи — на двухбайтовых
     ключах; новый — 1,2–1,5 везде. На ключах catN из 20 штук прежний был
     «идеальным» (1,0 пробы против 1,3) — поэтому хеш один выиграл мало, а
     вместе с `__memeq` — −11 % на товар.
   - «Одна проба на прочитать-и-записать» **не сделана**: ключи у пары
     `cats[p.category] ?? ...` и `cats[c.name] = c` — разные выражения, а кэш
     последнего поиска надо сбрасывать при каждой записи и шаге роста —
     недёшево сделать безопасно.
2. **Вынос неизменных вызовов из лямбд** (62cea22). `имя.lower()`, `upper()`,
   `trim()`, `len()` в теле лямбды считаются один раз до цикла, если имя —
   неизменяемая локальная или параметр типа `str` (не `str?`), объявленная вне
   лямбды и не объявленная в ней заново (параметр, let/var, for, if let,
   привязка match). Одинаковые вызовы — одна скрытая локальная. Пустой список —
   вызов один лишний раз, у этих методов без последствий. `var` не выносится,
   даже если в лямбде ему не присваивают (строже брифа).
3. **Слияние цепочек** (0b58a5e). `m.values()` с цепочкой `filter`/`map`/`any`/
   `all`/`count`/`find`/`sort_by` и цепочка из двух звеньев и больше у списка —
   один цикл (src/variant.kh, `parse_fused`): по массивам словаря (признак
   «жива», значение — словом или байтом у bool; число записей — из заголовка
   на каждом шаге, как у `for` по словарю) или по списку. Цепочка кончается
   на первом из any/all/count/find/sort_by; `sort_by` копит элементы и ключи и
   сортирует один раз. Сливаются только цепочки, где **все** лямбды без
   побочных действий (src/rw.kh, `lambda_pure`; иначе — прежний код целиком):
   нет присваиваний, изменяющих методов, return/break/continue, sql/ch, fetch,
   call, tx, функций библиотеки вне короткого списка чистых (`time_iso`,
   `parse_time`, `parse_date`, `to_json`, `sha256`, `url_encode`, `env`,
   подстановка `"{x}"`) и вызовов функций программы, у которых это есть
   (неподвижная точка; функция может присваивать своим локальным и менять
   свежие локальные коллекции). Семантика записана в docs/KHRIP.md: цепочки
   поэлементные, как в C#, Rust и Java Streams; видно это только по панике
   (её текст — у первого по порядку обхода элемента) и по тому, что any/all/
   find не смотрят элементы после ответа. Словарь в цикле не меняется
   (лямбды не пишут), поэтому словарь store, растущий по частям, читается
   по старым массивам, как values() и читатели; в читающем маршруте — под
   разделяемой блокировкой. `for x in m.values()` не сливается (вне брифа);
   поэтому /categories по-прежнему строит values() для своего цикла.
4. **Анализ чтения** (c506b35, src/rw.kh). Свежими стали `a ?? b` (если свежи
   обе части) и элемент `m[k]` локального словаря, объявленного как `{}`, в
   который кладут только свежее (`m[k] = v` со свежим v; предположение, что
   его собственные элементы свежие, — индукция по вставкам) и который больше
   никак не упоминается (кроме `m[k]`, `len/has/get/remove/keys/values/clear/
   contains(...)` и `for ... in m`: псевдоним, аргумент, возврат, литерал
   могли бы положить в него значение store в обход проверки). Параметр
   лямбды с именем свежей локальной — другое имя, если упоминание вне тела
   этой лямбды. GET /categories стал читающим; среди решений eval других
   изменений режима нет (`khc check --locks` по всем). Заодно исправлена
   старая ложная «свежесть» `a ?? b.copy()` (см. итоги).

## 7. Отступления от брифа и риски

Отступления:
- быстрый `lower()` — до 31 байта, а не для любых коротких (длиннее дешевле
  прежний путь);
- сравнение первого слова строк не встроено (§ п. 1), «одна проба» для
  `m[k] ?? d; m[k] = v` не сделана;
- `__memeq` ускорен (вне брифа), хеш встроен в `__map_hash`;
- вынос — только у let и параметров, не у var;
- у списков сливаются цепочки от двух звеньев (одно звено — и так один цикл);
  цепочка с одной нечистой лямбдой не сливается целиком (без слияния чистого
  начала); `for x in m.values()` не сливается;
- замер — одна партия на все стадии и C# (а не партия после каждого пункта):
  у каждого пункта есть своя строка против C# в той же партии;
- полный набор в трёх режимах — на основе, после п. 1 и на итоге.

Риски:
- **Семантика:** у чистых цепочек меняется, какая паника видна, и any/all/
  find больше не дают панике случиться в предыдущем звене на поздних
  элементах. Записано в docs/KHRIP.md; цепочки с побочными действиями — как
  раньше.
- **Анализ чистоты** — по лексемам; лямбда, ошибочно названная чистой,
  поменяла бы порядок побочных действий. Он консервативен (неизвестная
  функция — нечиста), правила покрыты мутациями.
- **Анализ чтения:** ложное read — гонка данных. Новые правила узкие (словарь
  `{}`, только свежие вставки, никаких других упоминаний), отрицательных
  случаев 12, мутаций 7. Глубина проверки ограничена 8 шагами — сложное
  (`a[k] ?? b[k] ?? ...`) остаётся write. Ревью нашло в нём срезы по строкам
  и по именам, которые давали ложное read (§9); после правок — 47 пишущих
  маршрутов в tests/locks/fresh_maps, rw_aliases и rw_named, 16 мутаций
  анализа и генератор (55 080 маршрутов без ложного read). Анализ по-прежнему по лексемам, а не по дереву разбора.
- **Хеш** без случайной затравки, как и прежний: подобранные ключи могут
  дать длинные цепочки.
- **Раскладка кода:** ±4–5 % на коротких запросах от сдвига адресов (§4).
- **Хвосты p99,9 на 5 000/с** (§3) не объяснены.

Найдено по пути (вне пунктов): `[1, 2].join(",")` (и любой `[int]`/`[float]`)
проходил проверку типов и падал с SIGSEGV — получатель метода `join` не
сверялся с `[str]` в `parse_method` (src/atom.kh). Исправлено после ревью
(§9).

## 9. После ревью

Независимое ревью (вопросы — ложное read, ложная «чистота», слияние, чтение
за концом памяти; повтор bank и shop) нашло ложные read в анализе чтения и
две ошибки методов. Исправлено одним коммитом 19c53d8.

1. **`??` в начале следующей строки (серьёзно).** `rw_expr_end` кончал
   выражение с концом строки, а парсер переводов строк внутри выражения не
   видит. В
   ```
   let b = seen["a"]
       ?? boxes["a"] ?? Box { n: 0, tags: [] }
   b.n += 1
   ```
   судилась только первая строка (`seen["a"]` — элемент свежего словаря), и
   маршрут, который меняет запись store, получал read — гонка данных (ревью
   показало её на сервере). Теперь конец выражения находит `rw_expr_scan`,
   который повторяет грамматику парсера (src/expr.kh, src/atom.kh): операторы
   `?? || && == != < <= > >= + - | ^ * / % << >> &` и постфиксы `.имя`,
   `.имя(...)`, `[...]` продолжают выражение и на новой строке, `;` лексер
   отбрасывает; незнакомое (fetch, sql, call, tx) — не свежее. Остальные срезы
   по лексемам проверены, три тоже были неверны:
   - цель присваивания искалась от начала строки, и `let t = 1; c.name = "x"`
     считалось объявлением — ложное read. Теперь цель — цепочка
     `имя(.поле | [...])*` назад от `=`; так её разбирает и парсер
     (`stmt_has_assign`: оператор начинается с имени, `=` — на его первой
     строке, поэтому `c.\nname = v` не компилируется);
   - объявление `let/var имя: тип =` узнавалось по любым именам и скобкам до
     `=`: в `var x: [int]; lists[k] = [1]` запись в store была «объявлением
     x». Это ложное read старше этапа (раньше — по началу строки). Теперь тип
     разбирается, как в `parse_type`;
   - присваивание имени (`c = groups["a"]`) замечалось только в начале
     строки — теперь где угодно.
2. **Имена (средне).** Свежесть локальной и свежего словаря решалась по
   объявлениям с этим именем где угодно в теле: `var groups = {}` во
   вложенном блоке (или ниже) делала «свежим» store `groups`, `let xs: [int]
   = []` в блоке — параметр `xs`. Теперь имя параметра функции, глобальной
   или store не судится по let/var вообще, а имя с двумя объявлениями — не
   свежее (по лексемам не понять, к которому относится упоминание). Анализ
   чистоты пользуется тем же кодом (`rw_assign_effect`, `rw_fresh_local`):
   функция, которая меняет глобальную `log` при локальной `log` во вложенном
   блоке, больше не «чистая», и цепочка с ней не сливается.
3. **Свои функции с именами методов (средне).** `x.values()`, `keys`,
   `filter`, `map`, `copy`, `split` считались новой коллекцией по имени, а
   `sort`, `sort_by`, `reverse` — своим получателем; но своя `fn values(s:
   Shop) -> [Cat] { return s.cats }` вызывается как `shop.values()` и отдаёт
   список store. Теперь — только если в программе нет функции с таким именем.
4. **Внутренние функции как методы (низко).** `xs.grow(n)`, `xs.vacate(i)`,
   `xs.cap()` вызывали `__list_*` библиотеки (`vacate` обнулил бы память
   списка store мимо блокировки). Теперь в коде программы у списков, int,
   float и bool — только методы из docs/KHRIP.md, остальное — «[int] has no
   method 'grow'» с подсказкой-списком методов списка.
5. **`[1, 2].join(",")` (низко).** Получатель сверяется с первым параметром
   функции библиотеки: «.join() works on [str], not [int]» с подсказкой
   `xs.map(x => x.to_str()).join(", ")`; так же `["a"].sum()`.
