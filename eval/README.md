# Проверка на типичных задачах бэкенда

Главная цель Khrip — чтобы ИИ писал на нём дешевле, чем на Go, C# и Python. Здесь
набор задач, общие проверки и протокол, по которому это можно измерить честно,
в том числе не нам.

## Что в наборе

- `tasks/<задача>/task.md` — условие на английском, без упоминания языка: порт
  8080, данные в памяти, коды ответов, проверки ввода.
- `tasks/<задача>/check.sh` — сценарий запросов через `curl` к уже запущенному
  серверу: коды ответов, тела, заголовки, одновременные запросы. От языка не
  зависит.
- `run.sh <задача> <язык> [папка]` — собрать, запустить и проверить решение. Языки:
  `khrip`, `go`, `csharp`, `python`; для любого другого — `START="команда" run.sh
  <задача> other <папка>`.
- `solutions/<задача>/<язык>/` — наши решения на Khrip, Go, C# и Python. Все
  проходят проверки.
- `PROMPT.md` — текст запроса к модели и правила попыток.
- `perf.sh` — нагрузочный замер: скорость, задержки, процессор, память, запуск,
  размер, время сборки и инварианты под нагрузкой; `load/` — данные и смеси
  запросов для `wrk`; `perf_table.py` строит таблицы. `RATE_MODE=1` — память
  при одной частоте для всех языков (wrk2, `load/rates.tsv`, RSS каждые 100 мс),
  `CONN_SCALE="64 1000 10000"` — память от числа соединений (`perf_rate.sh`;
  отчёт — bench/results/2026-10-26-memory-baseline.md).
- `results/` — таблицы токенов и замеров.

Задачи:

| Задача | Что проверяет |
|---|---|
| shortener | случайные коды, 302 с `Location`, проверка формата, 409 |
| bank | деньги в центах, переводы, 409 при нехватке, 60 одновременных переводов |
| notes | регистрация, пароли (соль + медленный хеш), токены, `Authorization: Bearer` |
| ratelimit | окно на ключ из заголовка, 429 с `Retry-After`, переменная окружения |
| catalog | дробные цены, фильтры, сортировки, страницы, PATCH, группировка |
| inventory | заказы «всё или ничего», отмена, одновременные заказы |
| polls | голос один раз на голосующего, проценты, 403/409 |
| bookings | разбор и проверка дат, пересечение интервалов, фильтр по дню |
| ledger | PostgreSQL: переводы «всё или ничего», 409/422, ключ идемпотентности при одновременных запросах |
| shop | PostgreSQL: поиск с фильтрами и сортировкой, заказы со складом, отмена, сводка по категориям |
| tracker | PostgreSQL: номера задач по проекту без пропусков, PATCH, фильтры, сводка |

Задачи с базой (файл `tasks/<задача>/db`) получают пустую базу в `DATABASE_URL`:
таблицы сервер создаёт сам, проверки идут через две копии сервера на одной базе
и после перезапуска.

## Токены

Размер правильного решения в токенах (`bench/tokens/eval.mjs`, код без
комментариев). Первые пять задач — **настроечные**: на них мы искали пробелы
языка и дорабатывали его (заголовки, `fail`, сужение `T?`, параметры по
умолчанию, `...` для PATCH, регулярные выражения, сырые строки). Три последние —
**отложенные**: написаны после того, как язык заморозили. Таблицы: «до доработок»
— [results/tokens-before.md](results/tokens-before.md), язык заморожен —
[results/tokens-frozen.md](results/tokens-frozen.md), итог —
[results/tokens.md](results/tokens.md).

| | Khrip | Python FastAPI | C# | Go |
|---|---:|---:|---:|---:|
| 5 настроечных задач, до доработок v0.9 | 2886 | 3168 (×1,10) | 3270 (×1,13) | 5079 (×1,76) |
| 5 настроечных задач, после | 2645 | 3168 (×1,20) | 3270 (×1,24) | 5079 (×1,92) |
| 3 отложенные задачи, язык заморожен | 2431 | 2186 (×0,90) | 2427 (×1,00) | 3425 (×1,41) |
| 3 отложенные, после `parse_time` | 1944 | 2186 (×1,12) | 2427 (×1,25) | 3425 (×1,76) |

o200k; в скобках — во сколько раз больше, чем у Khrip. Честный итог: на
отложенных задачах замороженный Khrip **не лучше Python** — бронирование без
разбора дат заняло 1046 токенов против 711; на складе и опросах Khrip меньше на
5–7%. После добавления `parse_time`/`parse_date` бронирование — 573, но это уже
снова доработка под увиденную задачу.

Задачи на PostgreSQL (v0.12; язык дорабатывался и на них — в первую очередь
проверки SQL):

| | Khrip | Python FastAPI | C# | Go |
|---|---:|---:|---:|---:|
| ledger, shop, tracker | 4295 | 5819 (×1,35) | 7428 (×1,73) | 9922 (×2,31) |

Здесь разрыв больше, чем на задачах без базы: на Khrip запрос — строка SQL с
`{x}` и тип результата, без кода подключения, чтения строк и разбора ошибок; на Go
это самый объёмный код решения. Справочник языка при этом вырос с 3025 до 3945
токенов.

Чего эти цифры **не** доказывают:

- Все решения написаны одним автором — тем же ИИ, который проектировал Khrip.
  Решения на других языках написаны добросовестно и проходят те же проверки, но
  оценку самого себя нельзя считать независимой. Решение бронирования на
  замороженном языке сохранено: [results/bookings-frozen.kh](results/bookings-frozen.kh).
- Размер готового решения — не то же, что стоимость его получения. Настоящая
  метрика — токены на решённую задачу: спецификация в промпте + все попытки +
  исправления. Модель видит Khrip впервые, а Go, C# и Python знает по миллионам
  примеров, поэтому может ошибаться на Khrip чаще.
- Задачи придумал тот же автор. Отложенные задачи защищают от подгонки языка, но
  не от подбора удобных для Khrip задач.

## Скорость, задержки, процессор, память

`perf.sh` для каждой задачи и языка: собирает решение, трижды замеряет запуск,
заполняет сервер одинаковыми данными (`load/seed.py`: 1000 ссылок, 100 счетов,
2000 товаров, 200 позиций склада, 100 опросов, 500 броней), даёт 3 с прогрева и
10 с нагрузки `wrk` (64 соединения) со смесью запросов из `load/<сценарий>.lua`.
Сервер — на 2 ядрах, `wrk` — на двух других. После нагрузки проверяются
инварианты: сумма денег в банке и товар на складе (с заказами) не изменились.
Все таблицы — [results/perf.md](results/perf.md).

Сводка — среднее геометрическое по 10 сценариям:

| | Khrip | Go | C# | Python |
|---|---:|---:|---:|---:|
| запросов в секунду | **35 235** | 18 087 | 23 157 | 1 953 |
| p50 / p99, мс | **1,6 / 9,3** | 3,2 / 22,7 | 2,3 / 20,9 | 30,7 / 135 |
| мкс процессора на запрос | **48** | 98 | 77 | 544 |
| память с данными до нагрузки, МБ | **0,3** | 9,2 | 72 | 45 |
| запуск, мс | **15** | 16 | 376 | 377 |
| размер | 123 КБ | 8,5 МБ | 95 КБ + среда .NET | 3 КБ + Python и пакеты |

По сценариям Khrip быстрее всех в 8 из 10 (в 1,2–2,6 раза быстрее лучшего из C# и Go). C#
быстрее в двух сценариях, где много вычислений над списками на запрос: поиск по
каталогу (20,5 тыс. запросов в секунду против 8,8 тыс.) и расписание переговорных
(10,8 против 8,0). Это генератор кода Khrip: пять фильтров по 2000 товаров
стоят ~15 нс на элемент за фильтр, JIT в .NET делает это в несколько раз быстрее.

Память. Пустой сервер Khrip занимает 0,2 МБ, с данными — до 1 МБ, данные хранятся
плотнее, чем у Go, C# и Python (банк: 95 байт на запрос против 148, 197 и 289).
Но **старые значения в `store` не освобождаются**: в сценарии, где товары только
обновляются, память Khrip растёт на ~96 байт на обновление без предела (168 МБ за
13 с), а у Go, C# и Python остаётся на месте. Для сервера, который работает
неделями и часто меняет данные, это пока главный недостаток.

Задачи на PostgreSQL ([results/perf_db.md](results/perf_db.md), три прогона, медиана):
перед каждым запуском — пустая база, затем 100 счетов, 500 товаров, 1000 задач;
PostgreSQL на той же машине без привязки к ядрам. Кроме процессора сервера
считается процессор базы на запрос.

| | Khrip | Go | C# | Python |
|---|---:|---:|---:|---:|
| запросов в секунду (ср. геом.) | **3 754** | 2 891 | 2 316 | 1 275 |
| p50 / p99, мс | **15,5** / 46,9 | 21,0 / **40,6** | 23,2 / 139 | 47,9 / 100 |
| мкс процессора сервера на запрос | **140** | 289 | 467 | 769 |
| мкс процессора PostgreSQL на запрос | 612 | **528** | 890 | 698 |
| память с данными, МБ | **0,8** | 14 | 95 | 48 |

Решения на Go, C# и Python держат строки `SELECT ... FOR UPDATE` в READ COMMITTED,
Khrip — `tx { }` в SERIALIZABLE: блокировок в коде нет, но около 15% переводов в
ledger повторяются, отсюда больше процессора базы.

Python запущен одним процессом uvicorn (с uvloop): данные в памяти процесса, а
несколько процессов не делят их между собой. Поэтому у него одно ядро из двух.

Что замер нашёл и что исправлено в этой же версии:

| Проблема | Было | Стало |
|---|---|---|
| вход: блокировка `store` держалась во время PBKDF2, все входы шли по одному | 5 входов/с, все по тайм-ауту | 116 входов/с |
| SHA-256 без инструкций процессора | 100 тыс. итераций PBKDF2 — ~560 мс | 16 мс (SHA-NI), быстрее OpenSSL (26 мс) |
| печать дробного числа через длинную арифметику | 15 мкс на число | 0,25 мкс; опросы 37 → 107 тыс. запросов/с |
| `lower`/`upper` и поиск подстроки по байту | — | по 8 байт за шаг; каталог ×1,3 |
| одна блокировка `store` на всё: читающие запросы шли по одному | каталог 5,1 тыс. запросов/с | 8,8–9,7 тыс.: компилятор находит маршруты, которые только читают, они идут параллельно |
| (v0.10) процессор без SHA-NI: SHA-256 шёл обычным кодом Khrip | `hash_password` — 560 мс, все входы по тайм-ауту | 81 мс — машинный код компилятора; Go — 70 мс, OpenSSL — 114 мс на той же машине |

## Протокол слепой проверки

1. Взять модель, которая не участвовала в разработке Khrip (любого поставщика).
2. Для каждой задачи и языка — новый диалог с текстом из `PROMPT.md`. Для Khrip в
   промпт входит `docs/KHRIP.md` целиком (~3000 токенов o200k), его стоимость
   учитывается.
3. Ответ модели сохранить в `attempts/<модель>/<задача>/<язык>/`, запустить
   `run.sh`. Не прошло — отправить вывод (ошибки компилятора или строки `FAIL`) и
   попросить файл целиком. Не больше 5 попыток.
4. Записать: прошло ли, число попыток, токены запроса и ответа по каждой
   попытке. Итог по языку — доля решённых задач и средние токены на решённую.
5. Повторить 3 раза на задачу и язык: модели недетерминированы.

Khrip выигрывает, только если при сравнимой доле решённых задач токенов на
решённую задачу меньше, чем у C# и Go, — с учётом спецификации в промпте.
